# 确定性测试模式

本文档定义了 QuantPilot 在第 1 周及以后使用的确定性测试模式。

其目的不是完美模拟现实。其目的是使编译、运行、回放、回测和 CI 行为足够可重复，以安全地测试当前 beta。

## 角色

确定性测试模式的存在是为了支持：

- 后端服务级别 API 测试
- 运行时回放和回归检查
- 编译和运行合约验证
- CI 安全的回测冒烟覆盖
- 未来前端 E2E 流程，不得依赖实时时序变化

它不重新定义交易模型。它约束执行，使得相同输入在相同模式和种子下产生稳定输出。

## 非目标

确定性测试模式不是：

- 实盘交易环境
- 真实市场保真度的声明
- 未来精确回测模式的替代
- 绕过已声明能力门禁的许可

如果某个行为仅在确定性测试模式下工作，但无法通过相同的公共运行时合约表达，它应被视为仅测试基础设施而非产品能力。

## 最小保证

当确定性测试模式启用时，QuantPilot 应保证：

- 固定种子或显式的无随机行为
- 固定或模拟的时钟行为
- 稳定的事件排序
- 不依赖外部网络状态
- 不依赖进程全局的可变开关
- 从相同输入包可重复回放
- 与正常 beta 模式相同的能力边界

关键规则很简单：测试模式可以简化时序和执行条件，但不得发明不受支持的产品特性。

## 必需的控制

测试模式的运行时入口点应显式暴露这些控制。

当前第 1 周实现位于：

- [qrpc_runtime/src/sandbox.rs](/D:/rust-js-pr/QuantPilot/quantpilot/qrpc_runtime/src/sandbox.rs)
- 通过 [qrpc_runtime/src/lib.rs](/D:/rust-js-pr/QuantPilot/quantpilot/qrpc_runtime/src/lib.rs) 导出

当前 Rust 面是：

- `DeterministicTestMode`
- `DeterministicClockMode`
- `DeterministicEventOrdering`
- `DeterministicParallelismPolicy`
- `RuntimeSupportBoundary`

- `enabled`：确定性测试模式是否活跃
- `seed`：存在随机性时的可重现伪随机种子
- `clock_mode`：挂钟或模拟时钟
- `start_time`：相关的固定逻辑开始时间戳
- `event_ordering`：排队事件的确定性排序策略
- `parallelism_policy`：受约束的线程或单线程执行（当可重现性需要时）

这些控制不得隐藏在环境变量或临时的全局变量中。当前第 1 周测试也锁定要求不同沙箱实例可携带不同的测试模式配置，而不依赖任何进程全局开关。

## 适用范围

### 编译和能力验证

确定性测试模式不放松能力门禁。

在正常 beta 模式下被拒绝的相同图或脚本在使用以下内容时仍应在测试模式下被拒绝：

- 不支持的指标
- 不支持的执行模块
- 隐藏或受门禁控制的前端模块
- 未声明的运行模式

### 服务级别 API 测试

对于 `/api/compile`、`/api/run`、`/api/backtest` 和 `/api/capabilities` 测试：

- 输入应为固定 fixture
- 返回的事件顺序应稳定
- 测试应断言结构化字段而非偶然格式
- 失败应可归因于合约漂移，而非时序噪音

### 回放和回归

回放是测试模式的主要消费者之一。

为保持回放有意义：

- 相同的输入图、市场数据 fixture 和运行时配置应重现相同的事件序列形态
- 成交行为应在相同种子和模式下保持稳定
- 快照和摘要应可在运行间比较

### 前端 E2E

当第 2 周引入浏览器 E2E 覆盖时，前端冒烟测试应针对确定性后端行为，而非时序敏感的实时循环。

这尤其重要：

- 编译按钮流程
- 事件流断言
- 回测摘要渲染
- 能力驱动的模块可见性

## 与沙箱模式的关系

确定性测试模式与沙箱模式正交。

它可以在以下模式内使用：

- `RealTimeSandbox` 用于可重复的运行时冒烟覆盖
- `FastBacktestSandbox` 用于 CI 安全的回放验证

当前第 1 周实现将选定的测试模式存储在沙箱实例内部，并通过 `SandboxSnapshot` 暴露。

它不应与未来的 `AccurateBacktestSandbox` 混淆。精确模拟关乎保真度。确定性测试模式关乎可重复性和合约置信度。

## 当前 beta 边界

在当前阶段，确定性测试模式应保持与实际 beta 边界一致：

- 仅 `paper`
- 有限的交易所集
- 有限的交易对集
- 能力门禁模块保持受门禁控制

当前第 1 周实现也通过 `RuntimeSupportBoundary` 导出运行时对齐的支持边界，因此 `/api/capabilities` 和运行时编译门禁不需要单独复制运行时模式和执行模块真实数据。

这保持测试基础设施诚实。项目绝不应使用测试模式来制造产品并未实际提供的支持表象。

- 测试模式的目的和边界清晰记录
- 测试模式与实盘交易和高保真回测显式区分
