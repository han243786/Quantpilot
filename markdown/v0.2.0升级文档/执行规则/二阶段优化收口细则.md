# QuantPilot v0.2.0 第二阶段优化收口细则

## 执行摘要

本文档基于 2026-04-30 全量审计结果制定。审计结论：v0.2.0 五阶段（Block A–E）框架已完整落成，**编译零错误、346 项测试全量通过**，但存在若干关键路径空洞、运维硬化缺失和发布门禁空白。本次优化的核心原则：

1. **不纳入新功能，不画新饼，不引入新思想** — 只对已有目标进行硬化
2. **排雷优先于收口，收口优先于打磨** — P0 阻性项必须先清零
3. **每一项改动必须有明确的验收标准** — 拒绝"改好了"式的主观判断
4. **所有变更不得偏离开发思想** — AI 在审批链之后、沙箱验证是唯一信任来源、运维闭环优先于功能堆叠

## P0 — 发布阻塞（必须清零方可进入 staging）

### P0-1: HotSwap AtomicSwitch 实现真实模块切换

**现状**: `qrpc_runtime/src/hotswap.rs` 中 `AtomicSwitch` 步骤仅写入一条日志事件 `"atomically switched deployment_revision"`，未执行任何实际模块替换。

**目标**: 在安全窗口内完成模块指针的原子替换。

**验收标准**:
- [ ] 切换后 `RuntimeCoordinator` 的 intent/agent/risk/execution 模块引用指向新模块
- [ ] 旧模块的状态快照已序列化并传递给新模块
- [ ] 若新模块状态迁移失败，自动回退到旧模块并记录 `SwapRolledBack` 事件
- [ ] 切换耗时 < 100ms（不含状态迁移耗时）
- [ ] 新增测试用例：成功切换、状态迁移失败回退、空模块目标拒绝

**涉及文件**:
- `qrpc_runtime/src/hotswap.rs`
- `qrpc_runtime/src/lib.rs` (RuntimeCoordinator)
- `qrpc_runtime/src/compat.rs`

**偏离开发思想的风险**: 无。文档明确要求"原子切换 deployment_revision"。

### P0-2: 合并引擎接入运行时链路

**现状**: `StrategyMergeEngine` 在 `qrpc_runtime/src/merge.rs` 中完整实现（三种合并策略、冲突裁决、集中度限制），但未接入主运行时链路，无 API 端点，运行时 Coordinator 不调用它。

**目标**: 将合并引擎作为 Agent 与 Risk 之间的标准处理节点。

**验收标准**:
- [ ] `RuntimeCoordinator` 在 Agent 产出候选后、Risk 裁决前调用合并引擎
- [ ] 多策略场景下，合并引擎产出单一 `MergedOutput` 而非透传多个候选
- [ ] 合并决策记录写入事件日志（含各策略权重、被压制信号、冲突计数）
- [ ] 新增 API: `GET /api/v1/merge/records?run_id=...` 查询合并记录
- [ ] 合并引擎配置可通过 runtime protocol config 控制（策略选择、权重上限）
- [ ] 新增集成测试：双策略加权合并、冲突压制、空输入降级为空操作

**涉及文件**:
- `qrpc_runtime/src/merge.rs`
- `qrpc_runtime/src/lib.rs`
- `src/runtime_api.rs`

**偏离开发思想的风险**: 无。文档明确要求"多策略输出统一进入合并层与统一风控"。

### P0-3: 沙箱验证实现真实参数注入回放

**现状**: `src/sandbox_verification.rs` 中 `compute_candidate_metrics()` 直接使用已有回测记录作为候选指标，未将 AI 提案中的参数注入沙箱执行独立回放。代码注释标注"后续阶段将集成"。

**目标**: AI 提案的参数变更在独立 `FastBacktestSandbox` 中执行完整回放窗口。

**验收标准**:
- [ ] 创建沙箱时注入候选参数覆盖（old_value → new_value）
- [ ] 回放窗口至少覆盖最近 30 天或可用事件全量
- [ ] 产出 8 项指标与基线对比（基线 = 当前已激活 generation 的回测结果）
- [ ] 沙箱回放使用与主运行时相同的 `capability_hash` + `event_slice`
- [ ] 若沙箱回放失败（数据不足/超时），报告标记 `replay_fidelity=partial` 并给出原因
- [ ] 验证耗时 < 5min（30 天窗口内）
- [ ] 新增测试：参数变更后沙箱产出差异报告、数据不足降级、超时处理

**涉及文件**:
- `src/sandbox_verification.rs`
- `qrpc_runtime/src/sandbox.rs`

**偏离开发思想的风险**: 无。这是文档核心结论之二："沙箱验证是唯一信任来源"。

### P0-5: 消除高风险 unwrap() 调用

**现状**: 全仓库 462 处 `.unwrap()`，集中分布在 `src/main.rs`（454 处）和集成测试中。生产环境下任一数据异常即进程崩溃。

**目标**: 生产路径中的 `.unwrap()` 替换为显式错误处理或安全默认值。

**验收标准**:
- [ ] `src/` 下所有非测试代码中：
  - 文件 I/O 路径：`.unwrap()` → `?` 传播或 `unwrap_or_*` 降级
  - JSON 解析路径：`.unwrap()` → `?` 传播
  - 时间计算路径：`.unwrap_or_default()` 安全降级
- [ ] 测试代码中的 `.unwrap()` 保留（测试中 panic 是期望行为）
- [ ] 处理后剩余 `.unwrap()` ≤ 30 处，且每处附带注释说明为何不可能失败
- [ ] `cargo clippy -- -W clippy::unwrap_used` 对 src/ 路径无新增告警
- [ ] 编译零错误，全部测试通过

**涉及文件**: 全量扫描，重点：
- `src/main.rs`（约 454 处）
- `src/runtime_api.rs`
- `src/runtime_persistence.rs`
- `src/compile_api.rs`

**偏离开发思想的风险**: 无。这是基础工程卫生。

## P3 — 优化打磨（架构完善 + 性能基线）

### P3-1: 事件信封升级为 Protobuf 内部格式

**现状**: 内部事件使用 JSON，序列化开销大、无 schema 校验。

**目标**: 内部模块间事件传递使用 Protobuf，前后端边界保持 JSON 兼容。

**验收标准**:
- [ ] 定义 `EventEnvelope.proto`，含 `event_id`、`event_name`、`schema_version`、`trace_id`、`ts_event`、`ts_ingested`、`payload`
- [ ] 核心事件类型（DataUpdated, IntentGenerated, RiskDecision, ExecutionPlanned, PositionUpdated）使用 Protobuf
- [ ] 前后端 API 边界仍使用 JSON（`RuntimeEventEnvelope`），序列化转换在 boundary 层完成
- [ ] `qrpc_core` 中新增 `event.proto` + 生成的 Rust 模块
- [ ] 回放兼容：Protobuf 事件可反序列化为 JSON 等价结构

**涉及文件**:
- `qrpc_core/src/event.proto`（新建）
- `qrpc_core/src/lib.rs`
- `src/runtime_event_projection.rs`

**偏离开发思想的风险**: 低。文档建议 Protobuf 信封，但转换成本需评估。JSON → Protobuf 迁移不影响外部 API 契约。

---

### P3-2: config_generation 计数器实现

**现状**: 参数变更使用 compile-time hash 作为版本标识，无递增 generation 号。

**目标**: 每次参数激活递增 `config_generation`，便于快速回滚和审计。

**验收标准**:
- [ ] `RuntimeCoordinator` 维护 `current_generation: AtomicU64`
- [ ] 每次 `ConfigGenerationActivated` 事件携带递增后的 generation 号
- [ ] 回滚时恢复到指定的 generation 号（不要求是上一号，可以是任意历史值）
- [ ] `GET /api/v1/runtime/generations` 返回 generation 历史列表
- [ ] 审批单的 `rollback_plan.target_generation` 使用 generation 号

**涉及文件**:
- `qrpc_runtime/src/lib.rs`
- `src/runtime_api.rs`

**偏离开发思想的风险**: 无。文档四层版本模型中明确定义了 `config_generation`。

---

### P3-3: Shadow Evaluation 在参数激活前执行

**现状**: 参数激活是直接生效，未经过影子回放验证。

**目标**: 参数在 `safe_window` 模式下激活前，使用最近 N 个事件做影子评估。

**验收标准**:
- [ ] 激活前在独立 sandbox 中使用最近 100 个 bar/tick 做 shadow evaluation
- [ ] 若 shadow 输出与当前 generation 偏差 > 阈值（如 sharpe 变化 > 50%），标记为高风险
- [ ] 高风险变更仍可人工审批通过，但审批 UI 显式标注"高风险"
- [ ] shadow evaluation 结果写入 mutation 记录
- [ ] 超时（5s）自动跳过 shadow 但标记 `shadow_skipped=true`

**涉及文件**:
- `qrpc_runtime/src/sandbox.rs`
- `src/runtime_api.rs`

**偏离开发思想的风险**: 无。文档明确描述"影子回放"机制。

---

### P3-4: 参数激活后观察窗口

**现状**: HotSwap 有观察窗口（60s），但参数 mutation 激活后无观察期。

**目标**: 参数激活后 60s 观察窗口，异常自动回滚。

**验收标准**:
- [ ] 参数激活后 `RuntimeCoordinator` 进入 60s 观察模式
- [ ] 观察期内若风控拒绝率 > 50% 或 order 异常率 > 阈值，自动回滚
- [ ] 观察期通过后记录 `ObservationPassed` 事件
- [ ] 观察窗口时长可通过 mutation 请求配置（默认 60s）

**涉及文件**:
- `qrpc_runtime/src/lib.rs`
- `src/runtime_api.rs`

**偏离开发思想的风险**: 无。文档 AI 变更生命周期中明确定义了"观察窗口（默认 60s，可配置）"。

---

### P3-5: 冷归档存储层

**现状**: 所有持久化数据存于 `storage/` 目录下，无分层/淘汰/压缩。

**目标**: 实现热—温—冷三层存储策略的基本框架。

**验收标准**:
- [ ] 事件明细 > 30 天自动移至 `storage/archive/` 子目录
- [ ] 归档文件使用 gzip 压缩（`.json.gz`）
- [ ] 关键事件（Key retention 级别）不受淘汰影响
- [ ] `GET /api/v1/storage/health` 返回各层占用统计
- [ ] 淘汰策略通过配置文件控制（`config/storage_policy.yaml`）

**涉及文件**:
- `src/runtime_persistence.rs`
- `src/main.rs`

**偏离开发思想的风险**: 无。文档定义了热—温—冷三层及 TTL 淘汰策略。
