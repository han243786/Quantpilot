# QuantPilot 非功能性需求实现细则深度研究报告

## 执行摘要

本报告以你在当前线程已经明确的协议锚点为第一优先级：主链路为 `Data → Intent → Agent → Risk → Execution → Fill`，关键事件至少包括 `DataUpdated / IntentGenerated / RiskEvaluated / ExecutionPlanned / OrderUpdated / PositionUpdated`。由于内部 RFC 原文没有附在本线程中，凡未在当前对话中被明确到字段级的内容，本文统一标注为“未指定”，并以“建议新增”的方式给出可执行实现细则。报告同时默认**不把真热插拔、任意策略任意组合、AI 直接插入执行链、毫秒级实盘调参**纳入第二阶段目标。  

公开资料显示，QuantPilot 的外部产品主线是可执行策略构建、回测、优化、导出，以及通过 MCP 服务器接入多类市场数据；帮助中心也把“Trading Strategies / Research Projects / QuantScript”作为独立工作流。这意味着第二阶段的非功能性建设，应该优先服务于**可执行、可回放、可解释、可导出、能力边界诚实**，而不是继续扩大功能表象。citeturn11view7turn11view8turn11view9turn14view0

本报告的核心结论有五条。第一，事件模型必须升级为“审计级事件总线”，每条事件都要同时满足审计内容、因果链、追踪关联和能力快照四类要求。第二，解释与报告不能无限保留，必须采用**热内存环形缓冲 + 温存储摘要 + 冷存储关键账本**的分层生命周期。第三，`/api/capabilities` 必须成为前端、文档、compile、runtime 的**唯一真实边界**，并通过 hash 与 CI 校验防止漂移。第四，权限治理必须遵守**最小权限**，AI 只能产出候选变更，插件默认无网络权限，非执行层不得跨层下单。第五，测试体系必须从“能跑”升级为“能验收”，其中回放验收和混沌实验要围绕稳态指标做。citeturn10view0turn11view3turn11view4turn11view6turn13view1turn17view0

从实施顺序看，建议先落地**事件契约、能力边界治理、安全权限底线**，再做**生命周期压缩、回放验收、监控告警**，最后做**容量管理、运营手册和混沌硬化**。如果只允许三次迭代，那么第一迭代必须把“边界诚实”和“证据链完整”立住，否则后续所有解释、优化与 AI 介入都会失真。  

## 约束与设计基线

### 范围边界

本报告只覆盖第二阶段的非功能性建设，不覆盖以下高风险目标：真热插拔、任意策略任意组合、AI 直接注入执行链、毫秒级实盘调参。它们会显著放大状态迁移、权限逃逸、回放不一致和审计失效风险，不适合作为第二阶段的默认范围。  

另一个基础约束是：公开资料虽然能证明 QuantPilot 的产品形态确实围绕策略、回测、优化、导出和 MCP 数据集成展开，但这些公开页面**不能替代内部 RFC 的字段定义**。因此，本文把公开资料只用作产品语义和行业实现依据；涉及事件名、链路顺序和内部能力边界时，仍以你在当前线程给出的协议锚点为准。citeturn11view7turn11view8turn11view9turn14view0

## 事件模型与数据契约

### 目标

这一维度的目标，是把现有“运行事件”提升为**可审计、可回放、可关联**的统一证据链。事件不能只是普通日志；它必须同时回答：发生了什么、何时发生、在哪里发生、由谁/哪个模块触发、结果如何、与哪些上下游事件有关。NIST 在审计记录内容上明确强调 `what / when / where / source / outcome / identity` 六类信息；OpenTelemetry 则强调日志要通过 `TraceId`、`SpanId` 和 `Resource` 与追踪、指标建立可靠关联。citeturn5search38turn10view0

### 设计原则

事件模型建议遵循四个原则。其一，**append-only**，不允许就地修改原事件，只允许后续补充校正事件。其二，**同一条业务因果链只有一个主键体系**，即 `event_id + run_id + sequence_no + parent_event_id + causation_event_id`。其三，**事件包络与业务负载分离**，包络统一、payload 按事件类型版本化。其四，**能力快照可追溯**，每条关键事件都能追溯到当时的 `capability_hash / strategy_version / parameter_version`。这样，回放时才能判断“结果差异究竟来自市场数据、参数变化，还是能力边界变化”。  

### 具体实现建议

#### 公共事件包络

公共 envelope 建议统一如下。这里的“来源”列里，`协议锚点` 表示来自当前线程已明确的链路与事件；`建议新增` 表示为了非功能性治理而补入的最小字段。

| 字段 | 必填 | 类型 | 来源 | 说明 |
|---|---|---|---|---|

| `stage` | 是 | enum | 协议锚点 | `data/intent/agent/risk/execution/order/position/system` |

| `occurred_at` | 是 | RFC3339 timestamp | 建议新增 | 事件真实发生时间 |
| `ingested_at` | 是 | RFC3339 timestamp | 建议新增 | 进入事件存储时间 |
| `trace_id` | 否 | hex string | 建议新增 | 参考 OTel，以便跨信号关联 |
| `span_id` | 否 | hex string | 建议新增 | 参考 OTel |
| `parent_event_id` | 否 | UUID | 建议新增 | 上一层直接父事件 |

| `module_key` | 是 | string | 建议新增 | 触发模块唯一键 |
| `module_version` | 是 | string | 建议新增 | 模块版本 |

| `symbol` | 否 | string | 建议新增 | 交易对；未指定则为空 |
| `venue` | 否 | string | 建议新增 | 市场/执行目的地；未指定则为空 |
| `mode` | 是 | enum | 建议新增 | `backtest/paper/live`；未指定则按实际运行模式填 |

### 验收测试用例

事件契约层至少要有这些验收用例：

| 用例 | 预期结果 |
|---|---|
| 启动一次 paper run | 六个关键锚点事件至少能按因果链串起来 |
| 同一 `run_id` 连续发事件 | `sequence_no` 严格递增，不允许回退 |
| 随机打断一条父链 | 产生 `EventGapDetected`，同时监控指标递增 |
| 运行时切换参数版本 | 后续事件的 `parameter_version` 变化清晰可见 |
| 使用旧前端读取新事件 | 通过 `payload_version` 做兼容或显示明确不兼容 |
| 读取时间轴 `view=key` | 只能看到买卖点、仓位变化、风控拒绝等关键事件 |

### 失败模式与降级策略

如果事件写入成功但索引更新失败，运行链不可中断，但必须把事件进入“未索引队列”，UI 降级为只能读取原始流，不能承诺高级查询。  
如果出现 `sequence_no` 缺口或父链断裂，系统不能静默吞掉，必须立刻发出 `EventGapDetected` 并把该 `run_id` 标记为“回放不可信”。  
如果 `capability_hash` 缺失，则禁止生成关键业务事件，只允许产生系统错误事件；因为没有能力快照的事件无法做可信回放。  

### 优先级与实施难度评估

这一维度优先级是 **P0**，实施难度 **中**。它不是最难，但必须最先做，因为后续所有治理都会依赖它的存在。

## 事件存储与报告生命周期

### 目标

这一维度的目标，是把“巨量解释”和“长期关键账本”分离，让系统既不会因为解释过多而爆内存，也不会因为过度压缩而失去复盘价值。参考 TTL 的通行做法，历史数据可以按年龄被删除、汇总、列级过期、迁移到冷热存储，或者重压缩到更高压缩率的介质。ClickHouse 的 TTL 实践明确展示了这几类生命周期操作都可以并存，而且历史压缩会在节省空间和查询 SLA 之间做权衡。citeturn17view0

### 设计原则

建议采用“三层四类”的生命周期设计。三层是：**热层内存环形缓冲、温层本地摘要存储、冷层关键账本存储**。四类是：**关键事件、摘要事件、调试事件、解释文本 blob**。调试类和长解释类必须天然短命；关键账本类必须天然长寿；摘要类介于中间。核心原则不是“所有内容都保留”，而是“所有关键结论都可追溯，所有长文本都可淘汰”。  

### 具体实现建议

#### 存储分层

| 层级 | 内容 | 建议介质 | 建议保留 | 查询目标 |
|---|---|---|---|---|
| 热层 | 最近高频 debug 事件、详细解释、未压缩富文本 | 进程内 ring buffer + 本地顺序日志 | 6 小时或达到上限即淘汰 | 运行中调试 |
| 温层 | 关键业务事件 + 精简摘要 + 采样后的数据事件 | 本地 append-only 文件 + 可索引摘要库 | 30 天 | 常规复盘、UI 时间轴 |
| 冷层 | 买卖点、订单、仓位、风控拒绝、每日汇总 | 压缩归档文件或列式冷存储 | 365 天；更久按需 | 审计、长期对账 |

#### 报告分级与压缩策略

| 等级 | 包含内容 | 压缩策略 | 删除策略 |
|---|---|---|---|
| `key` | `ExecutionPlanned / OrderUpdated / PositionUpdated / 风控拒绝 / 关键买卖点` | 不压缩字段语义，只压缩物理存储 | 长期保留 |
| `summary` | `IntentGenerated` 摘要、`RiskEvaluated` 摘要、采样后的 `DataUpdated` | 结构化归约、字段裁剪、按时间采样 | 30~180 天 |
| `debug` | 详细解释全文、特征向量、原始中间状态 | 文本 blob 去重 + zstd 压缩 + 环形淘汰 | 6 小时~7 天 |
| `blob` | 长解释模板、重复文本、可选堆栈信息 | 按 `template_hash` 去重，引用计数 | 与 `debug` 同步淘汰 |

#### 时间演进策略

| 时间窗口 | `DataUpdated` | `Intent/Risk` 解释 | 订单/仓位 | 报告行为 |
|---|---|---|---|---|
| 0~24 小时 | 全量 | 全量 | 全量 | 允许全文查询 |
| 1~7 天 | 采样到 5 秒或 1 分钟，取决于轮询频率 | 仅保留摘要 + 引用 | 全量 | 自动去重与二次压缩 |
| 8~30 天 | 只保留分钟级或 bar 级摘要 | 只保留 `reason_code + summary` | 全量 | 删除长文本 blob |
| 31~365 天 | 只保留关键点与每日汇总 | 只保留风控拒绝摘要 | 全量 | 账本化归档 |

#### 存储估算

在**未指定交易对数量**、**默认 1 个活跃交易对**、**`DataUpdated` 约 1 秒一次**、**详细解释开启**的保守估算下，可以使用以下容量模型：

| 类别 | 假设量级 | 单条压缩后估算 | 单日估算 |
|---|---:|---:|---:|
| `DataUpdated` | 86,400 条/日 | 120 B | 9.89 MB |
| `IntentGenerated` | 10,000 条/日 | 300 B | 2.86 MB |
| `RiskEvaluated` | 10,000 条/日 | 350 B | 3.34 MB |
| `ExecutionPlanned` | 2,000 条/日 | 280 B | 0.53 MB |
| `OrderUpdated` | 8,000 条/日 | 220 B | 1.68 MB |
| `PositionUpdated` | 3,000 条/日 | 220 B | 0.63 MB |
| 详细解释 | 100,000 条/日 | 600 B | 57.22 MB |
| **合计** |  |  | **约 76.15 MB/日** |

据此，单个活跃策略在**30 天温层**大约需要 **2.23 GB**；如果只保留长期关键账本与关键点，**365 天冷层**大约需要 **1.19 GB**。如果同时保留 5 个活跃 run，这两个数字大致会增长到 **11.15 GB（30 天温层）** 与 **5.95 GB（365 天冷层）**。热层环形缓冲若按 100,000 条、平均 800 B、加 30% 索引开销估算，建议至少预留 **约 100 MB**。这些数字是设计估算，不是实际运行上限。  

#### 推荐的阈值策略

| 项目 | 建议初值 | 说明 |
|---|---|---|
| 热层 ring buffer 上限 | 100 MB | 到 80% 触发预警，到 95% 强制丢弃 debug 级 |
| 单条长解释压缩阈值 | 512 B | 超过即进入 blob 存储 |
| 文本去重 key | `module_key + reason_code + template_hash` | 减少重复解释 |
| `DataUpdated` 采样阈值 | 7 天后降到分钟级 | 若轮询更稀疏，则按 5×轮询间隔取样 |
| 强制降级条件 | 磁盘水位 > 85% | 立即停写 debug，只保留 key/summary |
| 归档批大小 | 1 天一个 segment | 便于删除、压缩与回放切片 |

### 验收测试用例

| 用例 | 预期结果 |
|---|---|
| 连续 24 小时启用详细解释 | 进程内存不线性增长，ring buffer 达上限后只淘汰 `debug` |
| 温层保留 30 天模拟 | 容量曲线接近估算，不出现无限增涨 |
| 对 30 天前数据执行压缩任务 | `DataUpdated` 成功采样，订单/仓位不丢失 |
| 删除过期 blob | 时间轴仍能展示关键摘要，不出现空白关键节点 |
| 磁盘水位压到 90% | 自动停止 debug 写入并产生 `StorageWatermarkExceeded` |
| 回放冷层数据 | 能还原关键买卖点、仓位变化与风控拒绝 |

### 失败模式与降级策略

如果归档任务失败，系统应暂停删除源数据，避免“压缩未成功但源数据已删”的双重损失。  
如果磁盘接近打满，第一步只关闭 debug 级写入；第二步把 `DataUpdated` 立刻降采样；第三步才暂停新的非关键 run。  
如果 blob 去重索引损坏，系统应退化到保留摘要，不允许因解释文本损坏影响订单与仓位账本。  

### 优先级与实施难度评估

这一维度优先级是 **P0**，实施难度 **中**。难点不在技术本身，而在“删什么、保什么、何时删”必须与你的复盘目标严格对齐。

## 能力发现与真实边界治理

### 目标

目标是让 `/api/capabilities` 真正成为**唯一真实边界**，并使前端显示、文档描述、compile 检查、runtime 启动决策全部依赖它，而不是各自维护一套想象中的支持矩阵。只要这个机制没闭环，产品就会不断出现“页面能点、文档写支持、运行时报不支持”的漂移。  

### 设计原则

能力发现应遵循三个原则。第一，**单一来源**，只能有一个权威输出。第二，**显式状态**，能力不能只分“支持/不支持”，至少要区分 `supported / declared_only / experimental / blocked`。第三，**可校验**，任何 build 产物都要带着生成时的 capability hash。  

### 具体实现建议

#### 建议的 capability API 契约

| 字段 | 必填 | 说明 |
|---|---|---|
| `capability_version` | 是 | 能力描述 schema 版本 |
| `generated_at` | 是 | 生成时间 |
| `schema_hash` | 是 | 能力描述内容哈希 |
| `engine_version` | 是 | runtime/compile 使用的引擎版本 |
| `chain_stages` | 是 | 当前主链路阶段列表 |
| `module_support` | 是 | 各模块支持状态与原因 |
| `exchange_support` | 否 | 已支持交易所；未指定时返回空数组 |
| `symbol_support` | 否 | 已支持交易对；未指定时返回空数组 |
| `execution_destinations` | 是 | `paper/live/sim` 等 |
| `extension_point_support` | 是 | 允许的插件扩展点 |
| `permission_model_version` | 是 | 权限模型版本 |
| `unsupported_reasons` | 否 | 面向前端与文档的灰显原因 |
| `signature` | 否 | 若采用签名快照，可加签名 |

#### 一致性闭环

建议把能力边界闭环做成四个同步校验点：

| 环节 | 必须动作 |
|---|---|
| 前端 | 组件显隐、按钮可用性、表单校验只读 `GET /api/capabilities` |
| 文档 | 支持矩阵由 capability JSON 生成，不允许手工维护 |
| compile | 编译产物内写入 `expected_capability_hash` |
| runtime | 启动时比较 `expected_capability_hash` 与当前 `schema_hash`；不一致则拒绝启动或只读模式启动 |

建议再补一个系统事件：`CapabilitySnapshotTaken`，在每个 run 启动时写入完整 `schema_hash + simplified capability digest`。这样回放时才知道当时的能力边界究竟是什么。  

### 验收测试用例

| 用例 | 预期结果 |
|---|---|
| 前端尝试创建未支持模块 | UI 灰显并展示 `unsupported_reasons` |
| 文档生成任务与 runtime 返回不一致 | CI 失败，不允许合并 |
| compile 产物能力哈希与启动时不一致 | runtime 拒绝启动该 run 或强制只读 |
| 能力 API 暂时不可用 | 旧页面只能展示上次签名快照，不允许新建 run |
| 已声明但未支持能力 | 必须显示为 `declared_only`，不能伪装成支持 |

### 失败模式与降级策略

如果 `/api/capabilities` 短暂不可用，前端可以读取最近一次**已签名**快照用于显示，但必须进入“只读边界模式”，不允许用户新建运行。  
如果 capability hash 与 compile 产物不一致，运行链应 fail-closed，而不是“先跑再说”。  
如果文档生成失败，则保留上一次成功生成的文档，但必须明确标注版本和 hash，避免用户误以为它代表当前能力。  

### 优先级与实施难度评估

这一维度优先级是 **P0**，实施难度 **中**。它比权限治理稍简单，但对产品诚实度的影响同样是基础设施级的。

## 安全边界与权限治理

### 目标

这一维度的目标，是确保任何插件、AI 产物、前端操作和模块扩展都**不能绕过主链路、不能越权联网、不能跨层下单、不能偷偷改参数并立即生效**。NIST 对 least privilege 的定义要求只授予执行职责所需的最小授权和资源；AI RMF 则强调组织应通过可操作的方法管理 AI 风险，以促进可信和负责任的使用。citeturn11view6turn13view1

### 设计原则

这里建议把权限治理固定为四条硬规则。第一，**插件默认无网络权限**。第二，**只有执行层持有下单能力句柄**。第三，**AI 只能提交提案，不能直接激活**。第四，**所有越权尝试都要留下审计痕迹**。  

### 具体实现建议

#### 插件白名单与权限声明

| 清单字段 | 必填 | 说明 |
|---|---|---|
| `plugin_id` | 是 | 插件唯一标识 |
| `plugin_version` | 是 | 插件版本 |
| `plugin_type` | 是 | `data/intent/agent/risk/execution/ui/system` |
| `extension_points[]` | 是 | 允许挂载的扩展点 |
| `requested_permissions[]` | 是 | 如 `network`, `filesystem_read`, `filesystem_write` |
| `network_allowlist[]` | 否 | 仅 data/execution 可请求；默认空 |
| `fs_allowlist[]` | 否 | 文件访问白名单 |
| `binary_hash` | 是 | 二进制哈希 |
| `signature` | 是 | 审批签名；未指定签名方案可先用内部签发 |
| `review_state` | 是 | `pending/approved/revoked` |
| `approved_by` | 否 | 审批人 |
| `approved_at` | 否 | 审批时间 |
| `expires_at` | 否 | 权限到期时间 |

推荐的默认权限矩阵如下：

| 模块类型 | 默认网络权限 | 默认文件写权限 | 是否可拿到执行适配器 |
|---|---:|---:|---:|
| data | 否；按白名单申请 | 否 | 否 |
| intent | 否 | 否 | 否 |
| agent | 否 | 否 | 否 |
| risk | 否 | 否 | 否 |
| execution | 否；按白名单申请 | 否 | 是 |
| ui/system | 否 | 否 | 否 |

#### 禁止跨层下单

建议通过接口边界把“谁能下单”写死，而不是靠约定。最简单的规则是：

- `Intent` 只能产出意图，不得接触交易所配置。
- `Agent` 只能合成权重，不得接触执行适配器。
- `Risk` 只能批准或拒绝，不得直接构造交易所请求。
- `Execution` 才能把 `RiskDecision` 转成 `ExecutionPlan`，并调用外部适配器。
- 任何非 execution 模块尝试访问下单接口，都应产生 `SecurityViolationDetected` 并硬拒绝。

#### AI 输出审计

AI 介入建议全部走“proposal ledger”：

| 字段 | 必填 | 说明 |
|---|---|---|
| `proposal_id` | 是 | AI 提案唯一 ID |
| `source_model` | 是 | 模型标识 |
| `prompt_hash` | 是 | 提示哈希 |
| `output_hash` | 是 | 输出哈希 |
| `scope` | 是 | `parameter/module/report-only` |
| `target_run_id` | 否 | 目标 run |
| `diff_summary` | 是 | 人能读懂的差异摘要 |
| `risk_impact_guess` | 否 | AI 自评影响 |
| `review_state` | 是 | `pending/approved/rejected` |
| `reviewer` | 否 | 审批人 |
| `reviewed_at` | 否 | 审批时间 |
| `applied_parameter_version` | 否 | 生效后参数版本 |

第二阶段建议只允许两类 AI 输出自动进入系统：**只读报告**与**参数候选**。任何模块级变更都必须人工审批；任何涉及 execution 与 risk 的双重变更，建议要求双人审批。  

### 验收测试用例

| 用例 | 预期结果 |
|---|---|
| intent 插件申请 network 权限 | 拒载并写 `PluginLoadRejected` |
| risk 插件尝试直接构造交易请求 | 运行时硬拒绝并写 `SecurityViolationDetected` |
| AI 提交参数方案 | 进入 `pending`，不直接激活 |
| AI 尝试修改 execution 配置 | 要求人工审批，且无审批不得生效 |
| 篡改插件二进制 | `binary_hash` 校验失败，拒绝加载 |
| 权限服务不可用 | 不允许新插件、新提案进入生效态 |

### 失败模式与降级策略

如果签名校验服务失败，新插件和新提案都进入“冻结审批”状态，已有已批准插件可继续运行。  
如果 AI 审批账本不可写，系统仍可运行，但必须关闭所有 AI 自动建议入口，防止出现“变更已产生但不可追溯”。  
如果发现跨层下单漏洞，应该首先让 execution adapter 只接受来自 execution engine 的受限内部对象，而不是试图在上层逐个补洞。  

### 优先级与实施难度评估

这一维度优先级是 **P0**，实施难度 **中高**。难点不在写 manifest，而在把“权限原则”真正落到运行时对象图与审批流程里。

## 测试体系与回放验收

### 目标

这一维度的目标，是把第二阶段从“开发者觉得没问题”推进到“系统可以被证明在关键路径上没越界、没丢事件、没破坏回放”。契约测试的核心价值在于：它验证通信双方对消息的共享理解，而不是依赖昂贵且脆弱的大集成测试；混沌测试则强调围绕**稳态指标**做实验，通过真实扰动去尝试证伪系统的稳定性。citeturn11view2turn11view4

### 设计原则

测试体系建议采用六层：**单元、集成、契约、端到端、混沌、回放验收**。这六层不互相替代，而是自下而上减少不确定性。尤其对 QuantPilot 这种链路系统，端到端测试不能替代回放验收，因为“页面能显示”并不等于“账本可再现”。  

### 具体实现建议

#### 测试分层

| 层级 | 主要对象 | 第二阶段必须覆盖的重点 |
|---|---|---|
| 单元 | 事件 schema、权限校验、压缩逻辑、状态机 | `sequence_no`、event envelope、订单状态单调性 |
| 集成 | 数据源、风险链、执行适配器、存储分层 | 数据延迟、风控拒绝、归档压缩、磁盘水位降级 |
| 契约 | `capability API`、事件流接口、AI proposal API | schema 兼容、字段存在、状态枚举不漂移 |
| 端到端 | 前后端联动 | 时间轴、能力灰显、报告视图、告警展示 |
| 混沌 | 数据源波动、磁盘压力、重复事件、时钟偏差 | 稳态指标是否被破坏、是否触发正确降级 |
| 回放验收 | run 全链路 | 相同输入重放后关键账本一致 |

#### 关键测试用例

| 类别 | 用例 | 通过标准 |
|---|---|---|
| 单元 | `DataUpdated` 缺少 `price_basis` | 编译或测试失败 |
| 单元 | `OrderUpdated` 状态从 `filled` 回退到 `submitted` | 拒绝该状态迁移 |
| 集成 | 数据源延迟持续高于阈值 | 运行链停止产生 `ExecutionPlanned`，但继续保留数据与告警 |
| 集成 | 磁盘水位达到 90% | debug 事件被关停，关键账本仍可写入 |
| 契约 | 前端基于旧 schema 读取新 capability | 兼容字段可正常读，不兼容字段明确报错 |
| 端到端 | 一次完整 paper run | 时间轴能看到 Data→Intent→Risk→Execution→Order→Position 的关键节点 |
| 混沌 | 注入重复 `DataUpdated` | 不应造成重复订单，必须有幂等处理 |
| 混沌 | 注入 500ms 时钟偏差 | 触发 `clock_skew` 告警，不得静默污染回放 |
| 回放 | 同一输入切片重放 | 最终持仓、订单序列、关键风控拒绝一致 |
| 回放 | 能力哈希不同的 run 重放 | 必须明确标记“不可直接对比” |

#### 回放验收标准

回放验收建议分为两级：

| 级别 | 标准 |
|---|---|
| 强一致 | 同一 `capability_hash + strategy_version + parameter_version + input_event_slice` 下，最终持仓、订单状态序列、风控决策序列完全一致 |
| 业务一致 | 若底层时间戳或内部 ID 有细微差别，至少要求最终持仓、关键买卖点、PNL 结果在允许误差内一致 |

第二阶段建议至少把 **paper/backtest 模式**做成强一致。live 模式如果未来出现外部成交差异，也应退回到业务一致，而不是放弃回放能力。  

### 验收测试用例

这一维度的总验收可以压缩成五条红线：  
其一，所有关键事件都有 schema 契约测试。  
其二，所有权限路径都有越权失败测试。  
其三，至少一条完整 paper run 具备端到端可视化和回放一致性。  
其四，至少三类混沌扰动能触发预期降级。  
其五，能力 hash 漂移会导致构建或启动失败，而不是默默运行。  

### 失败模式与降级策略

如果混沌测试平台自身不稳定，不应把结果直接算作产品失败，必须保留 seed、扰动脚本和事件切片，允许重复实验。  
如果回放失败，产物不能作为“通过”，必须把失配 event slice 与 capability hash 一起归档，供后续定位。  
如果端到端 UI 测试过于脆弱，应优先把关键链路验证前移到契约测试和回放验收，而不是一味堆浏览器脚本。  

### 优先级与实施难度评估

这一维度优先级是 **P0**，实施难度 **高**。原因不是测试工具难，而是它要求你先把契约、生命周期、权限和能力边界全部定义清楚。

## 监控、告警与风险清单

### 目标

这一维度的目标，是围绕系统稳态建立最小可运营闭环：**知道数据是不是新鲜、事件是不是完整、风控是不是异常保守、执行是不是在失败、压缩是不是失控、能力边界是不是漂移**。OpenTelemetry 的思路是统一日志、追踪、指标的上下文；Prometheus 的思路是让规则评估与 Alertmanager 的抑制、聚合、通知分离。这对 QuantPilot 很合适，因为你需要的不只是监控 CPU，而是监控**证据链本身**。citeturn10view0turn11view3

### 设计原则

监控设计建议抓住两个重点。第一，**优先监控可破坏信任的指标**，而不是先做漂亮 Dashboard。第二，**避免高基数**，只在 `run_id` 级别或聚合视角暴露关键链路指标，详细定位靠事件流和 trace，不靠无限打 label。  

### 具体实现建议

#### 核心指标与默认告警建议

| 指标 | 含义 | 建议阈值 | 告警级别 |
|---|---|---|---|
| `data_ping_success_ratio` | 数据源 ping 成功率 | 5 分钟 < 99% | P1 |
| `data_freshness_p95_ms` | 数据最新鲜度 | > 3 × `poll_interval_ms` | P1 |
| `data_gap_total` | 数据缺口数 | 任意增长 | P1 |
| `intent_to_risk_latency_p95_ms` | 意图到风控耗时 | 未指定；建议 < 轮询间隔的一半 | P2 |
| `risk_reject_rate_5m` | 风控拒单率 | > 90% 且样本数 > 50 | P2 |
| `execution_submit_failure_rate_15m` | 执行提交失败率 | > 2% | P1 |
| `order_ack_latency_p95_ms` | 订单确认延迟 | 未指定；建议按 paper/live 分别配置 | P2 |
| `event_orphan_total` | 父链丢失事件数 | 任意增长 | P1 |
| `event_sequence_gap_total` | 序号断裂数 | 任意增长 | P1 |
| `report_ring_usage_ratio` | 热层 ring 占用 | > 80% 预警，> 95% 强降级 | P2 |
| `storage_watermark_ratio` | 磁盘水位 | > 85% 预警，> 90% 强降级 | P1 |
| `capability_mismatch_total` | 能力 hash 不一致 | 任意增长 | P1 |
| `ai_proposal_pending_age_max_sec` | AI 待审最长年龄 | > 24 小时 | P3 |
| `replay_divergence_total` | 回放失配次数 | 任意增长 | P1 |

#### 告警策略

建议把告警分成三类：

| 类别 | 典型事件 | 处理方式 |
|---|---|---|
| 立即阻断型 | `capability_mismatch_total`, `event_orphan_total`, `data_gap_total`, `storage_watermark_ratio>90%` | 触发 run 级阻断或强降级 |
| 运行退化型 | `risk_reject_rate_5m` 异常升高、`report_ring_usage_ratio` 偏高 | 发告警并进入摘要模式 |
| 运营观察型 | AI 待审积压、长期回放失败率上升 | 周报/月报，不立刻打断运行 |

#### 推荐的降级策略矩阵

| 触发条件 | 降级动作 |
|---|---|
| 数据新鲜度超过阈值 | 暂停生成 `ExecutionPlanned`，继续记录 `DataUpdated` 与健康事件 |
| 事件父链断裂 | 标记该 run 为“回放不可信”，继续运行但禁止生成审计报告 |
| 热层内存过高 | 只关停 debug 与长解释，不关停账本事件 |
| 磁盘水位过高 | 先关 debug，再采样 `DataUpdated`，最后暂停新 run |
| capability hash 漂移 | 不允许新 run 启动，已有 run 视风险进入只读监控态 |

### 验收测试用例

| 用例 | 预期结果 |
|---|---|
| 模拟数据源停 2 分钟 | `data_freshness_p95_ms` 告警触发，执行链停发计划 |
| 注入孤儿事件 | `event_orphan_total` 增长，同时 run 被标记为审计不可信 |
| 注入大量重复解释 | `report_ring_usage_ratio` 触发预警，debug 自动削减 |
| 伪造 capability hash | 启动受阻，告警产生 |
| 回放一致性测试故意失败 | `replay_divergence_total` 增长并产出失配工单 |

### 失败模式与降级策略

如果指标采集链自身失败，交易主链不应被指标系统反向拖死。建议保留本地最小 fallback：把关键计数器周期性落到本地快照文件，待监控恢复后再回补。  
如果告警过多导致疲劳，应优先调整阈值与聚合策略，而不是降低事件精度。因为事件证据链的完整性比告警面板“安静”更重要。  

### 非功能性风险清单与缓解措施

| 风险 | 表现 | 影响 | 缓解措施 |
|---|---|---|---|
| 能力边界漂移 | UI、文档、runtime 各说各话 | 用户误操作、测试失真 | capability hash + CI 一致性门禁 |
| 事件父链断裂 | 时间轴缺口、回放失败 | 审计不可信 | `sequence_no`、`parent_event_id`、`EventGapDetected` |
| 长解释膨胀 | 内存持续上涨 | 进程不稳定 | ring buffer、blob 去重、列级 TTL |
| 磁盘打满 | 写入失败 | 账本损坏风险 | 多级降级、强制归档、磁盘水位告警 |
| 插件越权联网 | 隐蔽外联、数据泄露 | 安全边界失守 | 默认无网络、白名单、签名校验 |
| AI 黑箱变更 | 参数或模块悄悄生效 | 结果不可追责 | proposal ledger + 审批门禁 |
| 回放非确定性 | 同输入不同结果 | 复盘失效 | capability/strategy/parameter/input slice 联合锁定 |
| 时钟漂移 | 事件顺序错乱 | freshness 与回放污染 | authoritative clock 校验与 skew 告警 |
| 告警疲劳 | 团队忽略真实问题 | 运营失灵 | 分级告警、抑制、聚合 |
| schema 演进破坏兼容 | 前后端读取失败 | 运行或展示错误 | `payload_version`、契约测试、兼容策略 |

### 优先级与实施难度评估

这一维度优先级是 **P1**，实施难度 **中**。它依赖前面几个 P0 维度先稳定，但一旦开始运营，就会迅速变成刚需。

## 实施里程碑与资源估算

### 迭代建议

| 迭代 | 建议周期 | 主要产出 | 验收标准 |
|---|---:|---|---|
| 边界与契约迭代 | 2~3 周 | 公共事件 envelope v1、六个关键事件 schema、`/api/capabilities` v1、能力 hash 注入、插件 manifest v1、AI proposal ledger v1 | 六个锚点事件能完整落盘；compile/runtime/front-end 使用同一 capability hash；未授权插件和 AI 变更全部被阻断 |
| 生命周期与验收迭代 | 2~3 周 | 热/温/冷存储分层、报告压缩任务、报告 TTL、时间轴三档视图、契约测试、回放验收 harness | 30 天容量模拟通过；回放在 paper 模式下强一致；磁盘/内存压力可触发正确降级 |
| 运营与硬化迭代 | 2~3 周 | 指标体系、告警规则、混沌实验、容量月报、runbook、签名快照与恢复流程 | 至少三类混沌扰动可重复触发预期告警；关键告警能被正确路由；回放失败能自动生成差异证据 |

如果团队人力有限，第一迭代绝不能被压缩得只剩“能显示事件”。它必须同时交付**事件契约、能力边界、权限底线**三件事；否则后面做的生命周期和告警只会建立在不可信的基础上。

### 最终建议

如果第二阶段只追求一件事，我建议追求**“可信证据链”**，而不是“更多解释文本”或“更复杂面板”。可信证据链意味着：能力边界诚实、每一步都能被事件解释、事件能回放、报告能收缩、越权能被拒绝、失败能被告警、压缩不会毁掉账本。只要这一层稳了，后续不管是策略合并、AI 辅助、还是更复杂的回测与执行，都会是在可控地基上加层；反过来，如果这一层不稳，功能越多，系统只会越像黑箱。
