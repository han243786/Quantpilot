# 第二阶段开发目标文档

## 执行摘要

本文件将第二阶段定位为：在不引入高风险能力的前提下，交付一个**可解释、可调参、可回放、可受限合并**的交易决策系统。范围覆盖数据模块、意图模块、代理模块、风控模块、执行模块、结果层，以及系统级的参数流式调整、受限策略合并、AI 调参与辅助、解释系统与报告生命周期、统一时间轴、策略版本系统、异常可观测。未指定的实现细节——包括支持的交易所、并发量、语言栈、部署形态、数据库选型与监管法域——均视为**无特定约束**，本文件按抽象接口与可验证目标定义。  

本文件的范围收缩是有意为之。官方交易所文档表明，实时行情、心跳、订阅确认、认证方式、速率限制、测试环境、订单状态上报方式存在显著差异；同时，事件溯源与读写分离虽然能增强可回放性与审计能力，但也会显著提高复杂度与一致性成本。因此，第二阶段应优先追求**链路稳定、接口抽象、审计完备、解释清晰**，而不是追求“任意组合、完全热插拔、AI 直接接管”的上限能力。citeturn3view0turn3view1turn5view0turn5view1turn3view9turn3view2turn10view0turn9view0

## 项目目标与范围

第二阶段的总体目标，是在既有主链路 **Data → Intent → Agent → Risk → Execution → Result** 不被破坏的前提下，补齐“可运营、可观察、可解释、可复盘”的产品能力，使系统从“能跑策略”进入“可被用户可信地使用和调整”的阶段。建议在正式文档中补充两类图表：其一是 **mermaid flowchart**，展示主链路及旁路能力（版本、日志、观测、回测）；其二是 **context diagram**，展示数据源、模拟盘、真实交易所、存储、告警、版本库之间的边界。事件溯源应仅引入**支持回放所必须的最小事件模型**，避免在第二阶段过早扩张为全域架构重构。citeturn3view2turn10view0

| 范围项 | 内容 |
|---|---|
| 项目目标 | 建立一个可解释、可调参、可受限合并、可审计、可回放的交易决策系统 |
| 范围内 | 数据模块、意图模块、代理模块、风控模块、执行模块、结果层；参数流式调整；受限策略合并；AI 调参与辅助；解释系统与报告生命周期；统一时间轴；策略版本系统；异常可观测 |
| 明确排除项 | 真·热插拔；任意策略组合 + 任意模块组合；AI 直接插入模块；实时高频调参 |
| 范围边界 | 不承诺特定交易所数量；不承诺特定并发级别；不承诺特定语言栈；不承诺特定数据库或消息中间件；不在本阶段定义具体监管法域条款 |
| 范围原则 | 主链路不可绕过；风控必须是统一闸门；AI 只能只读/建议/受限写入；事件与参数变更必须可追踪 |
| 需后续补充来源 | 目标交易所 API 手册、测试网能力差异、目标法域合规要求、组织内部安全基线、压测环境与 SLO 基线、日志保留政策 |

将高风险目标移出第二阶段是合理的：交易所连接与订单语义天然异构，连接保活、订阅、身份认证、签名方式、速率限制、订单状态与测试环境均不统一；而 AI 风险治理官方框架明确强调人机角色、持续监测、文档化、停用与变更管理机制。这意味着第二阶段更适合建设**受控扩展面**，而不是追求“开放式运行时组合能力”。citeturn3view0turn3view1turn5view0turn5view1turn3view9turn9view0turn3view4

## 模块化功能清单

交易所官方文档表明，行情获取通常同时包含 REST 快照、WebSocket 行情流、心跳/保活、symbol 元数据、速率限制和测试环境；订单侧则涉及不同的认证方式、订单状态、成交事件与失败语义。因此，模块设计必须以**统一领域模型 + 适配器层**为原则，而不是把具体交易所接口直接暴露给上层。回测视图和运行态视图应复用同一套标准化事件与行情抽象，以保证“看到的内容”和“真实执行链路”一致。citeturn7view0turn7view1turn7view2turn3view1turn5view0turn3view7turn8view0

| 模块 | 功能描述 | 关键子功能列表 | 验收标准 | 优先级 | 估计实现难度 |
|---|---|---|---|---|---|
| 数据模块 | 负责连通性检查、交易对合法性校验、实时价格展示、采集延迟与频率监控，以及回测行情可视化 | 运行前 Ping/订阅前检查；交易对与交易状态校验；实时价格与时间戳显示；采集延迟统计；采集频率可调；回测 K 线与买卖点/仓位变更/风控干预点标注 | 启动前健康检查报告至少包含：可达性、symbol 合法性、订阅确认、首包延迟、数据时间戳可解析；运行页持续显示当前价、最近更新时间、采集延迟、当前频率；频率调整在不重启主进程前提下于下一个安全采集周期生效；回测图支持同屏显示 K 线、买卖点、仓位变化点、风控拒绝点并可导出 | 高 | 中 |
| 意图模块 | 负责把市场状态映射成结构化的买/卖意图，并附带最小解释 | 参数化意图定义；多意图并存；声明式模块开发；原生扩展接口；意图解释输出；依赖数据追踪 | 每个意图实例至少包含：方向、强度、置信度、原因摘要、时间戳、来源依赖；至少支持一种声明式定义方式与一种原生扩展方式；无论来源为何，意图输出结构必须统一；界面可查看单个意图最近 N 次命中及其原因 | 高 | 中 |
| 代理模块 | 负责融合多个意图，形成候选订单或候选仓位调整方案，并抑制单一意图过度暴露 | 权重分配；冲突处理；单意图暴露上限；候选订单形成；归因解释 | 至少提供三类基础合并策略：加权合并、置信度优先、冲突抑制；每个候选订单都能追溯各意图贡献权重与抑制原因；支持单意图暴露上限；候选结果可被风控模块完整消费 | 高 | 中 |
| 风控模块 | 负责计算全局风险，对候选订单做批准、减仓、延迟或拒绝决策 | 仓位风险；名义价值限制；回撤控制；频率控制；连续亏损控制；全局风险快照；风险解释 | 对每个候选订单都输出明确决策（Approve/Reduce/Delay/Reject）、reason_code、关键风险指标快照；至少支持仓位、名义敞口、回撤、下单频率、连续亏损五类规则；可查询当前全局风险摘要与最近风险决策记录 | 高 | 高 |
| 执行模块 | 负责把已通过风控的执行计划映射为模拟盘动作或交易所调用，并回收执行结果 | 执行计划标准化；模拟盘适配器；真实/测试网适配器；预校验；重试与回退；状态追踪 | MVP 至少支持模拟盘；第二阶段其余功能至少支持一个真实交易所或测试网适配器；每次执行都记录请求摘要、返回摘要、重试次数、最终状态与耗时；发送前进行 symbol、订单类型、数量/价格边界的本地预校验 | 高 | 中 |
| 结果层 | 负责沉淀标准化的订单状态、成交、持仓、盈亏与历史查询结果 | 订单状态机；成交与拒单归档；持仓面板；已实现/未实现盈亏；交易历史查询与导出 | 能按 order_id 或策略运行 ID 追溯从候选订单到成交/拒绝的完整路径；成交后在一个结果刷新周期内反映到持仓与盈亏；支持按时间范围、策略、账户维度查询历史结果；具备导出能力 | 高 | 低至中 |

订单与成交结果不应直接复制单一交易所的语义，而应采用“最小公共状态集 + 适配器映射”的策略。原因是官方标准明确区分了收到订单、订单已打开、已成交、修改、取消、拒绝等不同事件与状态优先级；若不做标准化映射，结果层、时间轴、回放与审计都会在多适配器场景下失真。citeturn3view7turn8view0turn5view0

## 系统级能力

系统级能力不是对模块的简单叠加，而是对“整个决策流水线”的可配置性、可解释性和可治理性补强。这里要刻意避免把第二阶段做成“任意图结构编排平台”。一方面，事件溯源与 CQRS 确实适合用于回放、审计与读写分离，但官方文档也明确指出它们会引入额外复杂度、最终一致性与快照管理成本。另一方面，AI 风险管理框架强调人机角色分界、持续监测、透明文档、停用机制与变更管理。第三，统一可观测体系应同时覆盖 logs、metrics 与 traces，而不是只做日志堆砌。citeturn3view2turn10view0turn9view0turn3view4turn3view8

建议在产品设计稿中补充三类图表：**mermaid sequence diagram** 展示一次“数据到成交”的链路；**state diagram** 展示订单状态机与风险决策状态机；**timeline/gantt** 展示版本、参数变更、订单与异常在统一时间轴中的关系。citeturn3view7turn10view0turn3view8

| 系统级能力 | 功能描述 | 验收标准 | 实现注意事项 |
|---|---|---|---|
| 参数流式调整 | 在不重启主链路的前提下，允许对白名单参数进行在线调整，并记录差异、操作者、版本与回滚信息 | 仅对白名单参数开放在线修改；参数变更在下一个安全评估周期生效；每次变更都生成 diff、版本号、操作者、时间戳；支持一键回滚到上一稳定版本 | 明确“安全点”概念，避免运行中途修改导致状态漂移；参数更新应采用原子替换而非局部覆盖；应与版本系统和时间轴打通 |
| 策略合并受限版 | 支持多个策略并行输出意图，但收敛到统一代理与统一风控，不支持任意模块图组合 | 至少支持两个策略组并行运行；每个策略组有独立权重和归因；最终只允许一个统一 Agent、一个统一 Risk、一个统一 Execution 出口；全局风险只计算一次 | 拓扑应固定为“多意图源 → 单代理 → 单风控 → 单执行”；禁止跨策略绕过统一风控；需要处理资金占用与暴露重复计算 |
| AI 调参与辅助 | AI 仅承担只读分析、建议生成、受限写入三种角色，不允许直接下单或直接插入模块 | 至少提供三种模式：只读分析、建议模式、审批后对白名单参数受限写入；每次 AI 建议都保留输入上下文、输出建议、审批结果与最终生效版本；AI 不得直接发送订单或改变主链路结构 | 必须保留人工审批或策略门控；建议在生效前经过 dry-run 或回测；不允许 AI 直接写入代码或插入执行逻辑；要为 AI 提供严格的提示边界与可见数据范围 |
| 解释系统与报告生命周期管理 | 为意图、代理、风控、执行与结果提供可读解释，并控制高频日志/报告的体积 | 至少支持事件分级、TTL、压缩阈值、手动导出；长期保留最关键的买卖点、仓位变化、风控拒绝、异常事件、参数版本；详细解释在生命周期结束后自动压缩或清理 | 不能“什么都永久保留”；需要区分审计保留与调试保留；压缩前支持导出；应支持敏感字段脱敏与按角色查看 |
| 时间轴统一视图 | 以单一时间轴展示一笔交易或一次运行中的关键事件，从数据到结果可一键回看 | 支持按 order_id、strategy_run_id、time range 查询；支持从时间轴点击事件查看上下游关系；至少可重建“某次买/卖为何发生、为何被批准或拒绝”的完整路径 | 时间轴应基于标准化事件而不是各模块私有日志；建议在读模型中投影展示，不直接查询原始事件存储；需要与 tracing 上下文关联 |
| 策略版本系统 | 对配置、参数、模块组合、AI 建议、生效版本做统一版本化管理 | 每次运行都绑定唯一版本；支持版本 diff、标签、回滚、与回测/实盘记录关联；能查询“某次结果采用了哪一版策略与参数” | 版本应覆盖配置与依赖，不只覆盖参数；应避免“运行态配置”和“仓库配置”脱节；推荐把版本系统作为审计基石 |
| 异常可观测 | 统一采集日志、指标、链路追踪与告警，覆盖数据延迟、掉线、拒单、风险尖峰、适配器错误 | 至少输出 logs/metrics/traces 三类观测信号；具备数据延迟、连接中断、拒单率、风控拒绝率、执行失败率等告警；每条关键事件可关联 trace_id 或 correlation_id | 需要控制采样与噪音；应把业务事件与安全事件区分处理；建议使用可插拔的 collector/pipeline，避免把观测逻辑耦合进业务代码 |

AI 辅助能力必须遵循“治理先于自动化”的原则。官方 AI 风险管理框架明确提出，应清晰定义人类角色与职责、持续监测部署中的行为、保留文档以支撑透明度与问责，并为停用、覆写、恢复和变更管理提供机制。因此，第二阶段的正确做法不是让 AI 直接成为模块，而是把 AI 放入**分析—建议—审批—受限生效**的受控闭环。citeturn3view4turn9view0

统一时间轴和回放能力应采用“事件 + 快照”的折中方案。官方架构文档指出，事件溯源和 CQRS 能支持历史重建、只读视图再生成和查询优化，但也会带来最终一致性、快照生成成本与更高系统复杂度；因此，第二阶段建议将其限定为**回放、审计和界面投影所必需的最小实现**。citeturn3view2turn10view0

## 非功能性要求

第二阶段的非功能性要求应围绕五个关键词展开：**安全、审计、性能、可用性、可回放性**。官方安全与 API 指南显示，第三方 API 集成中的身份认证、资源消耗、接口清单管理、外部 API 安全消费、日志保护和密钥生命周期都属于高频风险点；交易所文档则进一步表明，实时系统必须显式处理 heartbeat、速率限制、回退与认证差异。citeturn5view2turn3view5turn3view6turn5view1turn5view0turn3view0turn3view1

| 类别 | 要求 | 说明 |
|---|---|---|
| 安全 | 所有交易所密钥、签名密钥、JWT 私钥统一纳入集中式 secrets 管理；禁止硬编码；按最小权限拆分读/写权限；支持轮换、吊销、过期管理 | 需要建立适配器级 credential policy；日志与报表中默认脱敏；权限模型至少区分只读、调参、审批、执行 |
| 合规与审计 | 所有关键动作必须可审计：参数变更、版本切换、AI 建议、风控决策、执行请求、结果回写、人工审批 | 需形成可导出审计包；日志、版本记录与时间轴可互相定位；日志保留时长需依据未来法域与组织政策补充 |
| 性能 | 运行态行情获取优先使用 WebSocket，REST 主要用于快照、补数和校验；关键路径需有延迟指标和上报 | 在未指定并发目标前，本文件不定义吞吐硬指标，但要求至少输出 p50/p95/p99 级别指标，并在立项后确定压测环境 |
| 可用性 | 启动前必须经过健康检查；运行中支持掉线重连、订阅恢复、退化运行与人工暂停；模拟盘与测试网可用于联调 | UI 必须始终可见“当前是否健康”；出现数据中断时应主动告警而不是静默失败 |
| 可回放性 | 系统必须能基于事件和版本信息重建一次运行或一笔交易的关键路径 | 回放至少覆盖：数据到达、意图生成、代理合并、风控决策、执行结果、仓位变化；回放结果需与版本系统绑定 |
| 存储压缩策略 | 采用分层保留：短期保留详细解释，长期保留关键事件和快照；对高频解释进行压缩和摘要化 | 长期保留项建议至少包括买卖点、仓位变化、风控拒绝、异常事件、参数版本、AI 审批记录；清理前支持导出 |

安全与可审计要求并非附加项，而是第二阶段成立的前提。OWASP 指南明确要求应用日志具有一致性、可监控性、保护措施与生命周期管理，同时强调日志不能保留不足，也不能超出保留期；密钥管理则要求集中化、标准化以及覆盖创建、轮换、吊销、过期的完整生命周期。citeturn3view5turn6view0turn6view1turn6view2turn3view6turn6view3

性能与连接策略也应遵循交易所官方文档。部分官方文档明确建议尽量使用 WebSocket 获取实时数据以降低请求压力，同时要求遵守速率限制、在收到 429 后退避，并处理心跳、订阅时限与连接有效期等约束。这意味着第二阶段必须把“连接健康、回退策略、重连恢复、速率监测”视为系统性能力，而不是零散功能。citeturn5view1turn3view0turn7view2turn5view0turn3view1

需要后续补充官方来源的非功能细则包括：目标法域下的数据保留期限、加密标准、审计要求；选定交易所的正式 SLA/SLO；部署环境的可用区与灾备要求；组织内部对审批与权限分离的制度约束。

## 开发里程碑建议

里程碑设计应遵循“先闭环，后增强”的原则。官方架构文档已经说明，事件溯源、CQRS 与读模型投影在带来回放与审计能力的同时，也明显提高了系统复杂度；因此，开发顺序应先确保主链路闭环和标准事件模型，再引入时间轴、版本、观测与压缩治理，而不是一上来建设复杂编排层。建议在项目计划中补充 **mermaid timeline** 或 **gantt** 图，直观展示里程碑与依赖关系。citeturn3view2turn10view0

| 里程碑 | 交付物 | 验收条件 |
|---|---|---|
| MVP | 数据模块基础版；单策略意图基础版；单一代理策略；核心风控闸门；模拟盘执行；结果层基础版；最小时间轴；最小版本记录 | 用户可完成“运行前检查 → 运行中看实时价/延迟 → 生成意图 → 风控审批/拒绝 → 模拟执行 → 查看订单/持仓/盈亏 → 回看关键事件”的完整闭环；所有关键动作可追溯 |
| 第二阶段其余 | 多意图代理策略；受限策略合并；参数流式调整；回测 K 线与买卖点标注；报告生命周期管理；统一观测；AI 只读/建议/审批后受限写入；至少一个真实交易所或测试网适配器；策略版本系统 | 可同时运行多个策略组并统一收敛；可在线调整白名单参数并回滚；可查看统一时间轴；可导出审计/回放所需信息；AI 建议不越权；真实或测试网适配器通过联调与基本回归测试 |
| 后续可选 | 多交易所扩展；更细粒度风险归因；高级执行策略；多账户/组合层风控； richer AI 协助；更完整的事件快照体系 | 不破坏第二阶段主链路；新增能力均通过版本系统、风险闸门与时间轴接入；不回退安全性、审计性与可解释性 |

MVP 的关键不是“少功能”，而是“第一条完整可信链路”。只要能让用户完整经历一次可解释的策略运行与回看流程，后续增强就可以围绕同一事件模型、版本模型和观测框架迭代，而不必重做底层抽象。citeturn10view0turn3view8turn3view5

## 风险与缓解措施

保留在第二阶段中的中等难度项，主要风险并不来自单模块开发，而来自**系统集成**：交易所适配差异、读写一致性、版本与运行态同步、日志体积、回放成本、AI 建议治理，以及多策略共享资本时的风险叠加。官方资料已经说明：API 认证与资源消耗错误会直接成为安全风险；第三方 API 的不安全消费本身就是高风险类别；读写分离与事件溯源会引入最终一致性和快照成本；日志既要可监控又要可清理；AI 系统则要求持续监测、停用、变更与人工职责明确。citeturn5view2turn10view0turn3view2turn3view5turn6view0turn9view0turn3view4

| 风险 | 影响 | 缓解措施 | 监测信号 |
|---|---|---|---|
| 参数流式调整导致状态漂移 | 同一运行中出现“配置已变、状态未变”或结果难以解释 | 只允许在安全点生效；每次变更都生成版本快照；采用原子替换；保留回滚；在时间轴中标记“参数变更事件” | 变更失败率、回滚次数、变更后异常率 |
| 受限策略合并导致资本重复占用或风险重复计算 | 风控被低估或仓位超预期 | 统一资本视图与统一风控快照；按策略组记录占用与归因；禁止多出口执行 | 实际敞口与预期敞口偏差、重复占用告警 |
| 交易所适配器语义差异 | 同一执行计划在不同适配器上行为不一致 | 建立适配器能力矩阵；用测试网/沙箱做契约测试；把订单状态映射到统一领域模型 | 适配器错误率、状态映射异常数、契约测试通过率 |
| 时间轴与回放成本过高 | 存储膨胀、查询慢、回放慢 | 采用最小事件集 + 快照；读模型投影；长期仅保留关键事件；支持压缩与导出 | 事件写入量、回放耗时、投影延迟 |
| 可观测信号过多导致噪音与成本上升 | 告警失真、排障效率下降 | 分级采样；业务与安全日志分流；默认仪表盘只看关键指标；异常自动聚合 | 告警噪音比、日志增长率、trace 采样率 |
| AI 建议越权或污染主链路 | 用户误以为 AI 直接控制系统，审计失真 | 默认只读；建议和受限写入需审批；AI 无法直接写模块、下单或变更执行逻辑；所有建议强制版本化 | AI 建议采纳率、审批拒绝率、AI 变更后回滚率 |
| 解释系统泄露敏感信息 | API key、签名字段、账户信息暴露 | 日志与报告脱敏；密钥统一托管；调试输出与业务输出分离；按角色控制日志可见性 | 脱敏失败告警、越权访问日志、敏感字段扫描结果 |

其中最容易被低估的是适配器层。官方文档显示，不同平台在 WebSocket 是否要求订阅时限、是否依赖 heartbeats、如何签名、如何处理沙箱、如何暴露订单/持仓/余额更新方面差异很大；如果不先固化统一能力矩阵和契约测试，执行模块很容易演化为一批“只在某一所能用”的临时代码。citeturn5view0turn3view1turn3view9turn5view1turn8view0

## 额外建议

以下功能值得实现，但不应挤占第二阶段核心交付：

| 功能 | 价值 | 建议优先级 |
|---|---|---|
| 交易前检查模板库 | 将常见数据源、symbol、账户、风控预检固化为模板，提升可用性与交付效率 | 中 |
| 滑点与交易成本归因 | 把策略收益拆分为 alpha、滑点、手续费与执行损耗，便于优化执行模块 | 中 |
| 高风险订单人工审批队列 | 对超过阈值的订单引入人工确认，提高实盘安全性 | 中 |
| 单次运行导出包 | 一键导出某次运行的版本、关键事件、图表与报表，便于复盘与沟通 | 中 |
| 数据来源与标签体系 | 为不同数据源标注来源、质量、延迟等级、适用品类，便于后续扩展 | 中 |
| 回测回归套件 | 让策略版本升级前自动对固定样本做回归验证 | 中 |
| 告警中心与订阅机制 | 将数据中断、风控拒绝尖峰、执行失败等集中推送到统一入口 | 中 |
| 策略模板与示例仓库 | 降低上手成本，帮助用户理解意图/代理/风控的推荐组合方式 | 低至中 |

这些能力大多不是第二阶段成功的必要条件，但会明显降低后续扩展和团队协作成本。其中“回测回归套件”和“单次运行导出包”尤其建议尽早设计接口，即便实现可以稍后，因为它们会直接影响后续的质量控制与跨团队协作效率。

### 关键术语定义

| 术语 | 定义 |
|---|---|
| 数据模块 | 负责数据源健康检查、行情获取、交易对校验、延迟监控与回测行情可视化的模块 |
| 意图 | 对“当前状态是否满足买/卖理由”的结构化表达，输出方向、强度、置信度与原因 |
| 代理 | 对多个意图进行权重融合、冲突处理和风险前收敛的模块 |
| 风控决策 | 对候选订单给出的批准、减仓、延迟、拒绝等结果及其原因 |
| 执行计划 | 已通过风控、准备送往模拟盘或交易所的标准化执行动作 |
| 结果层 | 订单状态、成交、持仓、盈亏与历史查询的统一展示与存储层 |
| 安全点 | 允许在线参数更新生效的离散时间点或评估周期边界 |
| 统一时间轴 | 将数据、意图、代理、风控、执行、结果和参数变更串联起来的单一视图 |
| 策略版本 | 一次运行所绑定的参数、配置、模块组合、AI 建议与审批结果的版本快照 |
| 报告生命周期 | 对解释、日志、报告按分级、TTL、压缩阈值实施的保留与清理策略 |

### 优先级与难度说明表

| 维度 | 含义 |
|---|---|
| 高优先级 | 不做则第二阶段主链路无法形成闭环，或系统缺乏基本可信度 |
| 中优先级 | 不影响最小闭环，但会明显影响可用性、扩展性或调参效率 |
| 低优先级 | 有价值但可延后，不影响第二阶段主目标 |
| 低难度 | 模块边界清晰、依赖少、主要为界面或标准化封装 |
| 中难度 | 涉及跨模块协作、状态同步或适配器抽象，但风险可控 |
| 高难度 | 涉及全局状态、一致性、跨策略共享视图或较强的系统集成复杂度 |
