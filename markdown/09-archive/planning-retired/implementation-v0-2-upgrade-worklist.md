# QuantPilot v0.2.0 升级工作清单

## 目的

本文档将 v0.2.0 升级研究转化为执行检查清单。
它是第一个治理种子落地后的第二阶段工作的活跃规划队列。

实现顺序有意保持保守：

1. 建立运行时治理基础。
2. 在该基础之上构建证据界面。
3. 添加受控的运行时变异。
4. 添加 AI 辅助提案和批准流程。
5. 加固合约优先交付、测试和运维。

## 主要工作块

| 块 | 范围 | 主要成果 | 状态 |
|---|---|---|---|
| 1. 运行时治理基础 | capabilities、event envelope、version/revision、permission boundary | 每次运行/事件可以证明它使用了哪个 capability、策略版本、参数生成、部署修订和权限模型 | 已完成 |
| 2. 证据界面 | 统一时间线、回放 API、报告生命周期、保留的关键事件 | 用户可以检查、回放、压缩和导出可信的证据链 | 已完成 |
| 3. 受控的运行时变异 | 参数流式传输、激活边界、回滚、安全窗口控制器 | 运行时更改可以提议、激活、观察和回滚，而不会在一个决策链内混合状态 | 已详细 |
| 4. AI 提案和批准链 | AI 提案台账、静态检查、沙箱回放、批准、审计 | AI 可以建议和提交候选方案，但不能直接更改实时运行时状态 | 已详细 |
| 5. 合约优先交付和运维加固 | OpenAPI/AsyncAPI、mock、Pact、e2e、指标、健康检查、告警 | 前端、后端、文档、测试和运行时通过机器可检查的合约保持一致 | 已计划 |

## 块 1：运行时治理基础

### 目标

使能力边界、事件身份、版本身份、部署身份和权限边界成为显式的运行时事实。本块是时间线、回放、报告压缩、参数热更新、安全窗口和 AI 批准的前提条件。

### 当前种子

第一个种子已存在：

- `/api/capabilities` 暴露模式哈希、链阶段、版本策略和权限边界。
- 运行时事件暴露 `envelope`。
- 运行和回测详情响应暴露 `governance` 快照。
- 回测清单保留治理快照。
- 前端诊断和回测详情视图通过共享的规范化器读取治理，并在不需要原始 JSON 检查的情况下显示治理身份。

本块中剩余的工作是将该种子加固为稳定的合约，而非尽力而为的响应形态。

### 交付物

| 交付物 | 描述 | 验收 |
|---|---|---|
| 能力合约 v1 | 稳定的能力模式，带有 `schema_hash`、链阶段、支持的部分、版本模型和权限边界 | 后端 fixture、前端默认能力、安全回退和运行时响应一致 |
| 事件 Envelope v1 | 附加到每个运行时/回测事件的稳定事件 envelope | 每个事件具有 `event_id`、`event_type`、`stage`、`run_id`、`sequence_no`、时间戳、版本 ID、`capability_hash`、`deployment_revision` 和 `retention_class` |
| 运行时治理快照 v1 | 运行/回测级快照，描述能力哈希、策略版本、参数版本、部署修订和权限模型 | 快照与保存的运行/回测一起持久化，并在重载后存活 |
| 部署修订模型 | 来自策略版本、编译 ID、参数版本和能力哈希的确定性修订 ID | 相同输入产生相同修订；更改的能力/参数产生新修订 |
| 权限边界模型 | 执行所有权、实盘执行、AI 写入、插件网络默认值和非执行订单访问的显式策略 | 当策略缺失或限制性时，运行时和前端可以失败关闭 |
| 兼容性默认值 | 旧运行/回测记录的安全反序列化默认值 | 旧持久化记录仍然以 `unknown`/安全治理默认值加载 |
| 合约测试 | 针对能力 fixture、运行事件 envelope、保存的回测清单和回退能力的聚焦测试 | 如果字段漂移或消失，测试失败 |

### 块 1 完成门禁

仅当所有这些检查都为真时，块 1 才能标记为完成：

- 能力响应、前端默认能力、后端 fixture 和安全回退都包含模式/哈希/版本/权限字段。
- 新运行、保存运行、临时回测、保存回测、回测清单、回放响应和 SSE 流一致地暴露治理和事件 envelope。
- 能力哈希和部署修订是确定性的，并由测试覆盖。
- 缺失或格式错误的权限边界为新写入/运行操作失败关闭。
- 遗留持久化记录成功加载，并显式标记为默认化/遗留。
- 诊断暴露足够的治理身份，供用户回答：哪个能力边界、策略版本、参数版本、部署修订和权限模型产生了此事件？

### 验收标准

当以下所有条件都为真时，块 1 完成：

- 每个新运行和回测都有治理快照。
- 暴露给前端的每个运行时/回测事件都有 envelope。
- `schema_hash`、`capability_hash` 和 `deployment_revision` 是确定性的。
- 缺失能力或缺失权限策略对新运行时操作失败关闭。
- 保存的工件在重载后保留治理数据。
- 前端至少为诊断和回退决策使用治理字段。
- 测试覆盖当前记录、保存记录、流式记录和遗留默认值。

### 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 哈希构建在响应和运行时快照之间分歧 | 回放无法证明运行时匹配了广告的能力边界 | 集中化能力哈希构建 |
| 自由格式字符串策略漂移 | 前端和后端对安全含义不一致 | 将阶段、保留类和策略提升为类型化枚举 |
| 旧持久化记录缺少治理 | 历史页面或回放可能在升级后失败 | 安全默认化并标记遗留记录为默认化 |
| 治理元数据仅成为 UI | 证据链保持不完整 | 在运行记录、回测清单和事件 envelope 中持久化快照 |

### 下一块进入标准

在块 1 至少具有这些稳定输入之前，不要开始统一时间线/回放/报告生命周期块：

- 规范事件 envelope
- 确定性治理快照
- 持久化能力哈希
- 类型化保留类
- 测试 fixture 证明保存的工件重载保留治理

## 块 2：证据界面

### 目标

在运行时治理基础之上构建面向用户的证据层。本块必须让用户检查发生了什么、回放事件链、理解哪些事实被保留为关键证据，以及无需从原始运行时 JSON 重建信任即可生成/导出报告。

块 2 不更改运行时决策。它组织、过滤、回放、总结和导出由受治理运行和回测已产生的证据。

### 来自块 1 的输入

块 2 假定这些事实是稳定的：

- 每个暴露的事件都有 envelope
- envelope `stage` 和 `retention_class` 是类型化合约字符串
- 运行/回测详情有规范化的治理快照
- 保存的工件在重载后保留治理和事件 envelope
- 遗留/默认化记录可读取，并由 `governance_source` 显式标记

如果这些输入中的任何一个漂移，块 2 工作必须停止，并且必须首先修复运行时治理合约。

## 块 3：受控的运行时变异

### 目标

允许运行时参数在策略运行时更改，而不在一个决策链内混合新旧状态。每个提议的变异必须具有版本化的参数身份、激活边界、回滚元数据、权限检查、安全窗口评估以及可链接回块 1 治理基础和块 2 证据界面的可审计事件。

块 3 不授予 AI 直接写入权限，也不引入实盘订单执行。它创建受控的变异基底，块 4 以后可以通过批准链使用。

### 来自块 2 的输入

块 3 假定这些事实是稳定的：

- 能力边界和运行时治理快照是失败关闭的
- 事件 envelope 携带序列、阶段、保留类、能力哈希和部署修订
- 时间线/回放/报告界面可以在没有原始 JSON 的情况下审计关键证据
- 报告生命周期和源更改检测可以证明审查消费了哪些证据
- 证据健康和清理端点可以观察报告/回放行为

如果这些输入漂移，运行时变异工作必须停止，直到治理和证据合约被修复。

### 交付物

| 交付物 | 描述 | 验收 |
|---|---|---|
| 参数变异合约 | 用于参数更改的类型化请求/提案/激活合约 | 每个变异具有提案 ID、参与者、目标范围、旧/新参数版本、原因、权限上下文和激活边界 |
| 参数版本身份 | 活跃参数集的确定性版本 ID | 相同的参数负载产生相同的版本；任何接受的更改产生新的版本，在治理和事件中可见 |
| 运行时变异台账 | 仅追加的提案、激活、拒绝和回滚持久化记录 | 重载的运行/回测可以解释每个边界处哪个参数集是活跃的 |

### 块 3 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 立即参数应用绕过边界 | 一个决策链混合新旧运行时状态 | 仅通过显式边界控制器调度激活；无直接写入路径 |
| 参数哈希包括显示噪声 | 治理更改而无实际参数更改 | 规范化规范化参数负载并排除时间戳/标签 |
| 回滚删除历史 | 审计线索无法证明发生了什么 | 使用仅追加回滚事件并保留每个先前的提案/激活 |
| 安全窗口策略仅成为 UI | 后端可以激活不安全更改 | 在调度/应用激活前在后端评估安全窗口 |
| 变异事件不保留 | 报告无法审计热更新 | 标记变异生命周期和拒绝事件 `retention_class=key` |
| 块 4 AI 路径直接写入 | AI 绕过人工批准和运行时守卫 | 块 3 仅暴露提案基底；块 4 必须使用相同的受守卫提案/批准路径 |

### 下一块进入标准

在 AI 提案和批准链开始之前，块 3 必须至少具有这些稳定输入：

- 参数变异提案合约
- 确定性参数版本身份
- 仅追加变异台账
- 激活边界控制器
- 安全窗口拒绝合约
- 通过边界控制器的回滚
- 时间线/回放/报告界面中可见的变异证据

## 块 4：AI 提案和批准链

### 目标

允许 AI 辅助运行时参数更改，而不给它直接写入实时运行时状态的路径。AI 可以起草候选方案、附加证据、运行静态检查、请求沙箱回放并建议批准决策。人工批准和块 3 变异边界控制器仍然是实时激活的唯一路径。

### 边界规则

- AI 输出在转换为受守卫的变异提案前是建议性的。
- AI 不能激活、回滚或直接更改活跃参数版本。
- 每个 AI 候选方案必须携带能力上下文、权限边界上下文、源证据、模型身份、提示身份和确定性哈希。
- 缺失或不支持的 `ai_write_policy` 失败关闭为提案只读行为。
- 静态检查和沙箱回放必须在批准授予前完成。
- 人工批准不能被 AI 自我批准替代。
- 批准的 AI 候选方案在运行时状态更改前仍然流经块 3 安全窗口和激活边界。
- 时间线、回放、紧凑证据和报告必须将 AI 批准生命周期暴露为受治理的证据，而非原始 JSON。

### 块 4 完成门禁

仅当所有这些检查都为真时，块 4 才能标记为完成：

- AI 不能直接变异活跃参数、激活更改或执行回滚。
- AI 候选创建被缺失、过时、格式错误或不支持的能力/权限上下文阻塞。
- AI 提案是类型化的、仅追加的、重载安全的，并包括模型、提示、证据、参与者、能力和部署身份。
- 静态检查在沙箱回放前运行并产生结构化的通过/失败原因代码。
- 沙箱回放与实时运行时状态隔离，并产生保留的比较证据。
- 转换前需要人工批准，AI 不能自我批准。
- 批准的 AI 候选仅转换为正常的块 3 变异提案；激活仍然依赖块 3 安全窗口和边界规则。
- 时间线、回放、紧凑证据和报告暴露 AI 提案、回放、批准和转换生命周期事件。
- 前端界面显示禁用状态和拒绝原因，无需原始 JSON 检查。
- 合约快照、单元测试、API 测试、前端测试和 E2E 演练覆盖主要路径和拒绝路径。
- UTF-8 和面向用户文本检查对 AI 批准标签保持绿色。

### 块 4 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| AI 直接写入运行时状态 | 批准链变成装饰性的并绕过块 3 安全性 | 没有 AI 端点可以调用激活、回滚或活跃参数更新路径；转换仅创建正常的变异提案 |
| AI 提案缺乏可重现身份 | 报告无法证明哪个模型/提示/证据产生了建议 | 持久化模型身份、提示哈希、证据哈希、源 ID、能力哈希和部署修订 |
| 沙箱回放改变实时状态 | 干运行证据在批准前更改运行时行为 | 在隔离上下文中运行回放，并断言活跃参数版本、变异台账和激活队列不变 |
| AI 自我批准 | 人工批准边界丢失 | 要求人工批准者身份，拒绝参与者/模型自我批准 |
| 回放后能力更改 | 批准基于过时的治理 | 在批准和转换前重新验证能力哈希、部署修订和权限边界 |
| 被拒绝的 AI 提案消失 | 审计线索隐藏不安全建议 | 保留被拒绝、拒绝、过期和已请求更改事件作为关键证据 |
| UI 暗示 AI 自治 | 用户相信 AI 可以执行实时写入 | UI 文案和禁用状态必须反映仅提案行为，除非未来能力策略显式更改 |
