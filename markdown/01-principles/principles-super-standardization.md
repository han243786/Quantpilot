# 超级规范化

> 生效日期: 2026-05-11 | v1.0.0 起强制执行 | 本文件是项目开发、检查、审计、优化的唯一执行标准

---

## 一、总纲

QuantPilot 的开发过程受 **五条流水线** 约束。每条流水线有明确的入口条件、执行步骤、产出物和验收标准。违反流水线要求的代码不得合并。

```
设计 → 开发 → 检查 → 审计 → 优化
  │       │       │       │       │
  │       │       │       │       └── 元流水线（自审计、自优化）
  │       │       │       └────────── 审计流水线（五维度 + GP 合规矩阵）
  │       │       └────────────────── 检查流水线（门禁脚本 + 测试套件）
  │       └────────────────────────── 开发流水线（代码 + 测试 + 文档）
  └────────────────────────────────── 设计流水线（设计文档 + 决策纪录）
```

### 版本号规则

采用语义化版本 (SemVer) `MAJOR.MINOR.PATCH`:

| 层级 | 触发条件 | 示例 |
|------|---------|------|
| **PATCH** (小版本) | 每轮优化更新（修复、收口、诱错修复） | v1.1.1 → v1.1.2 |
| **MINOR** (中版本) | 每轮完整流水线周期结束（Design→Dev→Check→Audit→Optimize 全部完成） | v1.1.x → v1.2.0 |
| **MAJOR** (大版本) | 对功能或系统架构进行大量追加更新 | v1.x.x → v2.0.0 |

版本号在 `Cargo.toml` 中声明，里程碑文档目录名跟随 `vX.Y.Z` 格式。

### AI 辅助开发的决策边界

当使用 AI 工具辅助开发时，以下情况 **必须** 向用户发起询问，不得自行决策：

| 需要询问 | 不需要询问 |
|---------|-----------|
| 架构方案二选一或多选一 | 单文件内 bug 修复 |
| 涉及 ≥3 个文件的跨模块变更 | 文档格式修正 |
| API 路由或数据模型的 breaking change | GP 违规的明显修正 (英文→中文等) |
| 里程碑范围变更 (新增/删除优化项) | 门禁脚本执行 |
| 版本号升级 (MAJOR/MINOR) | PATCH 版本号递增 |
| 技术栈/依赖选择 | 非功能性代码清理 |
| 存储或安全策略变更 | 测试用例修复 |

**原则**: AI 产出 → 用户审批 → 代码合并。AI 不得绕过 static check → sandbox → approval 链路。

## 二、设计流水线

### 2.1 触发条件

以下任一情况必须走过设计流水线后才能开始编码：

- 新增功能（非 bug 修复、非文案修改）
- 新增或修改 API 路由
- 修改插件协议或 capability contract
- 涉及跨模块（≥3 个文件）的架构变更
- 修改 `General_Policy.md` 或本文件

### 2.2 设计文档模板

每份设计文档存放于 `markdown/06-milestones/vX.Y.Z/`，按两位数字编号，必须包含：

| 节 | 内容 | 约束 |
|----|------|------|
| 目标 | 本次要达成什么 | 不写"为什么"（那是背景的事），只写"做到什么算完成" |
| 非目标 | 明确排除什么 | 防止范围蔓延 |
| 方案 | 改哪些文件、怎么改 | 文件级粒度，不写具体代码 |
| 验收 | 怎么验证完成 | 可执行命令或可观察行为 |
| 风险 | 可能出问题的地方 | 如有已知限制，必须写清 |

### 2.3 决策纪录

任何在开发过程中出现的 **二选一或多选一方案决策**，必须在设计文档中追加一条决策纪录：

```
决策: [标题]
选项:
  A: [描述] → 优点/缺点
  B: [描述] → 优点/缺点
选择: [A/B]
理由: [为什么选这个，不选那个]
影响: [选了之后哪些地方会受影响]
```

## 三、开发流水线

### 3.1 编码规范

全部规则已在 `General_Policy.md` 中定义，此处仅列出执行优先级：

| 优先级 | 条款 | 违规后果 |
|--------|------|---------|
| 阻断 | §1.1, §1.3, §5.4 (编译路径不可绕过) | 禁止合并 |
| 阻断 | §5.3 (禁止 stub evaluator) | 禁止合并 |
| 阻断 | §5.2 (禁止静默忽略参数) | 禁止合并 |
| 高 | §2.1 (错误全中文) | 合并前修复 |
| 高 | §5.1 (禁止硬编码魔数) | 合并前修复 |
| 中 | §2.3 (新 indicator 需测试) | 合并前补测试 |

### 3.2 提交规范

- 一个 commit 只做一件事（修复 / 功能 / 文档 / 审计）
- commit message 格式: `<type>: <Chinese description>`
- type: `feat` / `fix` / `docs` / `audit` / `style` / `refactor` / `test`
- 禁止 `--no-verify` 跳过 hooks

### 3.3 Pre-commit Hook

`scripts/pre-commit` 在 `git commit` 时自动执行：

```
cargo check --workspace
cargo test --workspace --no-run
cd frontend && npx vite build
cd frontend && npx vitest run
```

任何一步失败则提交被拒。

## 四、检查流水线

### 4.1 门禁矩阵

| # | 检查项 | 命令 | 阻断级别 |
|---|--------|------|:--:|
| 1 | UTF-8 编码 | `powershell tools/check-utf8.ps1` | 阻断 |
| 2 | 面向用户文本 | `powershell tools/check-user-facing-text.ps1` | 阻断 |
| 3 | 能力治理快照 | `powershell tools/check-capability-governance.ps1` | 阻断 |
| 4 | Rust 编译 | `cargo check --workspace` | 阻断 |
| 5 | Rust 测试全量 | `cargo test --workspace` | 阻断 |
| 6 | Clippy | `cargo clippy --workspace --all-targets -- -D warnings` | 高 |
| 7 | 前端构建 | `cd frontend && npm run build` | 阻断 |
| 8 | 前端测试 | `cd frontend && npm run test` | 阻断 |
| 9 | 前端 E2E | `cd frontend && npm run test:e2e` | 阻断 |
| 10 | npm 审计 | `cd frontend && npm audit --audit-level=moderate` | 阻断 |

### 4.2 收口包装器

```powershell
.\tools\run-closeout-gates.bat
```

执行全部 10 项门禁，任一失败则整体不通过。

### 4.3 门禁失败处理

| 阻断级别 | 处理方式 |
|----------|---------|
| 阻断 | 修复后重新跑全部门禁 |
| 高 | 修复后重新跑对应门禁 |
| 中 | 可在里程碑 closeout 时统一处理 |

### 4.4 角色诱错测试

除自动化门禁外，每里程碑 closeout 前必须执行**十角色诱错测试**。完整矩阵见 `markdown/05-testing/十角色全量诱错测试矩阵.md`。

十角色覆盖:

| # | 角色 | S0 场景数 | 核心关注点 |
|---|------|:--:|------|
| 1 | 新用户 | 5 | 首次操作不崩溃, 中文错误提示 |
| 2 | 策略开发者 | 5 | DAG 边界, 多时间框架, 并发文件 |
| 3 | CLI/QS 用户 | 5 | QS 语法错误, 死循环, 命令行参数 |
| 4 | 插件开发者 | 5 | Manifest 校验, Suite 完整性, 安全边界 |
| 5 | 运维者 | 5 | 存储配额, 凭证损坏, 端口冲突 |
| 6 | 安全研究者 | 6 | 路径注入, 凭证迁移, XSS, 速率限制 |
| 7 | API 调用者 | 4 | 空 body, 过期 hash, 负数参数 |
| 8 | 前端用户 | 1 | 窗口缩放, 撤销边界, localStorage 满 |
| 9 | 数据分析师 | 1 | 回测一致性, NaN 校验 |
| 10 | 系统管理员 | 2 | 启动目录创建, panic 恢复 |

执行规则: S0 场景必须全量通过, P1 发布前通过, P2 持续回归。

### 4.5 自由维度全量诱错审计

十角色诱错测试完成后，每个里程碑 **必须** 追加一轮**自由维度全量诱错审计**。

#### 4.5.1 与十角色诱错的区别

| | 十角色诱错 (§4.4) | 自由维度诱错 (§4.5) |
|---|---|---|
| 视角 | 预设角色身份 (新用户/开发者/运维...) | 无预设边界，Agent自主选择攻击向量 |
| 方法 | 按角色SOP执行固定场景 | 按技术维度自由搜索漏洞 |
| 覆盖 | 用户可见行为和接口 | 代码级漏洞、架构违规、并发/数值/持久化安全 |
| 产出 | 场景通过/失败清单 | 按严重度分级的发现清单 (S0/P1/P2/P3) |

两者互补: 十角色覆盖用户体验, 自由维度覆盖代码安全。

#### 4.5.2 五个自由攻击维度

每个维度由一个独立 Agent 并行执行，Agent 不受角色限制，可自由选择具体攻击向量:

| 维度 | 攻击焦点 | 工具方法 |
|------|---------|---------|
| A: 逻辑/契约/GP违规 | 编译路径绕过、静默忽略参数、stub实现、死代码、错误格式违规 | Grep搜索GP违规模式 + Read关键文件 |
| B: 并发/竞态/资源 | TOCTOU竞态、锁毒化、async/同步混用、内存泄漏、无界增长 | Grep搜索锁使用 + Read异步路径 |
| C: 边界/溢出/数值 | 整数溢出、除零、NaN/Inf传播、索引越界、时间戳溢出 | Grep搜索数值运算 + Read指标计算 |
| D: 序列化/持久化/一致性 | 非原子写入、serde安全、数据迁移、签名完整性、状态一致性 | Grep搜索fs::write + Read持久化路径 |
| E: API/错误处理/诊断 | 路径遍历、HTTP状态码、错误消息泄露、缺失验证、诊断质量 | Grep搜索路由handler + Read错误处理 |

#### 4.5.3 执行规则

- 每个维度至少1个Agent并行执行
- Agent必须输出按严重度(S0/P1/P2/P3)分级的发现清单
- 每个发现必须标注: 严重度、文件:行号、触发条件、修复建议
- S0 级发现 **必须在当前里程碑修复**
- P1 级发现 **在下个里程碑修复**
- P2/P3 级发现 **持续回归，逐步消化**

#### 4.5.4 多轮反复执行

自由维度诱错 **不限制执行轮次**。每个里程碑中可执行多轮，每轮更换攻击维度以获得更广覆盖:

| 轮次 | 示例维度 | 目标 |
|------|---------|------|
| 第1轮 | A:逻辑/契约, B:并发/竞态, C:边界/数值, D:持久化, E:API/错误 | 代码级漏洞全面扫描 |
| 第2轮 | F:前端渲染/交互, G:编译链完整性, H:测试质量, I:文档一致性, J:性能复杂度 | 上层质量和用户体验 |
| 第N轮 | 任意新角度组合 | 持续缩小盲区 |

**规则**:
- 每轮必须使用与之前**不重复**的攻击维度
- 每轮发现的 S0 必须在当前里程碑修复
- 多轮诱错的累计发现量是衡量系统质量的指标
- 在里程碑 closeout 报告中记录执行轮次和发现趋势

#### 4.5.5 验收标准

```bash
# 所有 S0 发现必须有对应的修复 commit
git log --oneline v1.1.2..HEAD | grep -c "S0"

# 修复后全部门禁通过
.\tools\run-closeout-gates.bat

# 自由维度审计报告落库
ls markdown/05-testing/自由维度诱错审计-*.md
```

## 五、审计流水线

### 5.1 五维度评分

每个里程碑结束时，对项目进行五维度审计：

| 维度 | 考察内容 | 评分标准 |
|------|---------|---------|
| 功能开发进度 | 指标覆盖、编译链完整、前端页面可用 | 1-10 |
| 仓库稳定程度 | 测试全量通过、编译 0 warning、npm audit 清零 | 1-10 |
| 发布就绪度 | 门禁全部通过、无架构违规、文档同步 | 1-10 |
| 用户友好程度 | 全中文错误、界面可用、文档准确 | 1-10 |
| 系统整体稳定性 | 回归检测、存储配额、编译路径合规 | 1-10 |

### 5.2 General_Policy 合规矩阵

逐条核查 §1-§8 全部条款，输出：

```
条款   状态     说明
§1.1   ✅/❌    具体发现
...
```

违规项必须在下个里程碑修复。

### 5.3 审计报告

存放于 `markdown/05-testing/`，命名包含日期。报告至少包含：

- 五维度评分表
- GP 合规矩阵
- 阻断/高/中/低 发现清单
- 修复优先级建议

## 六、优化流水线

### 6.1 触发机制

每个里程碑 closeout 后，审计报告中的发现转化为下个里程碑的优化项。优先级：

| 严重度 | 标签 | 处理时限 |
|--------|------|---------|
| 阻断发布 | S0 | 当前里程碑必须修复 |
| 发布前必须 | P1 | 下个里程碑必须修复 |
| 下个版本 | P2 | 两个里程碑内修复 |

### 6.2 优化项模板

每条优化项必须包含：

```
### [编号] [标题]
**严重度**: 阻断/高/中/低
**来源**: 审计发现 / 用户反馈 / 门禁失败
**策略**: 违反的 GP 条款
**问题**: 具体描述
**方案**: 步骤级操作
**验收**: 可执行的验证命令或可观察行为
```

### 6.3 里程碑文档

存放于 `markdown/06-milestones/vX.Y.Z/`：

- `01-规划方案.md` — 背景、原则、范围、验收总闸
- `02-综合优化清单.md` — 全部优化项（按 S0/P1/P2 分组）

## 七、元流水线

### 7.1 定义

元流水线是 **优化流水线的流水线**。它不在里程碑中规划，而是持续运行的后台进程。

### 7.2 自审计

| 检查项 | 频率 | 内容 |
|--------|------|------|
| 门禁脚本完整性 | 每月 | `check-gates-smoke.ps1` 验证所有门禁脚本自身可执行 |
| 测试覆盖率趋势 | 每里程碑 | 统计 `#[test]` 数量、`.test.js` 文件数变化 |
| 门禁耗时 | 每里程碑 | 记录每次 CI 全量耗时，超过 10 分钟必须分析原因 |
| 误报跟踪 | 持续 | 任何被手动 override 的门禁失败都记录原因 |

### 7.3 审计脚本的版本管理

所有 `tools/check-*.ps1` 脚本：

- 受 git 版本控制
- 自身通过 UTF-8 编码
- 脚本自身的修改必须注明原因
- 脚本输出格式必须稳定（下游可能解析）

### 7.4 策略检查工具的质量跟踪

当前检查工具: `check-utf8.ps1`, `check-user-facing-text.ps1`, `check-capability-governance.ps1`

跟踪指标：

| 指标 | 说明 |
|------|------|
| 误报率 | 检查报告违规但人工确认为误报的次数 / 总报告次数 |
| 漏报率 | 应当被检查捕获但遗漏的违规（由审计流水线补充发现） |
| 覆盖范围 | 检查覆盖的代码文件占比 |

## 八、执行规则

### 8.1 流水线触发链

```
提交代码
  → pre-commit (开发流水线)
    → CI (检查流水线全部门禁)
      → 十角色诱错 (§4.4)
        → 自由维度诱错审计 (§4.5) ← 可多轮反复执行
          → S0修复 → 再诱错 → S0修复 → ... (直至无新增S0)
            → 里程碑 closeout (审计流水线 → 五维度 + GP 矩阵)
              → 优化清单 (优化流水线)
                → 下个里程碑
```

### 8.2 阻断规则

以下情况**禁止进入下一阶段**：

- 任何阻断级门禁未通过
- 十角色诱错 S0 场景未全量通过
- 自由维度诱错 S0 发现未修复
- 审计发现阻断级违规
- 文档版本滞后于代码版本
- CHANGELOG 缺失当前版本条目
- GP 合规矩阵有 ❌ 项未修复

### 8.3 紧急豁免

如果需要绕过某条规则（例如修复线上问题需要快速合并），必须：

1. 在 commit message 中注明 `[EMERGENCY]` + 原因
2. 在下个里程碑中补齐所有跳过的检查
3. 紧急豁免本身被审计流水线追踪

## 九、与 General_Policy 的关系

| General_Policy | 本文件 |
|----------------|--------|
| 规定"做什么、不做什么" | 规定"怎么检查、怎么保证" |
| 代码级规范 | 流程级规范 |
| 静态文档 | 可执行流水线 |

两者是互补关系。GP 是实体法，本文件是程序法。
