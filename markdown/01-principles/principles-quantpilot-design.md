# QuantPilot 设计原则

## 产品定位

QuantPilot 不是一个单策略项目。

它是一个单机交易运行时平台，首要关注的是稳定的基础设施：

- 统一协议
- 统一数据语义
- 统一执行语义
- 集中式风险控制

## 核心原则

- 基础设施优先于策略特定的快捷方式
- 协议优先于临时实现
- 统一数据语义优先于交易所特定细节
- 统一执行语义优先于模式特定分支
- 集中式风险优先于直接下单
- 单机效率优先于过早的系统复杂性

## 文本编码规则

所有面向用户的文本、文档、前端源文件、导出模板和协议示例必须使用不带 BOM 的 `UTF-8` 编码。

规则：

- 切勿在前端或文档资源中混用 `GBK` / `GB2312` / 本地默认编码
- 前端源文件在提交前必须保存为 `UTF-8` 编码
- 面向用户的字符串必须在渲染后的 UI 中审查，而不仅仅是在源码 diff 中检查
- 导入旧文件时，在编辑内容之前先规范化编码
- CI 或预提交检查应拒绝替换字符、乱码或非 UTF-8 文本资源

此规则存在的原因是文本损坏是产品缺陷，而非外观问题。编码损坏会损害验证消息、运行时反馈、导出脚本和文档的可信度。

## 主链

QuantPilot 使用一条主链：

`数据 -> 意图 -> 代理 -> 风险 -> 执行`

任何策略、脚本或插件都不应绕过此主链直接下达最终订单。

此规则在以下环境中均须遵守：

- 实时模拟
- 快速回测
- 未来的精确模拟
- 后续的实盘交易

## 统一沙箱原则

当前项目优先级是构建统一的交易沙箱。

这意味着：

- 所有运行模式共享相同的对象语义
- 市场数据以规范化市场数据形式进入系统
- 风险检查在成交和执行之前进行
- 运行时事件是结构化且可回放的
- 状态可被快照和恢复

插件化依赖于此稳定基础。

## 层执行规则

系统按层顺序推进。

规则：

- 层间串行
- 层内工作可并行
- 并行工作必须使用同一份冻结的输入快照
- 层输出必须在下一层开始之前完成归并
- 内部可变状态不应跨层泄漏

此规则的存在是为了让实时和回测模式保持语义一致。

## 数据规则

只有规范化市场数据才能到达上层。

上层不应直接依赖原始交易所字段。

目标不是保留每一个原始字段，而是保持一个可复用、可测试、可回放的内部表示。

## 风险规则

风险是系统的中央关卡。

所有代理输出在进入执行之前必须通过风险检查。

风险负责处理以下事项：

- 敞口限制
- 杠杆限制
- 订单规模限制
- 下单频率限制
- 无效操作拒绝
- 结构化风险事件

## 持久化规则

QuantPilot 围绕热状态优先和轻量持久化设计。

持久化最高价值的输出：

- 账户快照
- 运行时事件日志
- 回测和回放报告
- 审计追踪

这使系统在单机上保持高效，同时保留恢复和可审计性。

## 长期方向

在统一沙箱稳定之后，系统可以安全地向以下方向发展：

- 将内建模块表达为插件
- 清单和锁定文件
- 依赖解析
- 本地缓存加远程注册中心
- 插件生命周期和生态系统治理
