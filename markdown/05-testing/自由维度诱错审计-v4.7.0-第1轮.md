## S0 阻断 (必须当前修复)

### S0-1: 锁顺序反转 — ai_proposals / approval_records 死锁风险

**严重度**: S0
**来源**: B — 并发/竞态
**文件**: `src/runtime/mutation.rs:1063,1103` vs `1823,1867`
**违反条款**: GP §9.4

**触发条件**: 并发调用 `POST create_runtime_ai_proposal` 和 `POST approve_ai_proposal`。

**问题**: `create_runtime_ai_proposal` 先获取 `ai_proposals` 写锁，再获取 `approval_records` 写锁。`approve_ai_proposal` 先获取 `approval_records` 写锁，再获取 `ai_proposals` 写锁。两个路径的锁获取顺序相反，形成死锁条件。

**修复建议**: 将 `create_runtime_ai_proposal` 中的 `persist_runtime_ai_proposal_transition` (获取 `ai_proposals` 锁) 移到 `approval_records` 插入之后，确保全路径遵循 `approval_records → ai_proposals` 顺序。

## P1 高 (已修复)

### P1-1: register/login 的 SQLite 调用未用 spawn_blocking

**严重度**: P1 | **来源**: B | **文件**: `src/auth/mod.rs:412,467` | **违反**: GP §2.8

**问题**: `register_handler` 和 `login_handler` 中的 SQLite 调用在 tokio 异步上下文中直接执行，阻塞工作线程。`refresh_handler` 已正确使用 `spawn_blocking`。

**修复建议**: 将 register/login 中的 SQLite 操作包装在 `tokio::task::spawn_blocking` 中。

### P1-2: graph delete 刷新缺 fsync

**严重度**: P1 | **来源**: D | **文件**: `src/graph_api.rs:779-785` | **违反**: GP §2.6

**问题**: `refresh_latest_graph_after_delete` 使用 `fs::write(.tmp)` 后直接 `fs::rename`，缺少 `sync_all` 和父目录 fsync。

**修复建议**: 替换为 `runtime_persistence::atomic_write_json` 或补充 sync_all + sync_directory。

### P1-3: 存储配额 TOCTOU 竞态

**严重度**: P1 | **来源**: D | **文件**: `src/storage_lifecycle.rs:368-407` | **违反**: GP §7.2

**问题**: `ensure_storage_quota` 采用 CHECK-BEFORE-WRITE 模式。并发请求可同时通过配额检查后写入，合计超过 500MB 限制。

**修复建议**: 降低 `reject_at_bytes` 至 90% (450MB) 增大缓冲区；或使用 AtomicU64 计数器做预扣减模式。

### P1-4: Auth 子系统未录入 OpenAPI

**严重度**: P1 | **来源**: E | **文件**: `contracts/openapi/root.yaml` vs `src/auth/mod.rs:803-812` | **违反**: GP §4.1, §3.3

**问题**: 三个 auth 端点 (`POST /api/auth/register`, `/api/auth/login`, `/api/auth/refresh`) 完全未出现在 OpenAPI 文档中。

**修复建议**: 在 `root.yaml` 中增加 `auth` tag 和三个端点定义。

### P1-5: README 宣称 "live" 为运行时模式

**严重度**: P1 | **来源**: E | **文件**: `README.md:102` | **违反**: GP §1.12, §3.3

**问题**: README 宣称 `live (OKX testnet 模拟盘)` 为运行时模式。`supportMatrix.js` 的 `SUPPORTED_RUNTIME_MODES` 只声明 `["paper"]`。"live" 是执行模块 (`live.okx`) 非运行时模式。

**修复建议**: 改为 `执行模块: builtin.execution.paper, live.okx (OKX testnet 模拟盘)`。

### P1-6: 空 v4 回测静默返回零值结果

**严重度**: P1 | **来源**: C | **文件**: `src/runtime/backtest.rs:586-593` | **违反**: GP §5.2

**问题**: v4 回测无执行数据时返回 `equity: 0.0` 的单点曲线，回测报告"成功"但所有指标=0。用户无法区分"策略收益为零"和"策略根本没执行"。

**修复建议**: 在空资产曲线时返回错误或在前面明确展示"无执行数据"状态。

## 审计后记

本轮审计在 25/25 closeout 门禁全部通过后执行。发现 1 个 S0 (锁顺序反转) 和 2 个 S1 (UTF-8 乱码 + 英文错误消息) — 均无法被当前门禁捕获：

- **S0 锁顺序反转**: 门禁测试不覆盖并发死锁场景
- **S1 乱码**: `cargo check` 不验证字符串编码有效性
- **S1 英文消息**: `cargo check` 和 `check-user-facing-text.ps1` 均不覆盖英文错误消息

证明了超级规范化 §8.5 自由维度诱错审计对自动化门禁盲区的补位价值。建议在 v4.8.0 及后续版本中持续执行，并将可模式化的检查 (如英文错误消息检测) 纳入 `check-user-facing-text.ps1`。
