# 工作模式路由

> Protocol: work_mode_routing
> Version: work-mode-routing-v1.2
> Scope: v4.16+ 所有开发、治理、文档和验证任务。
> Owner: 三矩阵治理层。

本文件把治理入口从“只有递归重构”升级为三种开发模式 + 一种维护模式。任何提案、口头指令、递归批次或临时修复在执行前都必须先判定工作入口。

---

## 1. 三种开发模式 + 一种维护模式

| 模式 | 目标 | 典型任务 | 默认产物 |
| --- | --- | --- | --- |
| 重构模式 | 改结构，不改功能 | 模块抽离、父子边界整理、旧链路替换、模块树 closeout | 等价基线、抽离记录、单叶 closeout、父叶残余判断 |
| 推进模式 | 推产品目标，形成新能力闭环 | 新功能、新接口、新页面、新运行能力、路线图里程碑 | 开辟清单、落实记录、测试证据、跳转/返回记录、写入 closeout |
| 切面打磨模式 | 横向提升质量，按档位先隔离再替换 | 性能、安全、UX、错误提示、日志、测试体系、可观测性、开发体验 | 轻量执行卡或隔离清单、镜像区、优化证据、裁剪切换清单 |
| 文档债清理 | 修复旧路径、旧索引或旧说明，不做功能开发 | 历史旧路径、冷文档降级、索引修复、门禁旧债 | 路径确认、替换/归档说明、docs gate、ledger 记录 |

前三种是开发模式，`doc_debt_cleanup` 是维护模式。四者共同组成工作入口。

重构模式不是默认模式。只有当任务目标明确是改变结构、拆分模块或裁剪旧结构时，才进入重构模式。

---

## 2. 模式判定表

| 触发问题 | 判定 |
| --- | --- |
| 是否要改变模块边界、父子关系、文件归属或 public owner? | 重构模式 |
| 是否要新增或补齐用户/开发者可用能力? | 推进模式 |
| 是否要在一条横向质量轴上优化多个入口或模块? | 切面打磨模式 |
| 是否需要先复制镜像、优化到满意后再裁掉旧代码? | 切面打磨模式 |
| 是否只清理旧路径、旧索引、冷文档或治理债? | 文档债清理 |
| 是否只是修一个局部 bug 且不改变结构、能力和切面? | 进入三档提案判定，不强制三模式升级 |
| 是否同时命中多个模式? | 先拆为主模式和附属模式；不得用重构流程吞掉推进或切面目标 |

不确定时必须先写清楚“为什么不是另外两种模式”。如果无法判断，进入 FitCheck，不得直接实现。

---

## 3. 模式互斥与转换

1. 重构模式不得自动吞并推进模式。结构整理完成后，如需新增能力，必须另起推进模式。
2. 推进模式不得顺手大规模整理结构。若结构阻塞目标闭环，必须按 `advance-mode-protocol.md` 的跳转/返回规则局部调用重构模式。
3. 切面打磨模式不得直接在旧代码上优化。必须先隔离和分叉。
4. 切面打磨模式进入裁剪阶段时，如果需要删除旧结构，裁剪步骤可临时借用重构模式的旧路径清除门禁，但主模式仍是切面打磨。
5. 发布过渡不是任何模式的默认结果。只有开发者明确声明进入发布版本过渡后，才允许提出发布态横向连接优化。

---

## 4. 模式入口记录

每次任务至少记录以下字段:

| 字段 | 含义 |
| --- | --- |
| `work_mode` | `refactor` / `advance` / `aspect_polish` / `doc_debt_cleanup` |
| `mode_reason` | 为什么选择该模式 |
| `not_other_modes` | 为什么不是其他模式 |
| `affected_workset` | 代码、契约、测试、文档和治理资产范围 |
| `primary_gate` | 本模式最小验证门禁 |
| `cutover_or_closeout` | 当前模式的收口条件 |

超轻量任务可使用 `governance-quality-speed-guard.md` 的入口卡:

```text
work_mode:
reason:
allowed_scope:
exit_gate:
```

用户只说“继续”时:

1. 若当前任务已有明确 `work_mode`，只能继续该模式。
2. 若当前任务没有明确 `work_mode`，先判定模式，不得默认进入递归重构。
3. 若继续过程中需要局部跳转，必须声明 `jump_to` 和 `return_condition`。
4. 一次性问题、进度报告或临时测试请求不得写入长期递归游标。

---

## 5. 与 QPCursor 的关系

QPCursor 仍是递归重构的权威执行格式，但不再代表所有任务。

| 模式 | QPCursor 使用方式 |
| --- | --- |
| 重构模式 | 默认使用 QPCursor 或兼容递归状态游标 |
| 推进模式 | 仅在推进中触发结构迁移时使用 |
| 切面打磨模式 | 仅在裁剪阶段需要删除旧结构或改模块边界时使用 |
| 文档债清理 | 不使用 QPCursor；仅在清理影响递归状态文件时更新兼容游标 |

模式路由优先于递归游标。递归游标不能把一次性用户问题、进度报告或临时调试要求混入长期流程。

---

## 6. 当前工作游标与 ledger

四种工作入口共同使用 `current-work-cursor.yaml` 作为当前治理坐标，防止代理靠聊天历史接管任务。

每轮 closeout 需要追加或确认 `topology-ledger.ndjson` 中的记录。递归重构仍可继续使用 QPCursor 或 `recursive-state.json`，但它们不能覆盖本文件定义的工作入口判定。
