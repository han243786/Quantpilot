# 推进模式协议

> Protocol: advance_mode
> Version: advance-mode-v1
> Scope: v4.16+ 新能力、新接口、新页面、新运行路径、新产品闭环和路线图里程碑。
> Owner: 三矩阵治理层。

推进模式用于把项目从“已有结构”推进到“新增可用能力”。它不是重构模式，也不是切面打磨模式。它允许新增代码和新增端口，但必须先说明这些新增能力如何接入已有系统，以及何时允许临时跳转到其他模式处理阻塞。

固定流程:

```text
开辟 -> 落实 -> 测试 -> 跳转 -> 返回 -> 写入
```

若新代码不满足技术指标，允许从任意阶段跳回 `开辟`、`落实` 或 `测试`，重新循环；不得用未达标实现强行写入主代码库。

---

## 1. 开辟

开辟阶段只确定能力边界和接入边界，默认不直接落代码。

必须标记:

| 类别 | 必须标记内容 |
| --- | --- |
| 目标能力 | 新增能力要解决什么问题，完成后用户或开发者能做什么 |
| 既有接入端口 | 会接入的既有 route、command、event、schema、store、component、service、state owner、持久化点 |
| 新增端口 | 需要新增的 route、command、event、schema、capability action、UI entry、测试入口、文档入口 |
| 技术指标 | 行为指标、性能指标、兼容指标、错误处理指标、可观测指标、安全指标 |
| 不得外溢范围 | 本轮不允许顺手改造、重构或打磨的模块、文件、接口和文档 |
| 验收路径 | 单测、集成测试、E2E、smoke、手动核查或截图核查的最小集合 |

开辟输出物固定为 `advance_opening_manifest`。

---

## 2. 落实

落实阶段允许新增代码、测试、契约和文档，但必须受开辟清单约束。

落实规则:

1. 新代码必须接在开辟阶段标记的既有端口或新增端口上。
2. 若发现端口设计不足，必须回到开辟阶段更新端口清单。
3. 不得借推进模式大规模搬迁旧代码；结构阻塞时进入跳转阶段。
4. 新 capability / route / event / schema 必须同步登记到契约或模块树候选节点。
5. 新 UI 入口必须说明来源页面、导航路径和失败/空态。

落实输出物固定为 `advance_implementation_record`。

---

## 3. 测试

测试阶段证明新增能力达到了开辟阶段的技术指标。

至少验证:

| 验证项 | 要求 |
| --- | --- |
| 成功路径 | 新能力主流程可以完成 |
| 失败路径 | 输入错误、后端失败、权限不足、超时或空数据有可控表现 |
| 兼容路径 | 既有端口和旧能力没有被破坏 |
| 契约路径 | route/schema/event/capability 与真实实现一致 |
| UI/交互路径 | 页面、焦点、响应式或手动 smoke 按本轮影响面验证 |
| 治理路径 | 模块树、全量树、里程碑或状态游标按实际新增能力更新 |

测试输出物固定为 `advance_test_evidence`。

---

## 4. 跳转

推进过程中如果遇到局部阻塞，可以临时跳转到其他模式。

| 跳转目标 | 允许条件 | 禁止事项 |
| --- | --- | --- |
| 重构模式 | 既有结构阻塞能力闭环，必须先调整模块边界、父子关系、public owner 或旧路径归属 | 不得把整个推进任务吞进递归重构；只处理阻塞局部 |
| 切面打磨模式 | 新能力的某个横向质量切面需要隔离、镜像、优化或裁剪 | 不得把产品能力目标替换成泛化体验优化 |

跳转必须记录:

```text
jump_from: advance
jump_to: refactor | aspect_polish
jump_reason:
allowed_workset:
return_condition:
```

跳转输出物固定为 `advance_jump_record`。

---

## 5. 返回

其他模式的局部调用完成后，必须回到推进模式继续验收新增能力。

返回条件:

1. 跳转时声明的 `return_condition` 已满足。
2. 局部重构或切面打磨没有扩大推进模式的目标能力。
3. 推进模式的开辟清单已按真实变化更新。
4. 测试计划已纳入跳转期间改动的影响面。

返回输出物固定为 `advance_return_record`。

---

## 6. 写入

写入阶段表示新增代码完全符合技术指标，可以并入主代码库和当前治理资产。

写入门禁:

| 门禁 | 要求 |
| --- | --- |
| 技术指标达标 | 开辟阶段声明的指标全部满足，未满足项必须有开发者认可的延期说明 |
| 主代码接入 | 新入口、新端口、新能力已经成为主路径或受控可选路径 |
| 契约同步 | API、事件、schema、capability、UI 导航、测试入口与实现一致 |
| 治理同步 | 模块树、全量树、里程碑、索引、状态记录同步当前事实 |
| 回退说明 | 写清如何禁用或回退新增能力 |

写入输出物固定为 `advance_write_in_closeout`。

---

## 7. 循环规则

推进模式允许循环，但必须记录原因:

| 循环方向 | 触发条件 |
| --- | --- |
| 测试 -> 落实 | 实现缺陷、失败路径缺失、契约不一致 |
| 测试 -> 开辟 | 技术指标或端口设计不完整 |
| 写入 -> 测试 | 写入前发现主路径或治理资产未验证 |
| 跳转 -> 返回 -> 测试 | 局部重构/切面打磨完成后继续能力验收 |

禁止用循环掩盖 scope creep。新增目标能力时必须重新开辟。
