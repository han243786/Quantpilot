# v1.0.0 综合优化清单

> 五阶段 | 估 TBD 天 | 三大目标: 插件化架构 + 重型策略 + 超级规范化

## Phase 1: 协议补全

### 1.1 RFC-001 数据请求协议落地

**严重度**: 🟠 高 | **策略**: v1.0.0 插件化基础

**问题**: `DataRequest` 协议已定稿但无对应 struct，当前数据请求走 FrontendRuntimeConfig 内嵌格式。

**方案**: `qrpc_core/src/lib.rs` 新增 `DataRequest` struct，字段包含 `exchange`、`symbol`、`kind` (Kline/Quote)、`timeframe`、`window_size`。

**验收**: `grep "struct DataRequest" qrpc_core/src/lib.rs` 存在且与 RFC-001 字段一致。

### 1.2 RFC-010 分配协议落地

**严重度**: 🟠 高 | **策略**: 组合优化基础

**问题**: `Allocation` 协议设计稿存在但未实现。当前加权 agent 内嵌分配逻辑，不可替换。

**方案**: `qrpc_core/src/lib.rs` 新增 `Allocation` struct 和 `AllocationMethod` enum (EqualWeight / FixedWeight / RankWeight / ScoreWeight)。代理决策输出 PortfolioTarget → Allocation 模块处理 → RiskDecision。

**验收**: `grep "struct Allocation" qrpc_core/src/lib.rs` 存在且可序列化。

### 1.3 RFC-012 订单协议落地

**严重度**: 🟠 高 | **策略**: 执行层插件化基础

**问题**: `Order` 协议未实现，当前 paper 执行模块内部模拟订单生命周期。

**方案**: `qrpc_core/src/lib.rs` 新增 `Order` struct (order_id, symbol, side, qty, price, type, status)。执行插件通过 Order struct 与 Sandbox 交互。

**验收**: `grep "struct Order" qrpc_core/src/lib.rs` 存在。

### 1.4 RFC-013 执行反馈协议落地

**严重度**: 🟠 高 | **策略**: 执行闭环

**问题**: `ExecutionFeedback` 未实现，当前 fill event 直接在 Sandbox 内生成。

**方案**: `qrpc_core/src/lib.rs` 新增 `ExecutionFeedback` struct (order_id, fill_qty, fill_price, status, timestamp)。执行插件产出 feedback → Sandbox 更新持仓和现金。

**验收**: `grep "struct ExecutionFeedback" qrpc_core/src/lib.rs` 存在。

### 1.5 RFC-020 插件清单协议完善

**严重度**: 🟠 高 | **策略**: 插件化架构基础

**问题**: `PluginManifest` 已定义但字段不足以支持双层模型和热接管声明。

**方案**: 扩展 `PluginManifest`，新增字段：
- `plugin_type: "atom" | "suite"`
- `atoms: Vec<AtomRef>` (仅 suite)
- `capabilities: Vec<CapabilityDeclaration>`
- `hot_handoff: bool` (声明是否支持热接管)
- `asset_management: bool` (声明是否有完整资产管理能力)

**验收**: `PluginManifest` 包含以上全部字段；`validate()` 拒绝缺失必填字段的 manifest。

## Phase 2: 插件架构

### 2.1 原子插件注册与加载

**严重度**: 🔴 阻断 | **策略**: 插件化核心

**问题**: 当前 18 种指标、6 种模块硬编码在 Core IR 和 evaluator 中，无法动态加载。

**方案**:

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core/src/plugin.rs` | 定义 `AtomManifest` (type, exchange, symbol, capability_version) |
| 2 | `qrpc_runtime/src/plugin_runtime_registry.rs` | 实现 `AtomRegistry`：从 `plugins/atoms/` 目录加载 .json manifest |
| 3 | `qrpc_runtime/src/core_ir_evaluator.rs` | 重构 dispatch match → trait object `dyn IndicatorEvaluator`，由注册表按 `CoreIndicatorKind` 查找 |
| 4 | `qrpc_runtime/src/data_module.rs` | 同样重构为 trait object `dyn DataModuleProvider` |

**验收**: 新增一个 atom (如 `atr.json`)，复制到 `plugins/atoms/`，启动后 `/api/capabilities` 包含该 atom。

### 2.2 套件插件打包与校验

**严重度**: 🔴 阻断 | **策略**: 插件化核心

**问题**: 无套件概念，策略组合完全依赖前端图编辑器手动连线。

**方案**:

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core/src/plugin.rs` | 定义 `SuiteManifest` (name, version, atoms: Vec<AtomRef>, route: DAG) |
| 2 | `qrpc_runtime/src/plugin_runtime_registry.rs` | 实现 `SuiteRegistry`：加载套件，校验 atom 依赖全部已注册 |
| 3 | 同上 | 套件校验：所有 atom 的 exchange/symbol 一致，否则拒绝打包 |
| 4 | `qrpc_core/src/plugin.rs` | `SuiteManifest::validate()` 实现：检查 DAG 无环、端口匹配、atom 存在性 |

**验收**: 创建一个套件 `okx_btc_ma.json` 引用 5 个 atom，校验通过；创建一个 exchange 不一致的套件，校验拒绝。

### 2.3 插件市场元数据

**严重度**: 🟡 中 | **策略**: 发现机制

**问题**: 无远端插件发现机制，用户需手动管理本地 json。

**方案**:

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core/src/plugin.rs` | 定义 `MarketMetadata` (repo_url, index_hash, plugins: Vec<PluginSummary>) |
| 2 | `src/` (新文件) | 实现 `PluginMarketClient`：HTTP GET 远端 index.json → 本地协议校验 |
| 3 | `src/app_router.rs` | 新增 `/api/plugins/market` 路由返回可用市场插件列表 |

**验收**: 配置远端 URL，调用 `/api/plugins/market` 返回插件列表；hash 不匹配时拒绝。

### 2.4 插件安全边界

**严重度**: 🟠 高 | **策略**: 安全

**问题**: 插件可访问 Sandbox 内部状态，缺乏权限隔离。

**方案**: 在 `PluginManifest` 中定义 `permission_boundary`，Sandbox 在调用插件前检查：
- `access_credentials: deny` (禁止插件访问凭证)
- `access_network: deny | same_exchange | any`
- `access_state: read_only | read_write | sandboxed`

**验收**: 插件声明 `access_credentials: deny` 但尝试调用 `vault.get_service()` 时 Sandbox 拒绝并记录安全事件。

## Phase 3: 重型策略

### 3.1 多时间框架支持

**严重度**: 🟠 高 | **策略**: 机构级策略基础

**问题**: 当前一个 K 线数据源只能配置一个 time frame。

**方案**: `FrontendRuntimeConfig` 的 data_sources 允许同一 symbol 声明多个 time frame (如 `1m`, `5m`, `1h`)。编译链为每个 time frame 生成独立 DataSourceConfig。DAG 路由中不同 intent 可引用不同 time frame。

**验收**: 创建一个策略，同时使用 BTCUSDT 的 1m 和 1h K 线，paper 运行成功。

### 3.2 DAG 策略路由

**严重度**: 🔴 阻断 | **策略**: 替代固定 pipeline

**问题**: 当前编译链假设 data → intent → agent → risk → exec 严格线性。

**方案**:

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core_ir/src/lib.rs` | `CoreIR` 新增 `edges: Vec<CoreIREdge>` (source_node, target_node, port) |
| 2 | `qrpc_compiler/src/lib.rs` | 编译时做 DAG 验证：环检测、端口匹配、拓扑排序 |
| 3 | `qrpc_runtime/src/` | Sandbox 按拓扑序执行节点，多入度节点等待所有输入就绪 |

**验收**: 创建一个分支策略 (data_kline → [intent_ma, intent_rsi] → agent)，编译通过且运行结果可复现。

### 3.3 热接管协议

**严重度**: 🔴 阻断 | **策略**: 策略运行时切换

**问题**: 无策略间切换机制，更换策略需停止 Sandbox 重启。

**方案**:

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core/src/lib.rs` | 定义 `HandoffSnapshot` (positions, open_orders, cash, current_cycle) |
| 2 | `qrpc_runtime/src/sandbox.rs` | 新增 `handoff()` 方法：接收当前策略快照 → 完整性校验 → 提交给接管策略 |
| 3 | `qrpc_core/src/plugin.rs` | `PluginManifest.hot_handoff` 为 true 时强制校验 `asset_management` 也为 true |

**验收**: 策略 A 运行 → handoff → 策略 B 接管并完成对账 → 策略 B 继续运行，持仓和现金一致。

### 3.4 组合权重可调

**严重度**: 🟡 中 | **策略**: 多标的组合基础

**问题**: 当前加权 agent 的权重在前端图编辑器静态配置。

**方案**: Allocation 模块支持运行时权重调整：`FixedWeight` 从策略参数读取，`RankWeight` 按信号值排序分配，`ScoreWeight` 按信号值比例分配。

**验收**: 创建一个两标的策略，权重 60/40，paper 运行验证目标持仓比例。

## Phase 4: 流水线固化

### 4.1 Pre-commit Hook 补全

**严重度**: 🟡 中 | **策略**: 超级规范化

**问题**: `scripts/pre-commit` 已存在但覆盖不完整。

**方案**: 追加检查：
- `cargo clippy --workspace --all-targets -- -D warnings`
- `powershell tools/check-user-facing-text.ps1`
- `powershell tools/check-capability-governance.ps1`

**验收**: 引入一个违规 (如英文错误消息)，`git commit` 被 hook 拒绝。

### 4.2 元流水线追踪

**严重度**: 🟢 低 | **策略**: 超级规范化 §7

**问题**: 门禁脚本无性能和质量追踪。

**方案**: 新增 `tools/track-gate-metrics.ps1`：记录每次门禁耗时、通过/失败、误报标记。输出 JSON 到 `storage/audit/gate-metrics.json`。

**验收**: 运行两次门禁，`gate-metrics.json` 记录两次数据。

### 4.3 设计文档模板强制执行

**严重度**: 🟢 低 | **策略**: 超级规范化 §2.2

**问题**: 现有里程碑文档格式不统一。

**方案**: 创建 `markdown/09-archive/planning-retired/design-doc-template.md`，包含目标/非目标/方案/验收/风险/决策纪录六个必填节。新 PR 如涉及设计变更但无设计文档，review 时拒接。

**验收**: 模板文件存在；下一个非 bugfix PR 携带符合模板的设计文档。

## Phase 5: 收口整合

### 5.1 全量审计

**严重度**: 🔴 阻断 | **策略**: 发布前必做

**方案**: 对 v1.0.0-rc 执行五维度审计，输出 GP 合规矩阵、阻断/高/中/低发现清单、修复优先级。

**验收**: 审计报告长期归档于 `markdown/09-archive/testing-retired/全量审计报告-v1.0.0.md`；无阻断级发现。

### 5.2 文档同步

**严重度**: 🟠 高 | **策略**: 文档进度 ≥ 代码进度

**方案**: 更新 `README.md`、`CHANGELOG.md`、`overview-current-status-and-roadmap.md`、`02-protocol/README.md` (RFC 状态全部更新)。

**验收**: 四处文档的版本号统一为 v1.0.0；RFC 状态与代码一致。

### 5.3 整合包发布

**严重度**: 🔴 阻断 | **策略**: 发布

**方案**: 基于 v1.0.0 tag 构建 Tauri 桌面安装包 (`.msi`)。包含：后端 binary、前端 dist、默认插件集、策略模板。

**验收**: 安装包在干净 Windows 11 上可启动；策略中心可浏览；凭证面板可管理；策略图可编译和 paper 运行。
