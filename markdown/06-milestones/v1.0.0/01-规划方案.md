# v1.0.0 规划方案

> 2026-05-11 | 首个整合包 | 三大目标: 插件化架构 + 重型策略 + 超级规范化

---

## 背景

v0.5.2 完成了全量排雷收口——测试套件全线通过、编译路径统一、存储配额在线、Rust warning 清零。项目已具备发布基线。

在此基础上，v1.0.0 不再追加零散功能，而是完成三项架构级升级，使项目从"个人沙盒"进化为"可插拔的策略研发平台"。

## 目标

### 1. 轻核心 + 重挂载 (插件化架构)

**做到什么算完成**：

- 核心只保留三件事：QS 编译链、Sandbox 调度器、插件协议
- 实现双层插件模型：原子层 (indicator/data module) + 套件层 (纯打包路由)
- 插件市场元数据支持远端拉取，本地协议校验
- 套件打包时校验 exchange/symbol 一致性
- 插件安全边界：不碰凭证管理，协议合规即放行

### 2. 重型策略支持

**做到什么算完成**：

- 多时间框架：一个策略可声明多个不同 time frame 的数据源
- 多标的组合：权重可调的 multi-symbol rebalance
- DAG 策略路由：data → [intent_a, intent_b] → agent → risk → exec，不强制单链
- 热接管：策略 A 运行时发 handoff 信号 → Sandbox 做中介 → 策略 B 接管（持仓、订单、现金完整迁移）
- 执行算法归插件：TWAP/VWAP/iceberg 等由插件提供

### 3. 超级规范化

**做到什么算完成**：

- 五条流水线全部可执行：设计→开发→检查→审计→优化
- pre-commit hook 阻断不合规提交
- 元流水线持续追踪门禁耗时、误报率、覆盖范围
- 全部设计文档符合 §2.2 模板
- 全部决策纪录可追溯

## 非目标

以下事项明确不在 v1.0.0 范围：

- 不开放实盘交易
- 不接入第三方插件市场运营
- 不做 Web 端多人协作
- 不做策略托管/云端运行
- 不引入新的指标或 intent 类型（已完成的 18 种维持不变）

## 决策纪录

### 决策 1: 插件粒度

**选项**:
- A: 仅原子层 (每个 indicator 一个插件，用户自由组合)
- B: 仅套件层 (完整策略链打包为一个插件)
- C: 双层模型 (原子层 + 套件层)

**选择**: C

**理由**: A 太碎，用户组合成本高；B 太重，无法灵活复用。双层模型在灵活性和便利性之间取平衡——原子层保证复用，套件层降低组装门槛。

**影响**: 需要维护两套 manifest schema；套件打包时需要校验原子兼容性。

### 决策 2: 策略路由拓扑

**选项**:
- A: 固定 pipeline (data → intent → agent → risk → exec，严格线性)
- B: DAG (有向无环图，一个 data 可喂多个 intent，允许多链并行)

**选择**: B

**理由**: DAG 能表达"同一 K 线数据同时计算 MA 和 RSI，两个信号的 agent 决策合并后统一过风控"这类真实场景。固定 pipeline 是一维的，机构级策略天然需要分支和合并。

**影响**: 编译链需要支持 DAG 验证（环检测、端口匹配）；运行时调度需要处理多链并发时的时序一致性。

### 决策 3: 热接管 vs 热插拔

**选项**:
- A: 支持运行时热插拔 (直接替换运行中的插件)
- B: 只支持热接管 (策略 A 退出 → 策略 B 接管，Sandbox 做中介)
- C: 两者都不支持

**选择**: B

**理由**: 热插拔风险过高——运行中的订单、持仓、现金状态无法安全迁移。热接管通过 Sandbox 中介 + 完整状态快照 + 对账机制保证安全。策略必须声明自己有完整资产管理能力才能声明热接管。

**影响**: 需要定义 handoff 协议 (快照格式、对账步骤、接管超时)；Sandbox 需要新增 handoff 调度逻辑。

### 决策 4: 插件市场元数据

**选项**:
- A: 纯本地 json registry
- B: 远端拉取 + 本地协议校验

**选择**: B

**理由**: 本地 registry 无法保证插件的完整性和版本一致性。远端拉取后本地按协议规范校验——远端提供可用性，本地保证安全性。

**影响**: 需要定义元数据 schema (名称、版本、依赖、能力声明、hash、签名)；需要实现拉取+校验链路。

## 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 插件协议设计过于复杂，开发周期失控 | 延迟发布 | Phase 2 先做最小可运行子集 (一个 atom + 一个 suite 跑通) |
| DAG 路由引入时序 bug | 策略执行结果不可复现 | 编译时做环检测 + 拓扑排序；运行时加确定性测试 |
| 热接管状态迁移不完整 | 接管后持仓/订单不一致 | Sandbox 做快照完整性校验；接管前必须对账 |
| 流水线过于严格拖慢开发 | 开发者绕过流程 | 紧急豁免机制；元流水线监控误报率 |
