## 方案

### 1. KlineProvider性能重构

**方案**: 增量返回 + 滑动窗口
- `value_at()`: 仅返回自上次调用以来的新bar（增量），而非全部历史
- `KlineSeriesSnapshot.window`: 截断为回看窗口大小（lookback_bars）
- `UnifiedTimeline.collect_at()`: 维护每个provider的游标，避免重复计算

**文件**: `qrpc_runtime/src/sandbox/timeline.rs`
**预期提升**: 500K-bar回测内存从∞降至~200MB

### 2. 风控系统补全

**方案**: 新增RiskMonitor组件
- `max_daily_loss`: 启动时记录initial_equity，每次cycle检查current_equity
- `max_drawdown_ratio`: 维护peak_equity，计算实时回撤
- `unrealized_pnl`: 在refresh_portfolio_state后更新并纳入风控检查
- 新增`RiskReasonCode::ExceedDailyLoss`和`ExceedDrawdown`

**文件**: `qrpc_runtime/src/risk_checker.rs`, `qrpc_core/src/lib.rs`
**RFC同步**: 对齐RFC-008/009协议定义

### 3. 编译链Graph→QS保留完整配置

**方案**: 扩展convert_graph_json_to_script_module()
- agent节点: 生成`agent("weighted", ...)`或`agent("arbitrage", ...)`语句
- risk节点: 生成`risk.profile("global", max_position=..., ...)`语句
- execution节点: 生成`execution.profile("paper", fee_bps=..., ...)`语句
- 保留rebalance配置

**文件**: `src/graph_quantscript_api.rs`

### 4. PBKDF2凭证迁移

**方案**: PBKDF2-HMAC-SHA256, 600k迭代
- 新凭证使用PBKDF2派生密钥
- 旧凭证(SHA-256)兼容加载，保存时自动升级
- 添加version字段到加密头

### 5. main.rs拆分

**方案**: 按领域拆分
- `src/api/` — compile, runtime, graph, credentials handlers
- `src/state.rs` — AppState + 初始化
- `src/middleware.rs` — auth, rate_limit, cors
- `src/cli.rs` — CLI解析
- `main.rs` — 入口 + 启动逻辑

## 风险

| 风险 | 缓解 |
|------|------|
| KlineProvider重构破坏回测确定性 | 保留旧代码路径作为feature gate，对比验证 |
| PBKDF2迁移中机器密钥变更 | 保留旧SHA-256密钥，仅新凭证用PBKDF2 |
| main.rs拆分引入循环依赖 | 先定义模块接口，再移动代码 |
| 风控补全改变回测结果 | 默认关闭新约束，通过配置启用 |

## 决策纪录

### 决策 1: KlineProvider 性能方案

**选项**:
- A: 增量返回 (value_at仅返回新bar)
- B: 滑动窗口 (value_at返回最近N条bar)
- C: A+B 结合

**选择**: C

**理由**: 增量返回给回测引擎(UnifiedTimeline)减少传输量，滑动窗口给指标计算(evaluator)保证正确性。两者共存是性能最优解。

**影响**: timeline.rs需重构value_at为两个方法：`collect_new_bars()`和`window_at()`。

### 决策 2: 风控系统集成

**选项**:
- A: 扩展现有RiskPolicy/risk_checker
- B: 新建RiskMonitor独立组件

**选择**: B

**理由**: 当前risk_checker已承载12+约束，职责过重。新组件职责分离清晰：RiskMonitor负责实时监控（drawdown/daily_loss/unrealized_pnl），RiskChecker负责单次决策风控。

**影响**: 新增`qrpc_runtime/src/risk_monitor.rs`，Sandbox在每Cycle后调用。

### 决策 3: main.rs拆分粒度

**选项**:
- A: 按领域拆分 (api/state/middleware/cli)
- B: 保持当前结构

**选择**: A

**理由**: main.rs 8879行是编译缓存瓶颈和可维护性障碍。按领域拆分5个模块，每个≤2000行。

**影响**: 
```
src/main.rs  → 入口+启动 (≤500行)
src/api/     → compile_api, runtime_api, graph_api, credential_api
src/state.rs → AppState+初始化
src/middleware.rs → auth, rate_limit, cors
src/cli.rs   → CLI解析
```

### 决策 4: v1.2.0 里程碑边界

**选项**:
- A: 5项目标全部纳入v1.2.0
- B: 先做性能+风控+编译链

**选择**: A

**理由**: 5轮诱错消化后，架构级问题需要集中解决。全部纳入一个MINOR版本周期可以确保系统在进入v1.3.0(功能追加)前有坚实的架构基础。

**影响**: v1.2.0预估工作量较大（5个架构级变更），需要2-3周开发周期。
