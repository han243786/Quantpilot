# v4.15.0 规划方案: 三矩阵完全接管 closeout

> 版本类型: MINOR governance。
> 基准: v4.14.0 治理门禁自动化。
> 执行档位: 重型。
> 主轴: 宣告三矩阵成为默认开发约束体系。

---

## 目标

v4.15.0 的目标是完成新治理方案的项目级接管。完成后，任何开发者、AI 辅助流程或后续里程碑都应先通过三矩阵定位、判档和验证，再进入实现。

---

## 完全接管标准

| 项 | 标准 |
| --- | --- |
| 入口 | README、总索引、当前路线图、全量树均能进入三矩阵 |
| 提案 | 所有非轻量变更都使用提案模板或等效结构 |
| 引导 | 重型变更必须写全量树节点、模块树节点、真实文件、public 方法、测试 |
| 模块树 | active 模块和关键 public 方法具备白箱节点 |
| 规范 | 父子通信硬规则、发布过渡协议、AI 禁止主动过渡均生效 |
| 门禁 | 缺声明、缺坐标、明显索引漂移和未授权横向连接会阻断 closeout |
| 旧文件 | GP、超级规范化和全量树作为历史主干被三矩阵引用，不再绕过三矩阵 |
| closeout | 形成治理 closeout 报告，记录剩余例外和后续维护责任 |

---

## 工作线

| 工作线 | 优先级 | 内容 | 验收 |
| --- | :--: | --- | --- |
| W0 入口顺序收敛 | P0 | 所有常用文档入口优先指向三矩阵 | 开发者不需要知道旧入口才能启动治理流程 |
| W1 旧规则导流 | P0 | GP、超级规范化、全量树添加或保持三矩阵引用关系 | 旧文件不再形成独立绕行路径 |
| W2 模块树 closeout | P0 | 汇总 active 模块覆盖率、public 方法覆盖率和未覆盖例外 | 例外必须有负责人、原因和后续里程碑 |
| W3 门禁 closeout | P0 | 汇总治理 gate 的覆盖范围和无法自动化项 | 无法自动化项转人工检查单 |
| W4 发布过渡演练 | P1 | 用人工样例验证发布过渡协议是否能约束横向连接 | AI 不能主动发起，开发者触发后必须有可撤销证明 |
| W5 治理回归样例 | P1 | 准备轻量、标准、重型三个样例提案 | 三档流程可被新开发者复用 |
| W6 完全落地报告 | P0 | 写治理 closeout 报告 | 明确是否达到完全接管标准 |

---

## 旧文件接管规则

旧文件不删除。接管方式是:

1. 三矩阵成为入口。
2. 旧文件成为被引用主干。
3. 规则冲突时，先按三矩阵判定流程定位冲突，再决定是否修改旧文档。
4. 旧文档中已有强规则继续有效，除非三矩阵里程碑明确迁移或废止。
5. 任何废止都必须走重型提案。

---

## 非目标

- 不把三矩阵变成大型官样文书。
- 不要求轻量修文也写完整重型提案。
- 不以完全接管为名一次性重构全项目代码。
- 不主动进入发布版本过渡。

---

## 验收标准

1. v4.12.0 至 v4.15.0 全部退出条件满足。
2. 三矩阵文档、模块树、里程碑和全量树互相可达。
3. 新提案无法绕过三矩阵影响声明。
4. 重型变更无法绕过引导坐标和模块树节点。
5. 发布过渡协议可执行，且不会被 AI 主动触发。
6. 治理 closeout 报告明确剩余风险、例外和后续维护方式。
