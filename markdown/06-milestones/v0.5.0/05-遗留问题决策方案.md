## P1-2 — JSON 错误消息汉化（残留 Axum 英文文本）

**现状**: `curl -d '' -H "Content-Type: application/json" -X POST /api/runtime/compile` → 返回 Axum 默认英文错误。`json_rejection_middleware` 已拦截 400/422/415，但 Axum 在 extractor 之前就返回了某些错误。

### 方案 A：扩展中间件正文匹配（30 分钟）

在 `json_rejection_middleware` 中不再检查 HTTP 状态码，改为检查响应正文是否以 Axum 的英文错误前缀开头（如 `"Failed to parse"` / `"Expected request"`），匹配则整体替换为中文 JSON。

| 优点 | 缺点 |
|------|------|
| 改动最小，只改一个函数 | 依赖 Axum 内部错误文本格式，升级 Axum 后可能失效 |
| 不改变现有路由/提取器 | 正则匹配英文文本本身不优雅 |

### 方案 B：自定义 Json 提取器（1.5 小时）

创建 `AppJson<T>` 自定义提取器，包装 `axum::Json<T>`，在 `FromRequest` 实现中捕获所有 `JsonRejection` 变体并转为中文错误。所有 handler 签名从 `Json<T>` 改为 `AppJson<T>`。

| 优点 | 缺点 |
|------|------|
| 类型安全，不依赖文本匹配 | 需修改所有 handler 签名（~30 处） |
| Axum 升级不敏感 | 工作量大 |

### 方案 C：接受现状，文档化（5 分钟）

在 `guide-api-reference.md` 中注明"请求必须携带 Content-Type: application/json 头"。不修改代码。

| 优点 | 缺点 |
|------|------|
| 零工作量 | 用户手动调用 API 时可能遇到英文错误 |
| 前端始终正确设置 Content-Type，实际影响小 | |

## P1-4 — 凭证损坏前端引导

**现状**: 凭证文件损坏时 `GET /api/credentials` 返回 503。前端 CredentialPanel 静默显示空列表，用户不知道如何修复。

### 方案 A：前端捕获 503 + 引导文案（20 分钟）

在 CredentialPanel 的 `loadServices` 中检测 503 状态码，显示"凭证文件损坏或密钥不匹配，请运行 `quantpilot credential set` 重新配置"。

| 优点 | 缺点 |
|------|------|
| 改动小，纯前端 | 用户仍需打开终端执行 CLI |
| 即时可用 | |

### 方案 B：新增 `/api/credentials/repair` 端点 + 前端一键修复（2 小时）

新增 API 端点，接受新的凭证字段 → 删除旧 vault 文件 → 重新创建。前端增加"重置凭证"按钮，用户可在 UI 内完成修复。

| 优点 | 缺点 |
|------|------|
| 用户体验最佳，无需离开界面 | 后端工作量较大 |
| 安全：需认证 | 新 API 端点引入攻击面 |

## P1-6 — 21 个前端测试断言修复

**现状**: `npx vitest run` 输出 223/242 通过，19 个测试断言失败。根因：代码汉化后测试期望值未同步（如 `"All 2"` → `"全部 2"`）。

### 方案 A：逐文件修复断言（2 小时）

逐文件读取失败测试，将英文期望值改为对应的中文字符串。之前已修复 2 个文件，剩余约 10 个文件。

| 优点 | 缺点 |
|------|------|
| 彻底解决 | 逐个文件手工修改，耗时 |
| 回归 100% 通过 | 需理解每个测试的业务逻辑 |

### 方案 B：生成 snapshot + 批量更新（30 分钟）

使用 vitest 的 `--update` 模式生成 snapshot，然后审查差异、批量接受正确的中文值。

| 优点 | 缺点 |
|------|------|
| 快速 | snapshot 可能包含非预期的中文值 |
| 适合纯 UI 文本断言 | 需人工审查快照差异 |

## P1-7 — npm audit esbuild 漏洞（公开发布阻塞项）

**现状**: `npm audit --audit-level=moderate` 报告 5 个 moderate 漏洞。根因：vite@6.x → esbuild@0.24.x 存在开发服务器 SSRF 漏洞。修复需要 Vite 大版本升级到 8.x。

### 方案 A：Vite 大版本升级（2 小时）

```
npm install vite@8 vitest@8 @vitest/mocker@8
```

更新 `vite.config.js` 适配新 API → 回归前端测试 + 构建。

| 优点 | 缺点 |
|------|------|
| npm audit 清零 | Vite 8.x 是 breaking change，可能破坏现有配置 |
| 属于"公开发布阻塞项"的正式修复 | | 

### 方案 B：接受风险，维持现状（5 分钟）

README 已记载此为"私有基线可接受的风险"。继续使用 Vite 6.x，公开发布前再升级。

| 优点 | 缺点 |
|------|------|
| 零风险，当前配置稳定 | npm audit 持续报警 |
| 私有基线不受影响 | | 公开发布已阻塞 |

### 方案 C：仅升级 esbuild（30 分钟）

```
npm install esbuild@0.25
npm dedupe
```

只升级漏洞依赖本身，不升级 Vite。

| 优点 | 缺点 |
|------|------|
| 改动最小 | Vite 可能锁定了 esbuild 版本范围 |
| | npm overrides 可能引入兼容性问题 |
