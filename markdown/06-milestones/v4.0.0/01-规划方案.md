# v4.0.0 规划方案 — 状态机化 QuantScript + 开发者学习流水线

> 版本类型: MAJOR | 基准: v3.7.1 稳定归档点 | 终稿确认: 2026-05-23
> 来源: 4.x.x 提案交流；用户已发出“敲定终稿”

---

## 目标

v4.0.0 的目标是把 QuantPilot 从“线性 DAG 策略链”升级为“顶层 DAG + 节点内状态机”的新一代量化表达架构，同时建立服务项目 owner 的开发者学习流水线。

核心变化:

- 顶层仍保留 `data -> intent -> agent -> risk -> execution -> fill` 量化基准 DAG。
- 顶层节点内部升级为标准状态机模板，释放复杂策略表达能力。
- QuantScript 升级为显式支持状态机、事件、缓存、静默、memory 和强类型的领域 DSL。
- 运行时引入事件模型、软静默、缓存优先恢复、Risk Plane、交易模式四象限和执行能力矩阵。
- 新增可迁移的 Developer Learning Pipeline，让项目 owner 在开发中同步理解项目细节。

## 非目标

- 不在 v4.0.0 第一版开放任意层级嵌套状态机。
- 不把 QuantScript 变成通用脚本语言。
- 不允许 QS 直接访问文件、网络、系统 API、密钥或真实下单接口。
- 不绕过 Risk Plane 做真实订单发送。
- 不一次性实现全部券商/交易所高级订单类型。
- 不把个人学习记录推送到 GitHub。
- 不承诺面向所有开发者的通用学习流水线；第一版只服务项目 owner。

## 总体架构

顶层架构继续使用量化基准 DAG:

```text
data -> intent -> agent -> risk -> execution -> fill
```

微观架构升级为:

```text
Top-level DAG node
-> MachineTemplate
-> StateGroup
-> State
-> Event-driven Transition
-> Typed Memory
-> Cache / Silence / Recovery
-> Diagnostic / Replay Evidence
```

系统目标不是让顶层图变复杂，而是把复杂度下沉到可治理、可审计、可回放的状态机模块内部。

## 三大状态机模板

v4.0.0 第一版只采纳三种高表达模板。

| 模板 | 职责 | 可覆盖原链路 |
|------|------|--------------|
| `ObservationMachine` | 数据拉取、聚合、指标计算、市场状态识别、特征与证据输出 | data |
| `DecisionMachine` | 意图生成、代理权重、风控判断、风险状态输出、子意图静默 | intent / agent / risk |
| `ExecutionMachine` | 执行计划、订单语义、路由、成交、费用、滑点、资产账本、模拟撮合 | execution / fill |

原有模块类别不删除。v4.0.0 通过兼容桥把旧链路映射为三大模板的默认实例。

## QuantScript 状态机 DSL

QuantScript v4 状态机面向量化语义，而不是主机系统编程。

第一批语法概念:

```text
machine
state
state_group
memory
on event
transition
when
do
emit
cache
silence
recover
priority
mode
diagnostic
```

语法治理:

- 以声明式 `transition` 为主。
- 受控 `action block` 为辅。
- `action block` 允许读输入、读事件、更新本节点 typed memory、emit 输出、record 诊断。
- `memory` 字段必须提前声明类型、默认值或可空性。
- 其他节点不能直接读写本节点 `memory`，只能读取显式输出。
- 第一版允许扁平 `state + state_group`。
- 任意层级嵌套状态机作为后续潜在优化方向；未来启用时必须向用户展示性能与可审计性警告。

禁止项:

- 任意文件访问。
- 任意网络访问。
- 任意系统 API。
- 直接读取交易密钥。
- 直接真实下单。
- 直接修改其他节点状态或 memory。
- 无限循环、递归、动态 eval。
- 动态生成不可审计的新顶层图结构。

## 事件模型

v4.0.0 采用正式事件模型。

硬规则:

```text
任何 machine 的 transition 都必须由明确事件触发。
没有事件，就没有状态迁移。
```

第一批事件域:

| 事件域 | 事件 |
|--------|------|
| Market | `price_tick`, `bar_opened`, `bar_updated`, `bar_closed`, `orderbook_updated` |
| Runtime | `strategy_started`, `strategy_paused`, `strategy_resumed`, `downstream_pull`, `silence_entered`, `silence_exited`, `cache_returned`, `recovery_started`, `recovery_completed`, `timer` |
| Decision | `intent_emitted`, `weight_changed`, `risk_decision_changed`, `execution_plan_created` |
| Execution | `order_requested`, `order_acknowledged`, `order_rejected`, `order_partially_filled`, `order_filled`, `order_canceled`, `order_expired`, `fee_charged`, `portfolio_changed` |
| Manual | `manual_override`, `manual_cancel`, `mode_changed` |

事件必须带:

```text
event_id
event_type
event_time
source
target_scope
payload
freshness
sequence
replayable
```

调度顺序:

```text
因果顺序 > 安全层级 > DAG 依赖 > 用户自定义优先级 > 稳定兜底排序
```

用户可以定义优先级，但优先级不能覆盖因果、安全、DAG 依赖和确定性回放约束。

## 缓存、软静默与异步恢复

v4.0.0 采用:

```text
soft silence
return last cache + async recover
```

模块静默后:

- 图结构不变。
- 模块保留最近缓存。
- 模块不主动处理普通事件。
- 模块仍响应 `downstream_pull`, `manual_override`, `mode_changed`, `runtime_recovered`。

下游重新拉取时:

```text
downstream_pull
-> cache_returned
-> recovery_started
-> recovery_completed
-> silence_exited
```

缓存输出必须携带:

```text
fresh | stale | recovering | invalid
```

默认安全规则:

```text
stale 数据不得直接扩大真实风险敞口，除非 Risk Plane 显式允许。
```

## Risk Plane

风控逻辑可以用 `DecisionMachine` 表达，但运行时必须有独立高优先级 Risk Plane。

Risk Plane 职责:

- 拦截所有 `ExecutionPlan` 和 `OrderRequest`。
- 维护 `normal`, `reduce_only`, `freeze_open`, `reconcile_only`, `emergency_halt` 等风险模式。
- 对真实下单路径拥有最终否决权。
- 监听成交、拒单、撤单、资产变化、价格异常、连接异常和人工急停。
- 记录所有风险决策证据。

真实下单链路:

```text
ExecutionPlan
-> risk_precheck
-> OrderRequest
-> risk_order_check
-> VenueAdapter
-> FillReport
-> risk_postcheck
-> PortfolioEvent
```

不可关闭底线:

- `LiveActual` 模式下真实订单必须经过 Risk Plane。
- `emergency_halt` 高于所有 QS 逻辑。
- `reduce_only` 只允许降低敞口。
- `freeze_open` 禁止新开仓。
- 交易所连接异常时可自动进入降级或冻结状态。
- 风控决策必须落事件日志和审计证据。

## ExecutionMachine 边界

ExecutionMachine 采用贴近主流券商/交易所的设计，参考 IBKR、富途、Binance、OKX 等主流场所。

v4.0.0 第一批采纳常用能力:

| 能力 | 说明 |
|------|------|
| `Market` | 市价单 |
| `Limit` | 限价单 |
| `PostOnly` / `LimitMaker` | 做 maker，不主动吃单 |
| `StopMarket` | 触发后市价执行 |
| `StopLimit` | 触发后限价执行 |
| `TakeProfitMarket` | 触发止盈后市价执行 |
| `TakeProfitLimit` | 触发止盈后限价执行 |
| `IOC` / `FOK` | 限价单成交约束 |
| `OCO` / `Bracket TP-SL` | 止盈止损组合保护 |
| `TrailingStop` | 跟踪止损 |

第一批必须支持的订单语义修饰符:

- `reduce_only` / `close_only`
- `open_long` / `close_long` / `open_short` / `close_short`
- `one_way` / `hedge` position mode
- `GTC` / `DAY` / `GTD`
- `client_order_id`
- `cancel` / `replace` / `amend`

能力来源硬约束:

| 来源 | 含义 | 规则 |
|------|------|------|
| `provider_native` | 交易所或券商原生支持 | 允许由 VenueAdapter 翻译执行 |
| `runtime_simulated` | QuantPilot 本地模拟或合成 | 必须在事件、日志、UI、报告中显式标记 |
| `unsupported` | 不支持且未模拟 | 编译期或运行前拒绝 |

不得静默降级。若某能力既非原生支持也无本地模拟实现，必须拒绝运行。

## 四种实时交易模式

交易运行模式由两个维度组合:

```text
Account Domain: paper | live
Settlement Authority: provider_actual | local_simulated
```

四种模式:

| 模式 | 说明 |
|------|------|
| `PaperActual` | 使用券商/交易所模拟盘或 sandbox 的真实接口结果 |
| `PaperSimulated` | 接实时行情，本地模拟成交、余额、手续费、资产曲线 |
| `LiveActual` | 真实账户、真实下单、真实成交 |
| `LiveSimulated` | 真实行情和真实账户上下文，不下单，本地模拟如果执行会怎样 |

四种模式共用统一事件:

```text
order_acknowledged
order_rejected
order_partially_filled
order_filled
fee_charged
portfolio_changed
```

差异只体现在事件来源:

```text
provider_actual | local_simulated
```

## 插件治理

插件分三层:

| 插件层 | 说明 |
|--------|------|
| `pure plugin` | 纯计算、指标、特征、无副作用 |
| `runtime plugin` | 本地撮合、费用、滑点、模拟账本 |
| `venue plugin` | 券商/交易所适配器 |

插件必须声明:

```text
name
version
input schema
output schema
deterministic
side_effect
runtime_permission
network_permission
capability matrix
test fixture
```

QS 负责声明使用什么能力，插件负责实现能力本身。真实下单能力只能通过受信 `venue plugin` 和 Risk Plane 执行。

## 性能预算

编译或运行前审计必须生成复杂度指标:

```text
state_count
transition_count
memory_field_count
plugin_call_count
mode_count
stale_dependency_count
estimated_order_paths
event_rate_estimate
```

超预算时警告，严重超预算时拒绝运行。未来若启用嵌套状态机，必须显示状态空间、最大嵌套深度、事件处理路径和回放成本警告。

## Developer Learning Pipeline

v4.0.0 引入开发者学习流水线，第一版服务项目 owner。

核心规范:

- 核心元流水线进入仓库。
- 个人学习记录放入 `markdown/learning/`。
- `markdown/learning/` 明确不推 GitHub。
- 每轮学习包含讲解、文件定位、调用链、状态/副作用、复述、纠偏。
- 学习记录只在用户明确说“记录本轮学习”“生成学习记录”等指令时写入。
- 学习流水线不进入常规强制门禁，但进入大版本 closeout 检查项。

三种学习读取模式:

| 模式 | 范围 |
|------|------|
| 快速地图模式 | 目录、配置、入口、测试、文档索引 |
| 主题追踪模式 | 围绕一个功能追踪相关文件和调用链 |
| 全量学习模式 | 用户明确触发后，显式 UTF-8 全量读取源码和文档 |

## 大版本 closeout 学习检查项

v4.0.0 及后续大版本 closeout 必须增加:

```text
本版本是否引入了需要项目 owner 学习的新核心机制？
```

如果是，必须记录:

- 是否已有零假设解释材料。
- 是否标注涉及文件和调用链。
- 是否说明状态、数据流、副作用和测试保护。
- 是否记录到本地 `markdown/learning/` 或正式元流水线文档。
- 是否需要 owner 复述/校准。

## 验收总闸

v4.0.0 不得 closeout，除非满足:

- V1 QuantScript 保留面没有被静默扩大。
- 新 QS 状态机语义有静态审计和拒绝路径。
- 顶层 DAG 仍可验证无环。
- 所有状态迁移都有事件来源。
- `memory`、cache、silence、recovery 可回放或可解释。
- Risk Plane 无法被真实下单绕过。
- ExecutionMachine 能力来源明确标记为 `provider_native` / `runtime_simulated` / `unsupported`。
- 四种实时模式边界在 UI、API、文档中一致。
- 个人学习记录目录被忽略，不推 GitHub。
- 大版本 closeout 包含学习流水线检查项。
