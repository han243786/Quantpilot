## P1 — GP 合规阻断 (2 项, 预计 6 人日)

### P1-1: 刷新令牌轮换 + 重放检测

**严重度**: P1
**来源**: 遗留规划 (v3.3.0 closeout §六 #1)
**策略**: GP §2.8 (用户认证安全)
**问题**: JWT refresh token 无轮换机制，旧 token 可无限重放刷新，泄漏后攻击者可永久维持会话。
**方案**:
1. `auth/mod.rs` — 刷新 token 时生成新 refresh token，废弃旧 token
2. 存储废弃 token 的 SHA-256 哈希，24h TTL 自动清理
3. 检测旧 token 重放 → 立即撤销全部用户 token + 返回 401
4. 数据库迁移: `refresh_token_hashes` 与 `revoked_token_families` 表
**验收**: 旧 refresh token 重复使用 → 401 + 该用户所有 token 失效
**依赖**: 无
**工时**: 3 人日 (含数据库迁移 + 测试)

### P1-2: 告警 resolve_condition 自动恢复

**严重度**: P1
**来源**: 遗留规划 (v3.3.0 closeout §六 #2)
**策略**: GP §9.3 (告警引擎 — 每条规则必须有恢复条件)
**问题**: AlertRule 缺少 `resolve_condition` 字段，告警只能手动 ack 无法自动恢复，高负载时段运维负担重。
**方案**:
1. `AlertRule` 添加 `resolve_condition: Option<String>` 字段
2. `trigger_alert_check` 改造: 对已触发告警额外评估 resolve_condition
3. 条件满足 → 自动标记 `AlertStatus::Resolved`
4. 10 条默认规则补充恢复表达式 (如 `data_freshness > 300` → `data_freshness < 60`)
**验收**: 模拟 data_freshness 从 0→301 (触发) → 下降到 59 (自动 Resolved)
**依赖**: 无
**工时**: 3 人日 (含默认规则恢复表达式整理 + 测试)

## P2 — 功能完整与质量提升 (10 项, 预计 12~18 人日)

### P2-1: 登录 bcrypt 验证 async 封装

**严重度**: P2
**来源**: GP §10.3 回归检查 (#3)
**策略**: GP §2.8 (用户认证 — 登录响应时限)
**问题**: bcrypt cost=12 的 `verify()` 在 Windows 上 >15s 阻塞 tokio 工作线程，导致 HTTP 超时。
**方案**:
1. 定位登录 handler 中的 `bcrypt::verify()` 调用点
2. 包裹为 `tokio::task::spawn_blocking(move || bcrypt::verify(password, hash)).await?`
3. 添加外层超时: `tokio::time::timeout(Duration::from_secs(30), spawn_blocking(...)).await`
4. 确认 hash 侧已在 `spawn_blocking` 中，无需重复处理
**验收**: `curl -X POST /api/auth/login -d '{"email":"test","password":"test"}'` 响应 < 3s (实测线程池调度延迟 < 50ms + bcrypt 实际计算 ~250ms)
**依赖**: 无
**工时**: 0.5 人日

### P2-2: 51 compiler warnings 清零

**严重度**: P2
**来源**: GP §10.3 回归检查 (#4)
**策略**: GP §5.2 (禁止静默忽略 — 技术债务)
**问题**: 累计 51 条警告: (a) `error_codes.rs` 30+ 未使用错误码常量; (b) 未使用导入 (`Path`、`HashMap` 等); (c) 未使用函数定义; (d) 死代码分支。
**方案**:
1. `error_codes.rs`: 分类处理 — 公共导出常量加 `#[allow(dead_code)]`，内部无用常量直接删除
2. 未使用导入: `cargo fix --bin executor --allow-dirty` 自动消除，残余手工清理
3. 未使用函数: 确无用者删除，测试专用加 `#[cfg(test)]`
4. 全局 `deny(warnings)` 预防回归
**验收**: `cargo clippy --workspace -- -D warnings` → 0 warnings
**依赖**: 建议在 P2-4 之后执行，避免重构引入新警告
**工时**: 1.5 人日 (逐文件排查 + 分类处理)

### P2-3: DEV 模式速率限制豁免

**严重度**: P2
**来源**: GP §10.3 回归检查 (#5)
**策略**: GP §2.7 (实时执行 — DEV 模式绕过安全限制)
**问题**: `QUANTPILOT_DEV=true` 跳过 auth 但未跳过 rate limiter，API 调试时频繁 429。
**方案**:
1. 在 `rate_limiter.rs` 的中间件逻辑中读取 `env::var("QUANTPILOT_DEV")`
2. DEV 模式 → 跳过 `check_rate_limit()` 直接调用 `next.run(req)`
3. 启动日志输出 `[rate_limiter] DEV 模式: 速率限制已豁免`
**验收**: `QUANTPILOT_DEV=true cargo run` → 循环 POST 10 次/秒 均返回 200 (非 429)
**依赖**: 无
**工时**: 0.5 人日

### P2-4: 集成测试 `include!()` 重构

**严重度**: P2
**来源**: GP §10.3 回归检查 (#6)
**策略**: GP §5.1 (测试架构独立于二进制入口)
**问题**: 测试文件 `include!("../../src/main.rs")` 拉取完整二进制代码，`#[tokio::main]` 和二进制项渗入测试上下文，`pub mod` 可见性混乱，编译时间长。
**方案**:
1. 评估方案 A (推荐): 将可测试核心逻辑抽入 `src/lib.rs`，测试通过外部 crate 引用
2. 评估方案 B (轻量): 在 main.rs 中标注 `#[cfg(test)] pub mod test_utils` 导出测试用函数
3. 选择方案后重写集成测试，消除 `include!()` 调用
**验收**: `grep -r 'include!.*main\.rs' tests/` 返回 0; `cargo test --workspace` 编译时间不劣于现状
**依赖**: 建议前置 P2-2 (避免重构中引入新警告)
**工时**: 2~4 人日 (取决于方案 A/B 选择)

### P2-5: 价格涌动 DOM overlay

**严重度**: P2
**来源**: 前端专业级规划
**策略**: 性能优化 — 实时更新避免 React diff 开销
**问题**: StrategyGraphPanel 中 ticker 价格走 React state → 每次更新触发全图子树重渲染。
**方案**:
1. 在 `StrategyGraphPanel.jsx` 中使用 `useRef` 创建 DOM 引用数组
2. 每个节点渲染时挂载绝对定位的 `<span ref={...}>` 用于价格显示
3. 收到 ticker 更新 → 直接 `ref.current.textContent = price` 绕过 React
4. 保持其他 UI 通过 state 管理不变
**验收**: Chrome React Profiler Recording: ticker 更新时 StrategyGraphPanel 无渲染火焰
**依赖**: 无
**工时**: 1 人日

### P2-8: 编译产物缓存

**严重度**: P2
**来源**: 性能规划
**策略**: 性能优化
**问题**: 同图同参数重复触发完整 QS 管道 (语法分析→类型推导→代码生成)，CPU 浪费。
**方案**:
1. 在编译入口处计算 `(graph_hash, compile_options_hash)` — SHA-256 摘要
2. 以哈希为 key 缓存编译产物 (StrategyIR + 诊断 + 签名)
3. 缓存容量 50 条，LRU 淘汰 (使用 `lru::LruCache` 或 HashMap + VecDeque)
4. 命中缓存直接返回，不进入 QS 管道
**验收**: 相同策略图编译 2 次 → 第二次耗时 < 100ms (vs 首次 ~2-5s)
**依赖**: 无
**工时**: 2 人日 (含 LRU 实现 + 缓存命中测试)

### P2-9: OKX testnet 实盘对接

**严重度**: P2
**来源**: 实盘模式规划
**策略**: 功能完整性
**问题**: 当前仅支持 OKX Paper 模拟环境，无法验证真实交易所延迟与 API 兼容性。
**方案**:
1. 新建 `ExchangeConnectorOKX` 结构体，封装 OKX testnet WS (`wss://wspap.okx.com:8443/ws/v5/public`) + REST (`https://www.okx.com/api/v5`)
2. `ws_client.rs`: 根据 `execution_mode == Live` 选择 testnet 连接替代 Paper feed
3. 下单: `POST /api/v5/trade/order` 签名 (OKX API-Key + Passphrase + Timestamp + Sign)
4. 错误处理: testnet 返回的错误映射到统一 `ExchangeError` 枚举
**验收**: Live 模式启动 → WS log 显示 connected to OKX testnet; 模拟下单 → 返回 testnet orderId
**依赖**: 依赖 P2-10 (模式切换 UI)，必须 P2-10 完成后才能切换并连接 testnet
**工时**: 3 人日 (含 OKX API 签名 + WS 协议对接)
