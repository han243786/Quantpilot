# v3.5.0 规划方案 — GP 全合规 + 前端专业级 + P2 质量收口

> 版本类型: MINOR | 基准: v3.4.0 | 目标: GP 18/18 + 前端专业级交付 + GP §10.3 P2 修复
> 来源: 遗留规划 + GP §10.3 回归检查 | 生效日期: 2026-05-20

---

## 目标

- 关闭 GP 合规最后 2 条 (刷新令牌轮换 + resolve_condition 告警恢复)
- 执行端前端 i18n 完整交付 + 4 项前端专业级体验 (价格涌动 DOM 覆盖、订单入场动画、ParamsPanel 热调参 UI、编译产物缓存)
- 实盘模式基础对接 (OKX testnet + Paper/Live 模式切换)
- 修复 GP §10.3 回归检查发现的 4 项 P2: 登录 bcrypt 超时、51 compiler warnings 清零、DEV 模式速率限制豁免、集成测试 include! 重构

## 非目标

- 不新增策略指标
- 不改变协议定义
- 不处理 P3 项 (v3.7.0 消化)

## 方案

### P1 — GP 合规阻断 (2 项)

#### P1-1: 刷新令牌轮换

**严重度**: P1
**来源**: 遗留规划 (GP §2.8 欠账)
**策略**: GP §2.8 (用户认证安全 — refresh token rotation + 重放检测)
**问题**: JWT refresh token 无轮换机制，旧 token 可无限刷新，令牌泄漏后攻击者可永久维持会话。
**方案**:
1. 在 `auth/mod.rs` 中实现 refresh token rotation: 每次刷新时生成新 refresh token 并废弃旧 token
2. 存储已废弃 token 的 SHA-256 哈希 (24 小时 TTL)，用于重放检测
3. 检测到旧 token 被重放后立即撤销该用户全部活跃 token
4. 配套数据库迁移: `refresh_token_hashes` 表 + `revoked_token_families` 表
**验收**: 旧 refresh token 重复使用 → 401 + 全部 token 撤销

#### P1-2: resolve_condition 告警自动恢复

**严重度**: P1
**来源**: 遗留规划 (GP §9.3 欠账)
**策略**: GP §9.3 (每条告警规则必须有恢复条件)
**问题**: AlertRule 缺少 `resolve_condition` 字段，告警触发后只能手动 ack，无法自动恢复。
**方案**:
1. 在 `AlertRule` 结构体添加 `resolve_condition: Option<String>`
2. 修改 `trigger_alert_check`: 对已触发告警额外评估 resolve_condition
3. 条件满足时自动标记 `Resolved`
4. 10 条默认规则补充恢复条件表达式
**验收**: 模拟 data_freshness 恢复 → 告警自动 Resolved

### P2 — 功能完整与质量提升 (10 项)

#### P2-1: 登录 bcrypt 验证超时

**严重度**: P2
**来源**: GP §10.3 回归检查 (#3)
**策略**: GP §2.8 (用户认证 — 登录响应需在合理时限内完成)
**问题**: bcrypt cost=12 的密码验证 (`bcrypt::verify`) 在 Windows 上耗时 >15 秒，远超 HTTP 客户端超时窗口 (通常 10s)。注册端 (`bcrypt::hash`) 因在异步上下文中执行 `spawn_blocking` 正常，但验证端直接阻塞 tokio 工作线程。
**方案**:
1. 在登录 handler 中将 `bcrypt::verify` 调用包裹为 `tokio::task::spawn_blocking(move || bcrypt::verify(...)).await`
2. 添加合理的超时封装 (如 `tokio::time::timeout(Duration::from_secs(30), ...)`)
3. 确认 hash 端 (已使用 `spawn_blocking`) 无需修改
**验收**: `curl -X POST /api/auth/login -d '{"email":"...","password":"..."}'` 响应 < 3s (bcrypt 实际耗时 ~250ms 异步转移后不阻塞)

#### P2-2: 51 compiler warnings 清零

**严重度**: P2
**来源**: GP §10.3 回归检查 (#4)
**策略**: GP §5.2 (禁止静默忽略 — 编译器警告亦是技术债务)
**问题**: 全 workspace 累计 51 条编译器警告，涵盖: (a) `ERR_BAD_REQUEST` ~ `ERR_PORT_RESERVED` 等 30+ 未使用常量声在 `error_codes.rs`; (b) 未使用导入如 `Path`、`HashMap` 散落在 `credential_vault.rs`、`live_execution.rs` 等文件中; (c) 未使用函数定义; (d) 死代码分支。
**方案**:
1. 对 `error_codes.rs`: 批量删除或 `#[allow(dead_code)]` 标注 GP 保留但未使用的错误码常量。优先删除确无用者，保留可能被外部引用的公共导出
2. 对未使用导入: 逐文件运行 `cargo fix --bin executor --allow-dirty` 自动清理，剩余手工检查
3. 对未使用函数: 检查是否真未调用，确无用则删除，计划外暴露则添加 `#[allow(dead_code)]` 或 `#[cfg(test)]`
4. 最终目标: `cargo clippy -- -D warnings` 零 warning 通过
**验收**: `cargo clippy --workspace -- -D warnings` → 0 warnings (允许对 GP 保留但未使用的常量使用 `#[allow(dead_code)]`)

#### P2-3: DEV 模式速率限制豁免

**严重度**: P2
**来源**: GP §10.3 回归检查 (#5)
**策略**: GP §2.7 (实时执行 — DEV 模式应完全绕过安全限制以便调试)
**问题**: `QUANTPILOT_DEV=true` 环境变量已用于跳过 auth 中间件，但速率限制器 (`rate_limiter`) 仍对所有请求施加 200ms 间隔限制。开发者在 DEV 模式下进行快速 API 调试时频繁遭遇 429 Too Many Requests。
**方案**:
1. 在 `rate_limiter.rs` 或速率限制中间件中检查 `QUANTPILOT_DEV` 环境变量
2. DEV 模式下跳过速率限制检查，直接放行
3. 保持 DEV 模式日志输出以便开发者感知当前处于无限制状态
**验收**: `QUANTPILOT_DEV=true cargo run` → 每秒 10 次 curl POST 无 429

#### P2-4: 集成测试 `include!()` 重构

**严重度**: P2
**来源**: GP §10.3 回归检查 (#6)
**策略**: GP §5.1 (测试架构应独立于二进制入口)
**问题**: 集成测试文件使用 `include!("../../src/main.rs")` 拉取整个二进制源码，导致 `#[tokio::main]` 宏展开和二进制专用项进入测试编译单元。这不仅拉长编译时间，还造成 `pub mod` 项的可见性混乱 — 原本在二进制 crate 中公开的模块在测试上下文中语义不一致。
**方案**:
1. 将需要测试的核心逻辑从 `src/main.rs` 抽取到独立的 library crate (如 `executor-lib`) 或 `src/lib.rs`
2. 集成测试改为通过 crate 公开 API 测试，而非 `include!()` 拉取整个 main.rs
3. 如果抽取库 crate 成本过高，至少将测试用公共模块提取为 `src/test_utils.rs` 并用 `#[cfg(test)]` 条件编译
**验收**: 集成测试不再使用 `include!("../../src/main.rs")`，`cargo test --workspace` 编译时间不劣于当前且语义清晰

#### P2-5: 价格涌动效果 (DOM overlay)

**严重度**: P2
**来源**: 前端专业级规划
**策略**: 用户体验 — 实时价格更新不触发 React 重渲染
**问题**: 策略图节点上的 ticker 价格通过 React state 更新，每 ticker 触发全图子树重渲染，性能开销大。
**方案**:
1. `StrategyGraphPanel`: 使用 `useRef` 持有 DOM 节点引用
2. 每 ticker 更新时直接操作 DOM overlay (绝对定位 `<span>`) 修改 `textContent`
3. 完全绕过 React diff 机制，更新成本降至 O(1) DOM 写
**验收**: ticker 更新时 Chrome React Profiler 不显示 StrategyGraphPanel 重渲染

#### P2-6: 订单动画 (入场 + 成交反馈)

**严重度**: P2
**来源**: 前端专业级规划
**策略**: 用户体验 — 新订单与成交状态可视反馈
**问题**: OrderPanel 中订单列表更新无动画，新订单突兀出现，成交状态变化不可感知。
**方案**:
1. 新订单入场: CSS `@keyframes slideIn` — 从右侧滑入，持续 300ms
2. 订单成交: CSS `@keyframes flash` — 背景闪烁绿色 (rgba(0,200,0,0.15))，持续 500ms
3. 使用 React `transition-group` 或纯 CSS class 切换实现
**验收**: 模拟新订单创建 → OrderPanel 显示 slide-in 动画; 订单 fill → 背景绿色闪烁

#### P2-7: ParamsPanel 热调参 UI 面板

**严重度**: P2
**来源**: 前端专业级规划
**策略**: 功能完整性 — 部署策略后需支持运行时参数调整
**问题**: 后端已实现热调参 GET/POST 接口以及 pending→commit→rollback 机制，但前端缺少可视化的 ParamsPanel 面板。
**方案**:
1. 创建 `StrategyParamsPanel.jsx` 组件: 从 `GET /strategies/{id}/params` 加载参数 schema
2. 参数按类型渲染: 数值滑块 (slider)、枚举下拉 (select)、布尔开关 (toggle)
3. 提交后显示 pending 状态条，支持 commit/rollback
**验收**: 部署含参数策略 → 面板展示可调参数 → 修改数值 → POST 提交 → 状态变 pending → commit 生效

#### P2-8: 编译产物缓存

**严重度**: P2
**来源**: 性能规划
**策略**: 性能优化 — 同图同参数跳过重复编译
**问题**: 用户反复编辑同一策略图并编译时，QS 管道 (语法分析→类型推导→代码生成) 每次完全重跑，相同输入产生相同输出却浪费 CPU。
**方案**:
1. 以 `(graph_hash, compile_options_hash)` 为 key 缓存编译产物
2. 编译前计算哈希，缓存命中则直接返回上次结果
3. 缓存上限 50 条，LRU 淘汰
**验收**: 相同策略图连续编译 2 次 → 第二次 < 100ms

#### P2-9: OKX testnet 实盘对接

**严重度**: P2
**来源**: 实盘模式规划
**策略**: 功能完整性 — 从 Paper 模拟切换到真实交易所 testnet
**问题**: 当前所有行情和下单均使用 OKX Paper 模拟环境，无法验证真实交易所延迟和 API 兼容性。
**方案**:
1. 新增 `ExchangeConnectorOKX` 结构体: WS 连接 OKX testnet (`wss://wspap.okx.com:8443/ws/v5/public`)
2. 替换 ticker feed: `ws_client.rs` 根据 `execution_mode` 选择 Paper 或 testnet 连接
3. 下单路径: 从本地模拟改为通过 OKX REST API (`https://www.okx.com/api/v5/trade/order`)
**验收**: 切换至 Live 模式 → 执行端 WS 连接 OKX testnet 并接收真实 ticker; 模拟下单返回 testnet 订单 ID

#### P2-10: Paper/Live 模式切换

**严重度**: P2
**来源**: 实盘模式规划
**策略**: 功能完整性 — 执行端需直观切换运行模式
**问题**: 执行端只有一个默认 Paper 模式，用户无法在 UI 中切换到实盘模式。
**方案**:
1. `ExecutorTopBar.jsx`: 新增 Paper/Live 切换按钮 (拨动开关样式)
2. 切换时弹出确认对话框: "切换到实盘模式将向真实交易所下单，确认继续？"
3. 状态同步: 模式变更通过 SSE 广播到所有标签页
4. 模式变更后自动重启 WS 连接 (切换到对应交易所 feed)
**验收**: 点击 Live → 确认弹窗 → 确认 → 顶部标签变 "Live" + 警报色; WS 连接切换到 testnet
