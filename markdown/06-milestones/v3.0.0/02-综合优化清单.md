## Phase 1: 执行端后端骨架 (8 任务)

### 1.1 执行端 main.rs
**目标**: 独立 binary, Axum server, 端口 3001
**方案**:
- 新建 `src-executor/` 目录
- `main.rs`: tokio main, 创建执行端 AppState, 注册路由, 绑定 127.0.0.1:3001
- `Cargo.toml`: 新增 `[[bin]] name = "executor" path = "src-executor/main.rs"`
**验收**: `cargo run --bin executor` 输出 "listening on 127.0.0.1:3001"

### 1.2 执行端状态管理
**目标**: 策略注册表 + WS 连接池 + 环形缓冲区
**方案**: `executor_state.rs`:
```rust
pub struct ExecutorState {
    pub strategies: RwLock<BTreeMap<String, ActiveStrategy>>,
    pub ws_pool: WebSocketPool,
    pub kline_buffers: RwLock<BTreeMap<Symbol, RingBuffer<KlineBar>>>,
    pub session_key: OnceLock<SessionKey>,
}
```
**验收**: `cargo check -p quantpilot --bin executor`

### 1.3 WebSocket 客户端
**目标**: 直连 Binance/OKX, 自动重连, 心跳
**方案**:
- `ws_client.rs`: 使用 `tokio-tungstenite` (或 `async-tungstenite`)
- Binance WS: `wss://stream.binance.com:9443/ws/{streams}`
- OKX WS: `wss://ws.okx.com:8443/ws/v5/public`
- 订阅: ticker + kline_1m + trade
- 自动重连: 指数退避 1s/2s/4s/.../max 30s
**验收**: 启动后日志显示 "WS connected to binance, subscribed BTCUSDT@ticker"

### 1.4 K线环形缓冲区
**目标**: 每标的最近 1000 条 K 线, OHLC 聚合, 一字线生成
**方案**:
- `kline_buffer.rs`: 固定大小环形缓冲区
- ticker 更新→检查当前分钟→写入/更新 OHLC
- 无交易时生成一字线 (O=H=L=C)
**验收**: 运行 1 分钟后, 缓冲区包含 ≥1 条完整 OHLC

### 1.5 策略迁移端点
**目标**: 接收/验证/加载策略包
**方案**:
- `POST /api/executor/strategies`: 接收加密策略包
- 解密→验证 SHA-256 签名→反序列化→注册到 strategies map
- 返回 strategy_id + 加载状态
**验收**: 测试端发送策略包→执行端返回 strategy_id

### 1.6 热调参端点
**目标**: GET/POST params + rollback
**方案**:
- `GET /api/executor/{id}/params`: 返回当前参数
- `POST /api/executor/{id}/params`: 安全窗口检查→写入 pending→返回
- `POST /api/executor/{id}/params/rollback`: 回滚到上一版本
**验收**: POST params→30s 观察窗口→自动回滚(如果指标偏离)

### 1.7 进程间加密
**目标**: 临时密钥生成 + AES-256-GCM + HMAC
**方案**:
- 启动时生成 32 字节随机 session_key
- 写入共享内存区域 (Windows: 命名共享内存, 权限仅当前用户)
- 测试端读取后立即清除共享内存
- 所有请求: body AES-256-GCM(nonce + ciphertext) + HMAC-SHA256(body)
**验收**: 抓包验证 API 请求体不可读

### 1.8 Cargo.toml 配置
**目标**: 新增 executor binary 和依赖
**方案**:
```toml
[[bin]]
name = "executor"
path = "src-executor/main.rs"

# 新依赖
tokio-tungstenite = "0.24"
lightweight-charts = (前端 npm)
```
**验收**: `cargo build --bin executor`

## Phase 2: 实时执行引擎 (5 任务)

### 2.1 实时策略运行器
**目标**: 加载 Core IR → 启动 WS 订阅 → 逐周期执行
**方案**: `live_runner.rs`:
- 从 ActiveStrategy 加载 Core IR
- 创建 RuntimeCoordinator (复用 qrpc_runtime)
- 每 ticker 到达→更新环形缓冲区→调用 run_cycle
- 区分 slow_cycle (K线闭合) 和 fast_cycle (ticker)
**验收**: 加载双均线策略→WS ticker→1分钟后产生 Buy 信号

### 2.2 实时指标热计算
**目标**: WS 数据到达→增量更新指标→触发检测
**方案**: `indicator_compute.rs`:
- 复用 core_ir_evaluator 的 18 个指标
- 增量计算: 仅重算最后一根 K 线
- 缓存中间结果 (RSI avg_gain/avg_loss, EMA 前值)
**验收**: RSI 值随每个 ticker 实时更新

### 2.3 触发引擎
**目标**: 信号变化→生成涌动事件→推送前端
**方案**: `trigger_engine.rs`:
- 比较前后 cycle 的 IntentSignal
- 新信号→TriggerEvent { type, strength, node_id, ts }
- SSE 推送前端: 策略图对应节点产生脉冲动画
**验收**: RSI<30 触发 Buy→前端节点闪烁+脉冲动画

### 2.4 订单管理
**目标**: 提交/取消/查询, 状态机, 成交反馈
**方案**: `order_manager.rs`:
- 复用 live_execution.rs 的 OKX API 签名逻辑
- 状态机: Created→Submitted→Accepted→PartiallyFilled→Filled
- 成交反馈: →SSE 推送前端更新挂单面板
**验收**: 触发信号→自动下单→成交→前端挂单面板显示已成交

### 2.5 多策略并发调度
**目标**: 独立 RuntimeCoordinator 实例, 资源隔离
**方案**: `multi_strategy.rs`:
- 每标签页对应一个 ExecutorHandle (包含 RuntimeCoordinator + WS client + buffer)
- tokio spawn 独立 task
- 资源监控: CPU/内存/WS连接数
**验收**: 3个策略同时运行→各自独立产生信号/下单

## Phase 5: 安全加固 (3 任务)

### 5.1 执行端独立凭证库
**目标**: 最高加密规范, 执行端独立密钥文件
**方案**: `credential_vault_v2.rs`:
- 独立的 `.executor-credentials` 文件
- 独立的 `.executor-machine-key` 文件
- PBKDF2 1,000,000 轮 (vs 测试端 600,000)
- AES-256-GCM + AAD 绑定文件路径
**验收**: 执行端凭证与测试端无法互相解密

### 5.2 API 守卫
**目标**: 请求解密, HMAC 验证, 时间窗口防重放
**方案**: `api_guard.rs`:
- Axum middleware: 拦截所有 /api/executor/* 请求
- 解密 body (AES-256-GCM)
- 验证 HMAC-SHA256 签名
- 检查 timestamp ±5s (防重放)
**验收**: 修改请求 body → 401 Unauthorized

### 5.3 不可删除审计日志
**目标**: 所有操作记录, 调参历史, 策略迁移记录
**方案**: `audit_log.rs`:
- 追加写入 `storage/.executor-audit.log`
- JSON Lines 格式, 每行一条记录
- 含 timestamp, operation, actor, strategy_id
**验收**: 执行操作→cat audit.log→记录存在
