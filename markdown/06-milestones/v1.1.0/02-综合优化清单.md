## S0 — 阻断发布（当前里程碑必须完成）

### S0-1 统一时间轴回放引擎

**严重度**: 阻断
**来源**: 方案 C1
**策略**: GP §1.1（QS 唯一路径）、GP §5.3（零 stub）
**依赖**: 无（可并行启动）
**被依赖**: S0-2, S0-3, S0-5
**问题**: `ReplayDataModule` 按 `min()` bar count 步进，不同时间框架/不同起始时间的数据源无法正确对齐。多标的策略回测结果不可信。
**方案**:
1. 新建 `qrpc_runtime/src/sandbox/timeline.rs` + `qrpc_runtime/src/sandbox/replay.rs`
2. sandbox 模块目录重组：`sandbox/mod.rs`（Sandbox trait）+ `sandbox/replay.rs`（UnifiedTimeline + ReplayDataModule）+ `sandbox/timeline.rs`（TimelineDataProvider trait）
3. 实现 `UnifiedTimeline` 结构体：收集所有数据源时间戳排序去重 → 构建 asof-join providers
4. 实现慢/快周期触发分离：慢周期仅在 K 线 `close_time_ms` 触发，快周期每个报价时间点触发
5. `FastBacktestSandbox::run_backtest()` 使用 `UnifiedTimeline` 替代按 index 遍历
**验收**:
```bash
# 多时间框架回测 step_count 正确（不被 min() 截断）
cargo test --test api_backtest unified_timeline_multi_timeframe

# 单标的回测无回归
cargo test fast_backtest_replay_produces_equity_curve_and_sessions
```

### S0-2 多标的信号路由

**严重度**: 阻断
**来源**: 方案 C2
**策略**: GP §1.2（跨三层验证）、GP §5.2（禁止静默忽略参数）
**依赖**: S0-1（时间轴变化后数据到达方式改变，需在统一时间轴上下文中验证多标的决策）
**被依赖**: S0-3（多标的 trade_ledger 数据正确性是指标计算的前提）
**问题**: `WeightedSignals` agent 将所有标的信号混为一个 net score，选第一个 symbol。ETH 信号被静默吞掉。
**方案**:
1. `build_weighted_agent_decision()` 改为 `build_weighted_agent_decisions()`，返回 `Vec<AgentDecision>`
2. 信号按 `(Exchange, Symbol)` 分组
3. 每组独立计算 weighted score + 生成 decision
4. `merge.rs` 确保多 decision 正确合并（单策略时跳过 merge）
5. `risk_checker.rs` 确保逐 decision 检查逻辑不变
**验收**:
```bash
# BTC+ETH 双标的回测各产生独立 decision
cargo test --test api_backtest multi_symbol_weighted_signals

# agent_module 的现有测试全部通过
cargo test agent_module
```

### S0-3 BacktestSummary 字段扩展 + 指标计算器

**严重度**: 阻断
**来源**: 方案 A1/A2/A3
**策略**: GP §1.2（跨三层）、GP §2.3（新 indicator 需测试）、GP §5.1（禁止硬编码）
**依赖**: S0-1（需统一时间轴产生的 session/equity_curve 为输入）、S0-2（需多标的 trade_ledger 逐笔 PnL 参与 profit_factor 等计算）
**被依赖**: 无（S0 最后一步）
**问题**: 当前 10 个字段中 3 个始终为 0（直接删除），缺少业界标准风险调整收益指标。
**方案**:
1. `qrpc_core/src/lib.rs` — `BacktestSummary` 分组子结构体：`BacktestRiskAdjusted` / `BacktestTradeAnalysis` / `BacktestDrawdownAnalysis` / `Option<BacktestBenchmarkComparison>`
2. 新建 `qrpc_runtime/src/backtest_metrics.rs` — 实现 `BacktestMetrics::compute()`
3. `sandbox/mod.rs` `run_backtest()` 末尾调用 `BacktestMetrics::compute()`
4. 新建 `.qs` 场景文件验证新指标 @assert
**验收**:
```bash
# 新指标全部填充非零值（除基准相关在无基准时为 None）
cargo test backtest_metrics

# 旧回测数据加载不 panic（废弃字段由 serde 忽略）
cargo test --test api_backtest load_v1_0_7_backtest

# .qs 场景中可 @assert 新指标
cargo test --test quantscript_real_strategy_authoring sharpe_assert
```

### S0-4 成交模型 — 买卖价差

**严重度**: 阻断
**来源**: 方案 B1/B2
**策略**: GP §5.1（禁止硬编码）、GP §5.3（零 stub）
**依赖**: 无（仅改 fill_engine.rs + 新增 slippage.rs，可并行启动）
**被依赖**: 无
**问题**: 当前 Market 订单以 mid price 成交，完全忽略买卖价差成本。在流动性差的市场，bid-ask spread 可能高达数十 bps，忽略导致回测收益系统性高估。
**方案**:
1. `FillEngine` 中 `build_fill_report()` → `compute_fill_price()` 使用 bid/ask 基准价
2. 当报价数据可用时（`NormalizedMarketData::Quote`）：买用 ask、卖用 bid
3. 当仅 K 线数据时：波动率缩放价差估算（`SpreadEstimateSource::VolatilityBased`），而非粗暴用 low/high
4. `DataQualitySnapshot` 新增 `spread_estimation_method` 字段，透明标注价差来源
**验收**:
```bash
# 用真实 Quote 数据的回测 fill_price 基于 bid/ask
cargo test fill_engine bid_ask_pricing

# 无 Quote 数据时 fallback 到波动率缩放估算
cargo test fill_engine spread_estimation_from_volatility

# 价差估算函数可独立验证
cargo test slippage_estimate_spread
```

### S0-5 基准权益曲线生成与 Alpha/Beta 计算

**严重度**: 阻断
**来源**: 方案 A4
**策略**: GP §1.2（跨三层验证）
**依赖**: S0-1（基准价格序列对齐统一时间轴，确定基准买入时点）
**被依赖**: 无
**问题**: 无基准对比的回测报告无法区分"策略优秀"和"市场单边上涨"。
**方案**:
1. `sandbox/replay.rs` 统一时间轴构建时输出基准价格序列
2. 基准 = 等权重持有策略交易的所有标的（initial_cash 按标的数均分）
3. `BacktestMetrics::compute()` 中计算 `BacktestBenchmarkComparison`
**验收**:
```bash
cargo test benchmark_equity_curve_generation
cargo test backtest_metrics_alpha_beta
```

**严重度**: 高

**验收**:

## P2 — 下个版本（两个里程碑内完成）

### P2-1 数据覆盖完整性报告

**严重度**: 中
**来源**: 缺口 6
**策略**: GP §7.1（数据生命周期声明）
**问题**: 回测启动前不校验各数据源覆盖范围是否满足回测周期要求。
**方案**:
1. `data_module.rs` 新增 `build_coverage_report()`
2. 回测启动前输出 `DataCoverageReport`，标注数据缺口告警
3. 报告作为 `BacktestOutput` 的附加 artifact 持久化
**验收**:
```bash
cargo test data_coverage_report
```

### P2-2 VaR / CVaR 计算

**严重度**: 中
**来源**: 方案 A（加分项）
**策略**: 业界标准风险管理指标
**问题**: 回测报告中缺少 VaR 和 CVaR 等极端风险度量。
**方案**:
1. `backtest_metrics.rs` 新增 `var_95`、`cvar_95` 计算
2. `BacktestSummary` 新增对应字段
3. 前端指标面板展示
**验收**:
```bash
cargo test backtest_metrics_var_cvar
```

### P2-3 收益率分布统计（偏度/峰度）

**严重度**: 中
**来源**: 方案 A（加分项）
**策略**: 评估策略收益的肥尾风险
**问题**: 均值-方差框架假设正态分布，加密货币收益率分布常呈肥尾和偏斜。
**方案**:
1. `backtest_metrics.rs` 新增 `skewness`、`kurtosis` 字段
2. 前端不强制展示（避免信息过载），可在"展开详情"中查看
**验收**:
```bash
cargo test backtest_metrics_skewness_kurtosis
```

### P2-4 月/季收益率分解

**严重度**: 中
**来源**: 需求分析
**策略**: 评估策略在不同时间段的一致性
**问题**: 仅总收益率无法体现策略在不同月份/季度的表现差异。
**方案**:
1. `BacktestOutput` 新增 `period_returns: Vec<PeriodReturn>`（月/季/年维度）
2. 前端新增 `MonthlyReturnsHeatmap` 组件
3. 复用到 `BacktestDetailPage` 和 `BacktestComparePage`
**验收**:
```bash
cargo test backtest_period_returns
cd frontend && npm run build
# 手动验证: 回测详情页可见月度收益热力图
```

### P2-5 回测缓存与增量计算

**严重度**: 中
**来源**: 性能优化
**策略**: 大规模回测（50 万 bar）计算指标不应每次重新计算
**问题**: 指标计算遍历全部 session 和 trade ledger，重复加载时浪费 CPU。
**方案**:
1. `BacktestSummary` 计算一次后写入 `metrics.json` artifact
2. 后续 GET 请求直接从 artifact 反序列化，不重新计算
3. API 响应增加 `computed_at` 字段表示指标计算时间
**验收**:
```bash
cargo test backtest_metrics_cache_hit
```
