# v4.13.0 规划方案: 模块树白箱扩面

> 版本类型: MINOR governance。
> 基准: v4.12.0 三矩阵治理入口启用。
> 执行档位: 重型。
> 主轴: 把模块树从种子模板扩展为可支持重大重构的白箱网络。

---

## 目标

v4.13.0 的目标是让重型变更不再只依赖文件路径判断，而是能定位到真实模块、父模块、关键 public 方法、输入输出和回归保护。

模块树不是文件树。它描述的是逻辑模块网络:

```text
root -> 大模块 -> 子模块 -> public 方法 / 接口 / 状态边界
```

任何子模块默认只通过父模块、登记接口、事件、adapter 或契约层对外沟通。

## 工作线

| 工作线 | 优先级 | 内容 | 验收 |
| --- | :--: | --- | --- |
| W0 模块分类 | P0 | 定义 `system`、`backend`、`frontend`、`executor`、`contracts`、`docs` 六类父模块 | 每类都有父模块职责和禁止事项 |
| W1 后端白箱 | P0 | 登记 router、capability、runtime、strategy config、AI proposal、persistence 等模块 | 每个模块有真实文件、输入输出、public 方法、测试 |
| W2 前端白箱 | P0 | 登记 workspace、capability projection、strategy config cockpit、runtime panels 等模块 | 页面不直接拥有 capability 真源 |
| W3 执行端白箱 | P0 | 登记 runner、preflight、credential vault、migration API、audit log 等模块 | 执行端启动边界和风险边界可追踪 |
| W4 文档治理白箱 | P1 | 登记三矩阵、全量树、里程碑、支持矩阵、GP 的关系 | 文档变更能引用治理节点 |
| W5 public 方法清单 | P0 | 盘点关键 public 方法、HTTP 路由、React 入口组件和导出工具 | 未登记 public 方法不能作为重型变更事实依据 |
| W6 模块化重构通道 | P0 | 固化“新模块化版本先并行、再适配、后退役”的步骤 | 不允许抽离和删除旧实现混在一次变更 |
| W7 回归保护矩阵 | P0 | 每个白箱节点登记最小测试或人工检查 | 重型变更能直接引用节点级回归 |

## 模块化重构规则

当原模块复杂纠缠、难以原地解耦时，可以建立新的模块化版本:

1. 新模块必须有父模块和模块树 ID。
2. 新模块必须声明输入、输出和状态归属。
3. 旧实现保留到新模块适配系统接口并跑通。
4. 新旧并存期间必须写兼容桥、入口选择和回退策略。
5. 删除旧实现必须另开重型提案。

这条通道适用于 v4 模块化状态机交易逻辑，也适用于前端工作区、后端能力聚合和执行端 runner 拆分。

---

## 非目标

- 不主动提出发布版本过渡。
- 不新增子模块横向连接。
- 不以性能优化为理由绕过父模块。
- 不在没有真实文件和测试证据时登记虚构模块。

---

## 验收标准

1. `module-tree.md` 覆盖主要 active 模块和关键 public 方法。
2. 每个新增白箱节点都能落到真实文件。
3. 每个重型变更都能引用至少一个模块树节点。
4. 全量树和模块树的职责边界清晰: 全量树回答“有什么”，模块树回答“怎么通信”。
5. 模块化重构有并行版本、适配、验证、退役四阶段规则。
