# v3.7.2 规划方案 — Closeout 真实性与安全回退收口

> 版本类型: PATCH | 基准: v3.7.1 | 日期: 2026-05-24
> 目标: 修复全量检查发现的“现状与预期效果不一致”问题，恢复 closeout 真实可信状态
> 执行状态: 推荐方案已采纳并完成落地；最终 23 项 closeout 已通过

---

## 一、背景

2026-05-24 全量检查显示，仓库源码已推送且 git 工作区干净，但当前文档声明、closeout 脚本和实测结果之间出现偏差：

- `tools/run-closeout-gates.bat` 已从 22 项升级为 23 项门禁，但活跃文档仍多处保留旧 closeout 口径。
- 完整 closeout 实测失败，阻断点为前端 E2E safe fallback 用例。
- 前端 Vitest、UTF-8 文件数量、E2E 结果等统计已随代码演进变化，活跃文档仍保留旧值。
- `cargo clippy --workspace --all-targets` 退出码通过，但仍输出 warning；文档需要明确这是“错误阻断”还是“warning-free 阻断”。
- 全量测试期间产生 `qrpc_session/storage/.executor-session-key` 临时文件，测试隔离仍有副作用风险。

本版本不引入新功能，只修复质量门禁和发布口径。

## 二、目标

1. 修复 safe fallback E2E 阻断，确保完整 closeout 可重新通过。
2. 让活跃文档只声明实测成立的状态，不再保留旧 closeout 21/21、旧测试数量或旧 warning 预算。
3. 明确 clippy 门禁语义，避免“通过但 warning 很多”被误读为 warning-free。
4. 消除或封装测试副作用，确保全量检查后 git 工作区保持干净。
5. 建立 v3.7.2 验收标准，作为 v3.7.1 稳定线修正后的归档补丁。

## 三、非目标

- 不新增 QuantScript、回测、交易、插件、AI 或 UI 平台能力。
- 不改变 `/api/capabilities` 的后端真源契约。
- 不修改 v4.0.0 状态机规划边界。
- 不把历史归档文档全部重写为当前状态；历史报告只在明显误导当前发布状态时修正。
- 不在未决策前放宽 safe fallback 的风险操作能力。

## 五、推荐优化方案

### 方案 A — 保持 strict safe fallback，修正 E2E 预期

在无缓存且 capability 服务不可用时，workspace surface 仍可见但不可点击，风险操作保持禁用。E2E 不再尝试点击禁用的 `workspace-tab-research`，而是在默认 dashboard 上验证：

- safe fallback banner 可见。
- 编译、启动模拟、运行回测、导出运行配置禁用。
- workspace tabs 明确禁用并带原因。
- 未出现未声明 API 请求。

这是当前推荐方案。它保持“能力真源不可用时不暴露虚假能力”的安全约束。

### 方案 B — 允许 readonly tab navigation，继续锁定风险动作

将 safe fallback 下的 workspace surfaces 改为可点击但只读，用户可进入研究/源码/监控页查看空态或只读材料，风险动作仍禁用。

该方案用户体验更顺滑，但需要重新定义 `workspace.surface.*` 的 `enabled` 含义：它将不再等价于“可进入”，而更接近“可执行”。这会扩大前端状态语义，需要补充更多测试。

### 推荐

采用方案 A。原因是 v3.7.2 是稳定线补丁，不应在修复 closeout 时扩大 safe fallback 的交互语义。
