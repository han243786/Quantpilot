# v4.11.0 策略配置系统端到端设计

> 配套里程碑：`01-规划方案.md`
> 设计主轴：v4 策略配置系统是一等功能切面
> 状态：设计约束稿，后续实现必须逐项回填证据

---

## 1. 设计目标

v4.11.0 要把现有分散能力组合成一条可解释的策略配置链路：

```text
策略图 / QuantScript / v4 QS handoff
  -> v4 strategy config artifact
  -> preflight
  -> PaperSimulated / backtest / PaperActual demo boundary
  -> evidence anchors
  -> AI proposal binding
  -> approval / rollback
  -> snapshot digest
```

成功状态不是“多一个页面”，而是用户能回答：

- 当前策略配置完整吗？
- 哪些配置域已经可运行，哪些只是可文档化，哪些后续再做，哪些明确不做？
- 为什么当前只能 PaperSimulated，或只能 PaperActual demo，而不是实盘？
- 本次运行、回测、AI 提案和快照是否来自同一个配置契约？
- 如果配置变更了，证据、风险和执行边界如何变化？

## 2. 设计指标追踪

| 指标 | 前端设计 | 后端设计 | 执行端设计 | 文档/门禁设计 |
| --- | --- | --- | --- | --- |
| `SC-1` 配置域完整 | 策略配置台按配置域展示状态 | 后端聚合 domain status | 执行端展示部署相关域 | 支持矩阵和功能切面同步 |
| `SC-2` 契约可导出 | 导出按钮只调用后端 artifact | 生成 canonical artifact + digest | 可接收 preflight 摘要 | OpenAPI 和测试 fixture 登记 |
| `SC-3` 能力不漂移 | UI 只投影 capability | 后端 capability 为真源 | 不自行推断能力 | capability stack 门禁 |
| `SC-4` 运行前可解释 | preflight 摘要和禁用原因 | fail-closed validation | 启动前核验 | 文案禁用 live 描述 demo |
| `SC-5` 证据闭环 | evidence anchors 可点击 | run/backtest/proposal/snapshot 锚点 | runtime evidence 绑定 | closeout 回填 |
| `SC-6` 用户不误解 | 不出现账号/搜索/实盘 CTA | unsupported 不进入 planned | 不显示实盘暗示 | 文档路径与 unsupported 审计 |

## 3. 核心契约

### 3.1 `StrategyConfigArtifactV1`

```json
{
  "schema_version": "quantpilot/v4-strategy-config-artifact/v1",
  "artifact_id": "local-generated-id",
  "strategy_id": "strategy-id",
  "strategy_version": "local-version",
  "created_at_ms": 0,
  "source": {
    "source_mode": "strategy_graph | formal_qs | v4_qs_handoff",
    "graph_digest": "sha256-or-null",
    "qs_digest": "sha256-or-null",
    "core_ir_digest": "sha256-or-null",
    "v4_graph_digest": "sha256-or-null"
  },
  "capability": {
    "capability_snapshot_hash": "sha256",
    "capability_source": "remote | cache | safe_fallback",
    "frontend_module_keys": [],
    "ui_actions": [],
    "workspace_surfaces": []
  },
  "config_domains": [],
  "runtime_boundary": {},
  "evidence_anchors": [],
  "proposal_bindings": [],
  "artifact_digest": "sha256"
}
```

约束：

- artifact 是导出与解释契约，不是第二条编译路径。
- artifact 不保存密钥、provider secret、refresh token 或账户资料。
- `artifact_digest` 使用 canonical JSON SHA-256；v4.11 不宣称 Ed25519 签名。
- digest 计算必须排除自身字段，避免递归摘要。

### 3.2 `ConfigDomainStatus`

| 字段 | 说明 |
| --- | --- |
| `domain_id` | `market`、`observation`、`state_machine`、`risk`、`execution`、`evidence`、`ai_governance`、`snapshot`。 |
| `lifecycle` | `implemented`、`documentable`、`milestone`、`unsupported`。 |
| `readiness` | `ready`、`incomplete`、`restricted`、`stale`、`blocked`。 |
| `source_refs` | QS、Core IR、v4 graph、capability、runtime evidence、snapshot 等来源。 |
| `findings` | 结构化诊断，必须有 code + 中文 message。 |
| `primary_action` | 当前域下一步动作，可为空。 |

生命周期用于对齐文档四分类；readiness 用于运行时 UI 状态。两者不能混用：`unsupported` 不能被 UI 渲染成 `ready`。

### 3.3 `RuntimeBoundary`

| 字段 | 说明 |
| --- | --- |
| `mode_label` | 用户侧只允许 `PaperSimulated`、`PaperActual`。 |
| `provider_order_submission_attached` | 是否连接 provider submission。 |
| `provider_order_submission_allowed` | 当前策略是否允许 provider submission。 |
| `live_execution_allowed` | 固定为 `false`，除非未来单独里程碑重审。 |
| `execution_capability_sources` | `provider_native`、`runtime_simulated`、`unsupported`。 |
| `rejection_reasons` | 不可启动或不可部署原因。 |

用户文案不得用 `live` 描述 OKX demo / testnet。内部能力键若仍为 `live.okx`，只能作为实现 ID，不得直出给用户。

### 3.4 `EvidenceAnchor`

| 类型 | 来源 | 用途 |
| --- | --- | --- |
| `compile` | `/api/runtime/compile` | 证明运行时编译输出。 |
| `v4_static_audit` | QS v4 audit | 证明状态机可审计。 |
| `run` | runtime run | 证明运行证据。 |
| `backtest` | v4 artifact | 证明回测机器轨迹和风控决策。 |
| `proposal` | AI proposal | 证明提案来源和目标配置域。 |
| `snapshot` | snapshot service | 证明本地恢复完整性。 |

### 3.5 `ProposalBinding`

AI proposal 必须绑定配置域：

```json
{
  "proposal_id": "id",
  "target_domain": "state_machine | risk | execution | market | ai_governance",
  "before_digest": "sha256",
  "after_digest": "sha256",
  "evidence_anchor_ids": [],
  "sandbox_status": "passed | failed | queued",
  "approval_status": "pending | approved | rejected | rolled_back"
}
```

未绑定配置域、无沙箱结果或试图直接写 QS 的 proposal 必须拒绝激活。

### 3.6 `StrategyConfigEvidenceDiffReport`

正式版本比较可以附带显式绑定的 v4 回测证据差异。该报告不是完整回测引擎 diff，而是用户理解“这版配置改动带来哪些运行证据变化”的第一层解释契约。

| 字段 | 说明 |
| --- | --- |
| `schema_version` | `quantpilot/v4-strategy-config-evidence-diff/v1`。 |
| `left_backtest_id` / `right_backtest_id` | 用户或 UI 明确选择的两个 v4 backtest 证据，不自动猜测。 |
| `status` | `same`、`different`、`missing`。 |
| `machine_trajectory` | visited states、transition hit counts、terminal state、first divergence。 |
| `risk_plane` | approved/rejected counts、action/reason counts、first divergence。 |
| `execution_capability` | accepted/rejected counts、runtime mode / capability kind / source / status counts、first divergence。 |
| `metrics` | step count、trade count、return、drawdown、final equity、net profit、win rate 的摘要差异。 |
| `diagnostics` | 缺少绑定、graph 不匹配、非 v4 artifact 或证据缺失时的结构化说明。 |

非目标：不做 tick/bar 全量 diff、成交流水逐笔 diff、权益曲线逐点 diff、自动优胜判定、跨策略 diff 或真实资金执行 diff。

## 4. 后端设计

### 4.1 模块边界

建议新增聚合层，命名可在实现前再核定：

| 模块 | 职责 |
| --- | --- |
| `strategy_config_service` | 聚合 compile、capability、v4 audit、snapshot、evidence。 |
| `strategy_config_artifact` | 定义 artifact、domain status、runtime boundary、digest。 |
| `strategy_config_preflight` | 生成运行前核验结果和 fail-closed 诊断。 |
| `strategy_config_diff` | 进行 artifact/domain 级 diff，并挂接正式图版本对比。 |

### 4.2 路由设计

| 路由 | 方法 | 请求 | 响应 | 约束 |
| --- | --- | --- | --- | --- |
| `/api/v1/strategy-config/artifact` | `POST` | graph/QS/v4 handoff 引用或内容 | `StrategyConfigArtifactV1` | 不绕过 `/api/runtime/compile`。 |
| `/api/v1/strategy-config/preflight` | `POST` | artifact 或策略草稿 | preflight report | unsupported 必须 fail-closed。 |
| `/api/v1/strategy-config/diff` | `POST` | two artifacts | domain diff | 不输出裸 JSON 噪声给用户；正式版本对比通过图版本 compare 路由复用该能力。 |
| `/api/graphs/{graph_id}/versions/compare/{left_version_id}/{right_version_id}` | `GET` | optional `left_backtest_id` / `right_backtest_id` | graph diff + `strategy_config_diff` + optional `strategy_config_evidence_diff` | 证据 diff 只使用显式绑定的同图 v4 backtest artifact。 |

如果实现时发现路由版本策略与现有 `/api` / `/api/v1` 治理冲突，必须按 `03-推进约束与防偏移检查单.md` 暂停并与用户确认。

### 4.3 校验规则

- QS/Core IR/v4 graph 三者不一致时，运行时行为以 `/api/runtime/compile` 为准。
- capability source 为 `safe_fallback` 时，preflight 只能给只读或禁用结论。
- required execution capability 中出现 `unsupported` 时，启动、部署和 AI 激活全部拒绝。
- `PaperActual` 只能表述为 OKX demo 边界；真实资金字段必须为 false。
- artifact digest 失败、缺失或不匹配时，恢复与执行端部署都必须拒绝。

### 4.4 错误模型

| code | 中文 message 口径 |
| --- | --- |
| `strategy_config_incomplete` | 策略配置尚不完整，缺少必要配置域。 |
| `strategy_config_stale_capability` | 当前配置使用的能力快照已过期，需要重新核验。 |
| `strategy_config_unsupported_execution` | 当前策略需要不支持的执行能力。 |
| `strategy_config_digest_mismatch` | 配置摘要不匹配，已拒绝继续执行。 |
| `strategy_config_ai_binding_required` | AI 提案缺少配置域绑定，不能激活。 |

## 5. 前端设计

### 5.1 信息架构

策略配置台应放在策略工作区主流程内，优先作为 `dashboard` 或 `code` 的核心面板，而不是新增独立营销页。

```text
策略工作区
  ├─ 配置总览
  │   ├─ 完整度 / digest / capability source
  │   ├─ 运行边界：PaperSimulated / PaperActual demo / unsupported
  │   └─ 下一步动作
  ├─ 配置域
  │   ├─ 市场与数据
  │   ├─ 观察与信号
  │   ├─ 状态机与 transition guard
  │   ├─ Risk Plane
  │   ├─ 执行
  │   ├─ 证据
  │   ├─ AI proposal
  │   └─ 快照
  └─ 差异与证据
```

### 5.2 组件拆分

| 组件 | 职责 | 数据来源 |
| --- | --- | --- |
| `StrategyConfigCockpit` | 策略配置台容器，承接 preflight、证据锚点、AI 提案绑定和本地上一份 artifact diff | backend artifact/preflight/diff |
| `StrategyConfigSummaryBar` | 完整度、digest、capability source | artifact |
| `ConfigDomainRail` | 配置域导航与状态 | `config_domains` |
| `ConfigDomainPanel` | 单域配置、证据和诊断 | domain status |
| `RuntimeBoundaryPanel` | PaperSimulated / PaperActual demo / unsupported | runtime boundary |
| `EvidenceAnchorList` | compile/run/backtest/proposal/snapshot 锚点 | evidence anchors |
| `ProposalBindingPanel` | AI proposal 目标域与沙箱结果 | proposal bindings |
| `StrategyConfigDiffPanel` | 当前 artifact 与本地上一份 artifact 的 domain diff | diff response |
| `StrategyConfigVersionDiff` | 正式持久化版本之间的配置契约 diff | graph version compare response |
| `StrategyConfigEvidenceDiff` | 正式版本比较中显式绑定的 v4 回测证据差异 | graph version compare response |

当前已落地的第一批 cockpit 不新增独立页面，直接挂在策略工作区 dashboard；它必须展示 `runtime_boundary.live_execution_allowed=false`、完整配置域列表、`ConfigDomainRail`、单域来源/诊断面板、`evidence_anchors`、`proposal_bindings`、当前 artifact JSON 导出入口与本地上一份 artifact 的 domain diff。正式版本间 diff 挂在版本历史卡片：用户选择两个持久化版本后，比较响应必须同时展示节点、连线、配置字段和 `strategy_config_diff` 配置契约差异；当用户再显式选择左右 v4 backtest 证据时，同一路径展示 `strategy_config_evidence_diff`，用于解释 machine trajectory、Risk Plane、execution capability 与摘要指标变化。后续若要把单域深钻升级为可编辑配置表单或自动修复动作，必须单独绑定后端动作语义，不得替代当前已接入的启动前 preflight 阻断。

### 5.3 交互规则

- capability 未加载：显示骨架和“正在核验能力”，高风险动作禁用。
- capability cache：允许只读查看，动作需提示后端仍会最终校验。
- safe_fallback：只读摘要，启动、部署、AI 激活禁用。
- `unsupported` 配置域：不提供 CTA，不展示“即将支持”暗示。
- `PaperActual`：按钮、提示、面板都必须带 OKX demo 边界。

### 5.4 视觉规则

- 采用现有设计系统令牌，不新增一套视觉语言。
- 配置域面板要紧凑、可扫描，避免营销式 hero。
- 不做卡片套卡片；重复项可以用表格、列表或分段面板。
- 所有新文案必须走 `t()` 和 i18n 字典。

## 6. 执行端设计

执行端只消费后端 artifact/preflight 摘要，不重新推断能力。

| 面板 | 内容 | 拒绝行为 |
| --- | --- | --- |
| `StrategyConfigPreflightPanel` | artifact digest、runtime boundary、Risk Plane required、unsupported capability | 不通过时禁用启动。 |
| `RuntimeBoundaryBadge` | `PaperSimulated` 或 `PaperActual / OKX demo` | 禁止显示 live。 |
| `ExecutionCapabilitySourceList` | provider_native/runtime_simulated/unsupported | unsupported 高亮并阻断。 |
| `EvidenceAnchorStrip` | 最近 run/backtest/proposal/snapshot | 缺失证据时提示重新核验。 |

## 7. 配套依赖设计

默认不新增依赖。v4.11 第一轮实现优先使用现有栈：

| 需求 | 默认方案 | 依赖策略 |
| --- | --- | --- |
| canonical digest | 复用现有 canonical JSON SHA-256 | 不新增 crate。 |
| JSON 序列化 | `serde` / `serde_json` | 已有依赖。 |
| schema 文档 | 先手写 OpenAPI schema | 暂不引入 `schemars`。 |
| artifact / version diff | 后端按 domain 手写 diff；图版本 compare 附带 `strategy_config_diff` 与显式 v4 evidence diff | 暂不引入 diff npm 包。 |
| 前端校验 | 后端校验为准，前端做投影 | 暂不引入 `zod` / `ajv`。 |
| 编辑器增强 | 沿用现有 QS 编辑路径 | 暂不引入 Monaco / CodeMirror。 |

如果实现阶段确需新增依赖，必须先暂停并提交依赖评审，说明收益、替代方案、bundle/编译影响、许可证和测试策略。
