# v4.11.0 规划方案：v4 策略配置系统一等化

> 版本类型：MINOR
> 基准：v4.10.0 UX 收口与产品边界固化
> 主轴：v4 策略配置系统 = 第一功能切面
> 约束：General Policy + 超级规范化 + 支持矩阵/用户功能切面总览

---

## 目标

v4.11.0 的目标是把 v4 策略配置从“分散在策略图、QuantScript、运行、回测、AI、快照、执行端的能力集合”，收束为用户可理解、可编辑、可验证、可交付的一等策略配置系统。

本里程碑不以新增页面数量为成功标准，而以以下设计指标为成功标准：

| 指标 ID | 设计指标 | 成功判定 |
| --- | --- | --- |
| `SC-1` | 配置域完整 | 市场、观察、状态机、风控、执行、证据、AI 治理、快照均有明确配置域、状态和证据入口。 |
| `SC-2` | 契约可导出 | 用户可获得单一 v4 strategy config artifact，包含版本、来源、能力边界、QS/Core IR/v4 graph 摘要和证据锚点。 |
| `SC-3` | 能力不漂移 | 前端入口、后端 capability、支持矩阵、OpenAPI 和测试 fixture 对同一能力给出一致结论。 |
| `SC-4` | 运行前可解释 | 启动仿真、回测或执行端部署前，用户能看到 PaperSimulated、PaperActual demo、unsupported 的明确边界。 |
| `SC-5` | 证据闭环 | 配置修改、运行、回测、AI proposal、审批、回滚和快照能追踪到同一 config hash 或 digest。 |
| `SC-6` | 用户不误解 | 不把账户系统、策略搜索筛选、真实资金自动交易、研究级回测、第三方插件市场写回产品路线。 |

推进硬规则：遇到本地代码、支持矩阵、总览文档、里程碑文档或产品边界之间的分歧点，必须按 `03-推进约束与防偏移检查单.md` 当场暂停，与用户讨论并解决后才能继续推进。

---

## 非目标

- 不新增账户系统、注销、密码找回、2FA、RBAC 或用户资料页。
- 不新增策略中心搜索、筛选、排序、分页或资产管理工作台。
- 不开放真实资金自动交易，不把 OKX demo 或 PaperActual 宣传为实盘。
- 不把基础回放升级宣传为研究级回测平台。
- 不建设第三方插件市场或远程插件安装 UI。
- 不允许 AI 自动改写 QS 并绕过用户审批执行。
- 不新增 Machine 模板，除非另开 MAJOR/MINOR 里程碑并先登记。
- 不新增 npm/cargo 依赖，除非在本里程碑 W7 依赖评审通过。

**严重度**：P0
**约束**：GP §1.5、§1.12、§1.13；超级规范化 §2、§3、§4；用户功能切面总览 §2

### 方案

- 建立 `SC-1` 到 `SC-6` 的设计指标追踪表。

- 文档里所有能力必须分为：当前已实现、当前可文档化、后续里程碑、明确不做。

### 验收

- `03-推进约束与防偏移检查单.md` 创建完成。
- 本里程碑任何后续设计或落地记录都能引用同一组指标。
- unsupported 项不会出现在功能演进登记的 supported 或 planned 列。

## W1：v4 strategy config artifact

**严重度**：P0
**约束**：GP §1.1、§1.3、§1.6、§1.7、§1.10、§1.12

### 目标

定义单一用户级配置契约，作为策略配置台、导出、快照、回测、AI proposal 和执行端 preflight 的共同对象。

### 最小字段

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `schema_version` | 后端常量 | 例如 `quantpilot/v4-strategy-config-artifact/v1`。 |
| `strategy_id` / `strategy_version` | 图持久化与版本历史 | 关联本地策略与版本。 |
| `source_mode` | graph/QS 编译输入 | 标记来源为 strategy_graph、formal_qs 或 v4_qs_handoff。 |
| `config_domains` | 后端聚合 | 市场、观察、状态机、风控、执行、证据、AI、快照状态。 |
| `capability_snapshot_hash` | `/api/capabilities` | 防止前后端能力漂移。 |
| `qs_digest` | QS 源 | 不保存密钥，不保存 provider secret。 |
| `core_ir_digest` | `/api/runtime/compile` | 运行时编译输出摘要。 |
| `v4_graph_digest` | v4 machine graph | 状态机契约摘要。 |
| `runtime_boundary` | capability + runtime | PaperSimulated、PaperActual demo、unsupported 等。 |
| `evidence_anchors` | run/backtest/proposal/snapshot | 运行、回测、AI proposal、快照引用。 |
| `artifact_digest` | canonical JSON SHA-256 | v4.11 先做摘要一致性，不宣称 Ed25519 签名。 |

### 拒绝行为

- 缺失 QS/Core IR/v4 graph 关键输入时，artifact 状态为 `incomplete`，不能伪装成可部署。
- capability hash 与当前后端快照不一致时，导出允许但必须标记 `stale_capability_snapshot`。
- 任何 `unsupported` execution capability 出现在 required 能力中时，preflight 必须 fail-closed。

## W2：后端配置聚合与校验

**严重度**：P0
**涉及层**：backend、qrpc_core_ir、quantscript、contracts、tests

### 方案

- 新增或扩展后端聚合服务，把 `/api/runtime/compile`、v4 static audit、capability snapshot、snapshot digest、v4 backtest artifact 统一投影为 strategy config view。
- 后端继续作为能力真源，前端不得从静态数组自行判定配置域可用性。
- OpenAPI 必须登记 artifact 导出、preflight、diff 相关路由。
- 后端测试必须覆盖 supported、restricted、unsupported、stale capability、missing evidence 五类状态。

### 候选路由

| 路由 | 方法 | 状态 | 说明 |
| --- | --- | --- | --- |
| `/api/v1/strategy-config/artifact` | `POST` | started | 根据当前策略输入生成 v4 strategy config artifact。 |
| `/api/v1/strategy-config/preflight` | `POST` | started | 返回配置完整度、运行边界、风险和拒绝原因。 |
| `/api/v1/strategy-config/diff` | `POST` | started | 对比两个 artifact 或配置草稿；第一批先返回 domain 级结构化差异。 |

## W3：前端策略配置台

**严重度**：P0
**涉及层**：frontend、i18n、tests、capability projection

### 方案

策略配置台不是新营销页，而是策略工作区内的主工具面。它必须展示：

- 配置域导航：市场、观察、状态机、风控、执行、证据、AI、快照。
- 每个配置域的状态：已配置、缺失、受限、后续、unsupported。
- 每个配置域的真源：QS、Core IR、v4 graph、capability、runtime evidence、snapshot。
- 运行前摘要：是否可编译、是否可 PaperSimulated、是否可回测、是否可部署到 OKX demo 边界。
- 不做项提示：账户、策略搜索、真实资金、研究级回测不得作为 CTA 出现。

### UI 约束

- 延续现有工作区密度和 Adobe 风格设计系统，不做 landing page。
- 不使用卡片套卡片；配置域可以用紧凑面板和表格承载。
- 所有用户可见文本使用 `t()`。
- safe_fallback 时只显示只读摘要与禁用原因，不恢复完整操作。

## W4：配置差异与证据差异

**严重度**：P1

### 方案

- 支持正式持久化版本之间的策略图 / 配置契约 diff。
- `/api/graphs/{graph_id}/versions/compare/{left_version_id}/{right_version_id}` 必须附带 `strategy_config_diff`，把图版本对比和配置域对比放在同一用户路径。
- `/api/v1/strategy-config/diff` 继续支持 artifact-to-artifact diff，作为配置契约 diff 的底层能力。
- diff 结果必须按配置域分组，不按 JSON 原始路径裸露给用户。
- 在正式版本比较路径上支持显式绑定左右 v4 回测证据：`left_backtest_id` 与 `right_backtest_id` 必须由用户或 UI 明确选择，不做自动猜测。
- `strategy_config_evidence_diff` 只比较同一 `graph_id` 下两个持久化版本的 v4 backtest artifact，范围限定为 machine trajectory、Risk Plane decisions、execution capability sources 与 summary metrics。
- 缺少绑定、graph 不匹配、非 v4 artifact 或证据缺失时必须返回结构化 diagnostics，不得静默降级为“无差异”。

### 非目标

- 不做云端协作 diff。
- 不把策略中心改造成版本管理平台。
- 不做自动优胜判定、tick/bar 全量 diff、成交流水逐笔 diff、权益曲线逐点 diff、跨策略 diff 或真实资金执行 diff。

## W5：AI proposal 配置域绑定

**严重度**：P1
**约束**：GP §9.1、§9.4；`ai_write_policy=proposal_only`

### 方案

- AI proposal 必须声明目标配置域、修改前值、修改后值、证据来源、沙箱结果和回滚路径。
- proposal 不得直接写 QS，不得直接启动运行，不得绕过 approval。
- sandbox 失败必须进入可见状态，不得静默丢弃。

### 当前落地

- AI proposal 静态检查已要求携带 `config_domain_binding`，包含 `target_domain`、`before_digest`、`after_digest`、`evidence_anchor_ids`；缺失会形成不可审批通过的失败候选，保留审计轨迹。
- 后端静态检查会校验 proposal 目标模块与配置域是否一致，并校验 before/after digest 与规范参数版本一致。
- v4 AI proposal 必须绑定 backtest evidence；非 v4 proposal 仍绑定 run evidence。
- 审批通过前必须满足：配置域绑定存在、静态检查通过、沙箱报告存在且未判定为 underperform；否则返回 `423 Locked`。
- 自动沙箱 3 次失败会写入审批生命周期，审批通过路径继续保持阻断。

## W6：执行端启动前配置核验

**严重度**：P1
**约束**：GP §1.9、§1.10、§2.7

### 方案

- 执行端接收 artifact 或 preflight 摘要，不自行推断策略能力。
- 启动前展示 runtime mode、provider submission attached/allowed、Risk Plane required、unsupported capabilities。
- PaperSimulated 和 PaperActual demo 文案必须明确，不得出现实盘暗示。

## W7：支持矩阵与依赖治理

**严重度**：P0

### 方案

- 支持矩阵必须同步本地代码中的 16 个前端模块键和 `start_v4_simulation` action。
- 若新增后端 artifact/preflight/diff 路由，必须同步 OpenAPI、capability fixture、支持矩阵、用户功能切面总览。
- 默认不新增依赖；如确需 JSON Schema、diff 或编辑器增强依赖，必须先写依赖评审：
  - 是否已有标准库或现有 crate/npm 包可完成。
  - 是否影响 bundle 体积或 Tauri 启动。
  - 是否有维护风险、许可证风险和测试替代方案。
