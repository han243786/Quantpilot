# v4.8.1 规划方案 — API 契约与部署治理超级规范化

> 版本类型: PATCH | 基准: v4.8.0 closeout | 建议启动: v4.8.2/v4.9.0 非账户项落地前后均可
> 来源: 2026-05-26 只读全量审计; 约束: 全量树 + GP 矩阵 + 超级规范化文档
> 范围裁剪: 按用户要求, 账户、登录、注销、密码找回、会话撤销与 refresh token 语义不纳入本轮里程碑

---

## 目标

v4.8.1 不扩展交易能力边界, 不新增账户产品能力, 只把审计中可独立落地的契约和治理问题收口为可验证里程碑。

1. **OpenAPI 结构修复**: 凭证路由必须位于顶层 `paths`, 不得缩进到 `components`。
2. **Route Diff 入口**: 建立实际路由与 OpenAPI path 的差异检查输入, 为 v4.9.0 API 版本治理提供基线。
3. **部署 Profile 矩阵**: 固化 `dev` / `local-secure` / `production` / `executor` 的运行画像、能力源、风险平面和执行平面。
4. **四平面治理**: 将 Capability Plane、Risk Plane、Execution Plane、Audit Event 对齐为可审计矩阵; 本轮不引入 Account/Auth Plane 新能力。
5. **依赖现代化评估**: 只输出分批升级和回归基线, 不在本 PATCH 内混入大版本依赖升级。

## 非目标

- 不新增、修改或承诺账户相关功能。
- 不新增登录、登出、密码找回、会话撤销、refresh token 行为变更。
- 不开放真实资金 `LiveActual` 自动下单。
- 不新增交易 provider、资产类别、Machine 模板或 V1 QS 语法面。
- 不把 OKX demo/testnet 描述为真实实盘。
- 不将规划文档描述为已实现能力; 只有代码、测试和 closeout 通过后才能改为已完成。

## W0 — OpenAPI 凭证路径结构

**严重度**: P1
**约束**: GP §4.1, 超级规范化 §4.3

### 问题

`/api/credentials` 和 `/api/credentials/{service}` 曾位于 `components` 缩进层级, 不是顶层 `paths`。这会让 OpenAPI 解析器、代码生成器和契约 lint 误判凭证 API 缺失。

### 方案

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `contracts/openapi/root.yaml` | 将凭证路由移动到顶层 `paths` |
| 2 | `contracts/openapi/root.yaml` | 保留 schema 在 `components/schemas`, 路由与 schema 不混放 |
| 3 | 工具链 | 后续补充 YAML 结构 lint 或 route diff 检查 |

### 验收

- OpenAPI 解析器能识别 `/api/credentials` 与 `/api/credentials/{service}` 为 path。
- `components` 下不再出现以 `/api/` 开头的 path key。
- `POST /api/runtime/runs` 等实际存在路由仍在规范中可检索。

## W1 — Route Diff 基线

**严重度**: P2
**约束**: GP §4.1, GP §4.4

### 方案

建立“实际路由 → OpenAPI path”的差异输入, 先覆盖主后端 `src/app_router.rs` 和执行端 `src-executor/main.rs`。v4.8.1 可先形成清单和脚本入口, v4.9.0 再纳入阻断门禁。

### 验收

- 差异清单能区分“已实现但未公开规范”“规范存在但代码未实现”“故意内部路由”。
- 新增公开 API 时必须同步 OpenAPI 与全量树。

## W2 — 部署 Profile 契约

**严重度**: P2
**约束**: GP §1.12, GP §3.3, GP §10

| Profile | 能力源 | 风险平面 | 执行端 | 用途 |
|---------|--------|----------|--------|------|
| `dev` | backend capability projection | optional by route | optional | 本地快速开发 |
| `local-secure` | backend capability projection | required for execution | optional | 本地安全验证 |
| `production` | backend capability projection | required | configured | 发布候选 |
| `executor` | executor capability/status | required by strategy | required | 执行端联调 |

### 验收

- README、支持矩阵、全量树和 closeout 对 profile 命名一致。
- 启动日志或状态接口能说明当前能力源、风险平面状态和执行模式。
- Docker/桌面启动配置不产生“服务健康但主流程不可用”的假健康状态。

## W3 — 四平面治理矩阵

**严重度**: P2
**约束**: GP §1.9, GP §1.10, GP §1.12, 超级规范化 §5
