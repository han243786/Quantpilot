## P1 — v4.8.1 必须完成

### P1-1: OpenAPI 凭证路径缩进到 components 中

**策略**: GP §4.1

**问题**: `/api/credentials` 和 `/api/credentials/{service}` 位于 `components` 缩进层级, 不是顶层 `paths`。自动验证工具、SDK 生成器和契约审计会把凭证 API 视作缺失或结构损坏。

**影响文件**:
- `contracts/openapi/root.yaml`

**方案**:
1. 将两个凭证路由移动到顶层 `paths`。
2. schema 保留在 `components/schemas`。
3. 补充后续 route diff 输入, 避免同类缩进问题复发。

**验收**:
- OpenAPI 解析器能识别 `/api/credentials` 与 `/api/credentials/{service}`。
- `components` 下不再出现 `/api/` path key。
- `git diff --check` 与 UTF-8 门禁通过。

## P2 — 建立治理基线

### P2-1: 实际路由与 OpenAPI path diff 缺少基线

**策略**: GP §4.1, GP §4.4

**问题**: 当前路线图只靠人工审计发现 OpenAPI 漂移, 缺少“代码路由 vs 规范 path”的可重复对比入口。

**方案**:
1. 提取 `src/app_router.rs` 和 `src-executor/main.rs` 的公开路由清单。
2. 与 `contracts/openapi/root.yaml` 的 `paths` 做 diff。
3. 标注内部路由、legacy 路由和待公开规范路由。

**验收**:
- route diff 能输出至少三类结果: missing-in-openapi、missing-in-code、internal-only。
- v4.9.0 API 版本治理可以直接引用该清单。

### P2-2: 部署 profile 缺少机器可读契约

**策略**: GP §1.12, GP §3.3

**问题**: `QUANTPILOT_DEV`、API key、Docker、桌面启动脚本和 executor guard 分散表达, 缺少统一 profile 矩阵。结果是能力源、风险平面和执行平面的边界不够醒目。

**方案**:
1. 建立 `dev` / `local-secure` / `production` / `executor` 矩阵。
2. 启动日志输出当前 profile。
3. health/status 响应增加能力源、风险平面、执行模式摘要。
4. README、支持矩阵、全量树同步 profile 命名。

**验收**:
- 每个 profile 可由文档和运行状态互相印证。
- Docker 默认配置不造成假健康。

### P2-3: 四平面治理矩阵尚未阻断化

**策略**: GP §1.9, GP §1.10, GP §1.12

**问题**: v4 已强调 Capability Plane、Risk Plane 和 Execution Plane, 但执行入口的审计事件和插件执行安全还需要固定矩阵化描述。

**方案**:
1. 为图保存、compile、paper run、v4 run、executor provider、plugin execution 建立四平面条目。
2. closeout 报告固定包含四平面一致性结论。
3. 对 executor provider 路由保留 HMAC + mode guard + audit event 三重约束。
4. 对 plugin execution 要求 manifest + registry truth + sandbox policy。

**验收**:
- 新增入口缺少任一平面声明时不得标记 supported。
- closeout 能追踪每个执行入口的能力来源、风险约束、执行边界和审计事件。

## P3 — 持续回归或独立升级

### P3-1: npm 依赖现代化评估

**策略**: 超级规范化 §2.2, GP §10.3

**问题**: `npm audit` 当前无中高危漏洞, 但 React、Vite、Vitest、Playwright、Zustand 等存在新版本。该项是维护漂移, 不应与契约修复混合。

**方案**:
1. 保留 `npm audit --audit-level=moderate` 为安全门禁。
2. 使用 `npm outdated --long` 作为评估输入。
3. 按测试工具、构建工具、运行时依赖分批升级。

**验收**:
- 形成独立升级清单和回滚策略。
- 双前端 build 与关键路径 E2E 作为每批升级基线。

### P3-2: 前端依赖升级缺少截图/E2E 基线

**策略**: GP §10.3

**问题**: React/Vite 等大版本升级可能改变渲染、事件和测试环境。需要先固定视觉与 E2E 基线。

**方案**:
1. 对主前端、执行端前端分别建立截图或 Playwright 基线。
2. 升级前后比较图编辑、编译、运行、executor 面板。
3. 大版本不兼容时分流至后续 MINOR。

**验收**:
- 每批依赖升级都有可复验基线。
- UI 行为差异必须有记录。
