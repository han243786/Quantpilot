## P1-9: 4 页面 i18n 包裹

### 现状分析

| 文件 | 硬编码数 | 主要字符串类型 |
|------|:--:|------|
| `RunbookPage.jsx` | ~20 | 步骤编号前缀("诊断步骤"/"恢复步骤"/"验证")、症状标签、展开/折叠文本 |
| `SnapshotsPage.jsx` | ~15 | 创建/恢复按钮、签名字段名、空状态提示 |
| `ChaosPage.jsx` | ~15 | TYPE_LABELS 静态映射、注入类型名、实验创建按钮 |
| `BacktestComparePage.jsx` | ~15 | 工具提示、指标标签、加载/错误/空状态文案 |

### 方案: 增量包裹 + locale fallback 安全

**核心思路**: `t()` 在当前 zh-CN locale 下调用 `messages[baseText] || baseText`。
如果 locale 文件缺少某个 key，t() 回退显示 key 本身（即中文原文）。
这意味着——**即使只包裹了字符串但没在 en-US 中添加翻译，zh-CN 模式完全不受影响。**

**实施步骤**:

1. 各文件 `useI18n` 已导入（上轮已完成），直接使用 `const { t } = useI18n()`
2. 逐文件包裹用户可见字符串:

```jsx
// 静态文本: 直接包裹
<h3>{t("诊断步骤")}</h3>

// 拼接文本: 先拆再包
<span>{t("症状")}: {s.symptoms}</span>

// 条件文本: 在分支内包裹
{running ? t("运行中...") : t("运行测试")}

// TYPE_LABELS 静态映射: 改为访问时调用
const label = t(TYPE_LABELS[type]);  // key 是中文, fallback 正常
```

3. **不包裹的内容**:
   - 后端返回的数据字段名（如 `s.scenario_id`、`e.experiment_id`）
   - 符号/emoji（`✓` `✗` `⊘`）
   - 技术标识符（`#6b9e7a`、`deterministic_mock`）

**回滚安全**: 每个文件独立修改，任意文件出错不影响其他文件。`t()` fallback 行为保证即使 locale 缺失也不会显示空白。

**验收**:
- `grep -n "[一-鿿]" <file>` 仅匹配 t() 调用内和数据变量名
- zh-CN 模式下页面显示与包裹前完全一致
- 每个文件改完后 `npx vitest run` 通过

**估时**: 30min (4 文件 × ~8min)

## P1-21: ApprovalPanel 内联样式

### 现状分析

ApprovalPanel.jsx 337 行，剩余约 20 个 `style={{...}}`。分布:
- 间距类: `marginTop`/`marginLeft`/`marginBottom` ~8 处
- 颜色类: `color: "var(--ad-*)"` ~5 处
- 字号类: `fontSize: 11/12` ~4 处
- 布局类: `display: "flex"` 等 ~3 处

### 方案: 提取 4 个语义 CSS 类

**核心思路**: 不为每个内联样式创建类，而是为语义化模式创建类。

```css
/* 追加到 styles.css */

/* 审批面板 — 时间戳/次要文本 */
.approval-meta-text {
  font-size: var(--ad-font-size-xs);
  color: var(--ad-text-muted);
}

/* 审批面板 — 状态强调色文本 */
.approval-status-text {
  font-size: var(--ad-font-size-sm);
  font-weight: 500;
}

/* 审批面板 — 报告表格数据格 */
.approval-report-cell {
  font-size: var(--ad-font-size-sm);
  color: var(--ad-text-secondary);
  font-family: var(--ad-font-mono);
}
```

**替换映射**:

| 原内联 style | 替换为 className |
|-------------|-----------------|
| `style={{ fontSize: 12, color: "var(--ad-text-muted)", marginLeft: 8 }}` | `className="approval-meta-text" style={{ marginLeft: 8 }}` |
| `style={{ color: "var(--ad-text)", fontWeight: 500 }}` | `className="approval-status-text"` |
| `style={{ color: "var(--ad-text-secondary)", fontFamily: "var(--ad-font-mono)", fontSize: 12 }}` | `className="approval-report-cell"` |
| `style={{ fontSize: 11 }}` | `className="approval-meta-text"` (合并) |
| `style={{ cursor: "pointer" }}` | 保留 (1 处, 独特语义) |

**不替换的保留项** (~5 处):
- `style={{ cursor: "pointer" }}` — 语义独特
- `style={{ marginTop: 8, display: "flex", gap: 6 }}` — 组合布局, 保留
- 条件渲染的 `marginTop: 8` — 上下文决定

**回滚安全**: 每处替换独立，CSS 类仅影响 ApprovalPanel。样式效果完全一致。

**验收**:
- ApprovalPanel 渲染与替换前像素一致
- 内联样式从 ~20 减少到 ~8

**估时**: 20min

## P2-17: 并发保存 5 个 POST

### 现状分析

`saveGraph()` 在 `graphStorePersistenceActions.js:81` 定义。当前流程:
```
1. get().graph           ← 捕获 graph
2. compileGraph(...)     ← 同步
3. saveGraphToStorage()  ← 同步
4. set({...})            ← 乐观更新
5. await postJson(...)   ← 网络请求 ← 竞态窗口
6. refreshGraphIndex()   ← 刷新
```

**竞态**: 5 次快速调用 → 5 个并发 POST → 服务端可能产生 5 个版本记录。

### 方案: saveGraph 添加 saving 锁 (与 compileStatus 同模式)

**核心思路**: 不阻止调用（可能来自不同组件），但串行化执行。

```js
// graphStore.js 初始状态
savingGraph: false,

// graphStorePersistenceActions.js
async saveGraph(options = {}) {
  if (get().savingGraph) {
    // 已有保存进行中, 不重复提交
    return;
  }
  set({ savingGraph: true });
  try {
    // ... 原有保存逻辑 ...
  } finally {
    set({ savingGraph: false });
  }
}
```

**与现有机制的兼容**:
- `saveGraph()` 已有失败回滚（上轮添加）→ 保持不变
- TopToolbar 的 `saving` 状态是 UI 层面的 → 保持不变
- `savingGraph` lock 是 store 层面的 → 新增, 互补

**注意**: `savingGraph` 是锁不是队列——如果调用时锁已存在，直接返回。这意味着快速点击 5 次只有第 1 次生效。如果用户希望第 5 次配置生效，需要在第 1 次完成后重新点击。这是合理的行为。

**为什么不实现队列**: 队列会增加复杂度（超时、去重、优先级），且用户场景中连续保存 5 次的动机几乎总是误操作，丢弃后 4 次是正确的。

**回滚安全**: lock 在 finally 中释放，异常安全。不影响现有逻辑。

**验收**:
- 快速点击保存 5 次 → 仅 1 个 POST 发送
- 正常保存 → 行为不变
- `npx vitest run` 全量通过

**估时**: 15min

## P2-18: compileStatus 静默 null

### 现状分析

```js
// graphStoreCompileActions.js:136
if (get().compileStatus === "loading") return null;
```

调用方 (`startRuntime`/`startBacktest`/`exportRuntimeConfig`) 看到 `null` 后各自处理:
- `startRuntime`: 静默退出
- `startBacktest`: 静默退出  
- `exportRuntimeConfig`: 回退到过期的 compileResult

### 方案: 已由 S0-5 runtimeActionLock 间接解决, 添加注释说明

**不再单独修复的理由**:

1. `compileStatus` lock → 防止并发编译 (编译按钮点击)
2. `runtimeActionLock` → 防止并发启动 (启动/回测按钮点击)

两层锁覆盖了所有生产路径。`return null` 只在理论上可触发（如果某处程序化调用 `compileCurrentGraph` 绕过了两层锁），但生产代码中不存在这种路径。

**方案**: 添加文档注释说明锁层次, 不做代码改动。

```js
// 编译并发控制: compileStatus (编译级) + runtimeActionLock (运行级)
// 正常用户路径下这两层锁已覆盖所有场景, return null 仅用于防御性编程
if (get().compileStatus === "loading") return null;
```

**验收**: 无需代码改动, 文档注释更新

**估时**: 2min

## P2-21: compile 通知 2.6s 自动消失

### 现状分析

```js
// useWorkspaceActionBarModel.js:16
const NOTICE_FADE_DELAY_MS = 2600;
```

成功/失败通知在 2.6s 后自动消失。用户编译后如果切到其他 tab 再回来，看不到任何编译历史。

### 方案: 利用已有的 ToolbarIssues 区域显示编译状态

**核心思路**: 编译后无论成功/失败，在 `ToolbarIssues` 区域（工具栏下方的问题芯片区）追加一条持久记录。用户始终可见最后一次编译结果。

**实现**:

1. 新增 store 字段: `compileResultNotice: { type: "success" | "error", text: string, time: number } | null`
2. 编译成功后设置: `compileResultNotice: { type: "success", text: "编译成功 — 已生成运行协议", time: Date.now() }`
3. 编译失败后设置: `compileResultNotice: { type: "error", text: "编译失败 — 查看诊断", time: Date.now() }`
4. TopToolbar 渲染时在 `ToolbarIssues` 块后显示编译状态芯片（与诊断芯片样式一致）

```jsx
// TopToolbar 渲染
{compileResultNotice && (
  <span className={`toolbar-issue-chip issue-${compileResultNotice.type === "error" ? "error" : "info"}`}>
    {compileResultNotice.text}
  </span>
)}
```

**为什么不用持久通知栏**: 避免引入新 UI 组件。ToolbarIssues 区域已存在且用户已习惯在此查看状态。

**回滚安全**: 新增字段和渲染逻辑完全独立，不影响现有通知行为。

**验收**:
- 编译成功 → ToolbarIssues 区域显示绿色芯片 "编译成功"
- 编译失败 → 红色芯片 "编译失败 — 3 个错误"
- 下次编译覆盖上次记录
- 通知 2.6s 自动消失保持不变（两个机制互补）

**估时**: 25min

## P2-22: 回测前冗余 recompile

### 现状分析

```js
// graphStoreRuntimeSessionActions.js:198
const result = await get().compileCurrentGraph();
```

每次 `startBacktest()` 都调用 `compileCurrentGraph()`，即使刚编译过。

### 方案: 使用 compileResult 缓存跳过

**核心思路**: 如果 `compileResult` 已存在且 graph 自上次编译后未被修改，跳过 recompile。

**实现**:

```js
const graph = get().graph;
const lastCompileGraphId = get().compileResult?.backend_compile?.artifacts?.strategy?.metadata?.graph_id;
const currentGraphId = graph.metadata?.graph_id;

let result;
if (lastCompileGraphId === currentGraphId && get().compileResult) {
  // 自上次编译后 graph 未变, 复用编译结果
  result = get().compileResult;
} else {
  result = await get().compileCurrentGraph();
  if (!result) { set({ runtimeActionLock: false }); return; }
}
```

**安全性**:
- `graph_id` 在每次 `saveGraphToStorage`/`createNode`/`updateNodeConfig` 后更新
- 如果 graph_id 相同 → graph 结构未变 → 编译结果有效
- 如果 graph_id 不同 → graph 已修改 → 重新编译

**为什么不完全移除**: 如果 graph 被程序化修改但未触发 graph_id 更新（可能性极低但有理论风险），跳过编译会导致使用过期 runtime_config。`graph_id` 比较提供了安全网——只有确认 graph 未变才跳过。

**回滚安全**: 如果 graph_id 比较逻辑出错的最坏情况是每次都 fallback 到 `compileCurrentGraph()`，即当前行为。

**验收**:
- 编译后立即点回测 → 跳过 recompile (graph_id 相同)
- 修改节点后点回测 → 执行 recompile (graph_id 不同)
- 回测结果与当前策略一致

**估时**: 15min

## P2-23: 对比选择策略作用域

### 现状分析

```
graphStore.js:78  backtestCompareSelection: []
```
12+ 个 reader/writer 分布在:
- `strategyResearchSelectors.js:377` — 读取
- `useStrategyDirectoryModel.js:249` — 读取
- `useStrategyWorkspacePageData.js:118` — 读取
- `graphStoreRuntimeHistoryState.js:10,19,28,37,86` — 写入
- `graphStore.js:234,303` — 重置
- `graphStoreEditorActions.js:143` — 重置
- `graphStorePersistenceActions.js:55` — 重置

### 方案: Wrapper 函数 + 渐进迁移

**核心思路**: 不直接改数据结构，而是添加两个 wrapper 函数统一读写，让旧代码逐步迁移。新代码通过 wrapper 访问。

```js
// graphStoreRuntimeHistoryState.js 新增

function getCompareSelection(state, strategyId) {
  const raw = state.runtime.backtestCompareSelection;
  // v1.0.5: 向后兼容旧数组格式
  if (Array.isArray(raw)) return raw;
  // 新格式: { [strategyId]: string[] }
  return raw[strategyId] || [];
}

function setCompareSelection(state, strategyId, ids) {
  const raw = state.runtime.backtestCompareSelection;
  const base = Array.isArray(raw) ? {} : { ...raw };
  return { ...state, runtime: { ...state.runtime, backtestCompareSelection: { ...base, [strategyId]: ids } } };
}
```

**迁移步骤**:

| 步骤 | 文件 | 改动 |
|------|------|------|
| 1 | `graphStoreRuntimeHistoryState.js` | 新增 wrapper + 内部调用 wrapper |
| 2 | `strategyResearchSelectors.js:377` | `raw → getCompareSelection(state, strategyId)` |
| 3 | `useStrategyWorkspacePageData.js:118` | 同上 |
| 4 | `useStrategyDirectoryModel.js:249` | 同上 |
| 5 | `graphStore.js` 重置点 | `backtestCompareSelection: {}` |
| 6 | `graphStoreEditorActions.js` 重置 | 同上 |
| 7 | 测试 | 更新 fixture |

**向后兼容**: `getCompareSelection()` 的 `Array.isArray(raw)` 检查确保旧 localStorage 数据仍可读取。新数据写入对象格式后向下兼容。

**回滚安全**: wrapper 函数层使得数据结构变更对调用方透明。如果新格式有问题，只需修改 wrapper。

**验收**:
- 切换策略 A → 选 2 个回测 → 切换策略 B → 选 2 个回测 → 切回 A → A 的 2 个回测仍在
- 旧 localStorage 数组格式数据正常迁移
- `npx vitest run` 全量通过

**估时**: 45min

## 汇总

| # | 方案类型 | 改动文件数 | 估时 | 风险 |
|---|---------|:--:|:--:|:--:|
| P1-9 | 增量 t() 包裹 | 4 | 30min | 低 (fallback 安全) |
| P1-21 | 4 个语义 CSS 类 | 2 | 20min | 低 (独立样式) |
| P2-17 | savingGraph 锁 | 2 | 15min | 低 (finally 安全) |
| P2-18 | 文档注释 | 0 | 2min | 无 |
| P2-21 | compileResultNotice 字段 | 3 | 25min | 低 (独立字段) |
| P2-22 | graph_id 缓存比较 | 1 | 15min | 低 (fallback 安全) |
| P2-23 | wrapper 函数 + 渐进迁移 | 8 | 45min | 中 (多文件, 但 wrapper 隔离) |
| **合计** | | | **~2.5h** | |

### 设计原则

1. **向后兼容**: 所有方案保留旧数据/旧行为作为 fallback
2. **独立可回滚**: 每项修改互不依赖, 出问题可单独 git revert
3. **最小改动**: 优先复用现有机制 (wrapper/复用组件/已有字段)
4. **异常安全**: 所有锁/状态切换在 finally 中释放
