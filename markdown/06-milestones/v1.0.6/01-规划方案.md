# v1.0.6 用户困惑点全量优化

> 基于四维度全量审计 | 4 个 agent 并行分析 | 无新功能 | 纯用户体验修复

---

## 背景

v1.0.5 完成了前端样式深度修复、分页全栈贯通、API 客户端统一、18 指标全实现等 55 项优化。系统功能完整，但用户实际使用中存在大量困惑点。

本轮从"用户看到什么、理解什么、下一步做什么"的角度，启动**四维度用户困惑点全量审计**，由 4 个 agent 并行分析：

- **Agent 1**: 后端错误消息审计 — `api_errors.rs`、`compile_diagnostics.rs`、`runtime_diagnostics.rs`、`runbook.rs`、`auth_middleware.rs`、`rate_limiter.rs`、`runtime_validation.rs`、`sandbox_verification.rs`、`alert_engine.rs`
- **Agent 2**: 前端 UX 困惑点审计 — `errorText.js`、`actionFailure.js`、`i18n/index.js`、`en-US.js`、`router.js`、`tutorialSteps.js`、`App.jsx`、`graphStore.js`、`supportMatrix.js`、`runtimeGovernance.js`
- **Agent 3**: API 响应设计审计 — `app_router.rs`、`frontend_api_types.rs` (2019 行)、`cli_support.rs`、`capability_api.rs`、`api/client.js`、`graphStorePersistenceHelpers.js`
- **Agent 4**: QuantScript 编译器诊断审计 — `quantscript/src/diagnostics.rs`、`lowering/` 全部 13 个文件、`resolve.rs`、`analysis.rs`、`compile_diagnostics.rs`

共计发现 **79 项**用户困惑点，其中 S0 阻断 13 项，P1 高优 22 项，P2 中优 24 项，P3 低优 20 项。

---

## 原则

1. **GP §2.1 强制遵守**：所有用户可读文本必须是中文。代码标识符（诊断码、API 错误码、枚举变体名）保留英文
2. **GP §2.5 强制遵守**：前端用户可见字符串使用 `t()` 包裹，不可硬编码中文或英文
3. **只改消息内容和展示层**，不碰功能逻辑、业务流程、数据模型
4. **不引入新 npm 依赖**，不新增 API 路由
5. **向后兼容**：不改变 API 响应结构（error 字段名、JSON 形状）、不改变诊断码映射
6. 全量门禁持续通过：`cargo check` / `cargo test --workspace` / `npx vite build` / `npx vitest run`
7. 遵循超级规范化 §2.2 设计文档模板

---

## 非目标

- 不新增功能（无新 indicator、无新路由、无新页面）
- 不重构架构（不改变编译管道、不修改 Core IR 结构）
- 不履行翻译（en-US.js 补齐是后续里程碑的事）
- 不改变 API endpoint 命名（路由名称保持不变）
- 不修改 General_Policy.md 或超级规范化文档

## 设计决策纪录

### 决策 1: 错误消息语言策略

```
选项:
  A: 全部改为中文（严格 GP §2.1） — 优点: 统一，符合规范 / 缺点: 英文错误码丢失
  B: 保留诊断码英文、其余中文 — 优点: 协议标识符稳定 / 缺点: 存在混用边界

选择: B
理由: GP §2.1 明确"API 错误码保留英文（它们是协议标识符）"、"诊断代码保留英文"。
      文本消息、提示、建议全部改为中文。
影响: 34 处英文消息需要汉化，诊断码保持不变。
```

### 决策 2: en-US.js 补齐策略

```
选项:
  A: 本里程碑补齐全部 250 个缺失翻译 — 优点: 完整 / 缺点: 工作量巨大，与核心困惑点无关
  B: 本里程碑只修复结构性翻译缺失（如 capabilityMessage 硬编码英文不走 t()），
     补齐翻译留给后续里程碑 — 优点: 聚焦核心问题 / 缺点: 英文 UI 仍有中文

选择: B
理由: 本里程碑目标是消除"用户困惑"，核心是让中文用户看到一致的中文、英文用户至少
      不会看到中英混合。翻译补齐是纯工作量问题，不影响困惑度。
影响: 只修复 graphStore.js 中 3 处硬编码英文不走 t() 的问题。
```

### 决策 3: QS0609 代码冲突处理

```
选项:
  A: 修改 resolve.rs 中的 WARNING 使用新代码 QS0613 — 优点: 最小改动 / 缺点: 新增代码需注册
  B: 修改 analysis.rs 中的 ERROR 使用新代码 QS0613 — 优点: WARNING 变体更常用 / 缺点: ERROR 更严重应有独立代码

选择: A
理由: QS0609 在 analysis.rs 中作为 ERROR 使用，直接关联到"形式化 QuantScript 不支持
      可变列表"的语义，应保留 QS0609 作为错误。resolve.rs 中的 WARNING（重复变量定义）
      改用 QS0613，语义更清晰。
影响: 需更新 tools/check-i18n.ps1 中的诊断码列表。
```

### 决策 4: API 错误格式统一策略

```
选项:
  A: 定义一个 ApiErrorResponse struct，所有 handler 强制使用 — 优点: 完全统一 / 缺点: 改动 30+ handler
  B: 只修复最混乱的 5 处（裸字符串 → JSON），其余保持不变 — 优点: 改动小 / 缺点: 不彻底

选择: B
理由: 全量统一需要修改所有 handler 的错误返回签名，属于架构变更，超出本里程碑范围。
      本里程碑只消除最差的 5 处：compile_api.rs 的裸字符串、app_router.rs 的 not_found、
      auth_middleware.rs 的非 RFC 9457 格式、api_errors.rs 的 internal_error 丢弃根因。
影响: 前端 errorText.js 的 humanizeErrorText 需要增加对新格式的处理。
```

### 决策 5: 分页 total 信息保留策略

```
选项:
  A: fetchJson 不再自动解包，返回 {data, total} 结构 — 优点: 完整 / 缺点: 所有调用方需改
  B: fetchJson 保持自动解包，但单开一个 fetchJsonWithTotal 返回完整结构 — 优点: 向后兼容 / 缺点: API 分裂

选择: A
理由: 当前 fetchJson/postJson/deleteJson 三个函数中重复了相同的解包逻辑，且 total 被
      静默丢弃。统一改为不解包，由调用方显式取 data 字段。受影响调用方 ~30 处，通过
      全局搜索 `fetchJson(` / `postJson(` / `deleteJson(` 定位并修改。
影响: graphStoreHelpers.js、graphStorePersistenceHelpers.js、graphStoreCompileApi.js 等
      文件中所有直接使用 fetchJson 返回值的地方需要加 .data 访问。
```

```bash
# 门禁全量通过
cargo check --workspace

cargo clippy --workspace --all-targets -- -D warnings

npx vitest run

# 质量检查
grep -rn "bail!\|anyhow!\|\.map_err" src/ --include="*.rs" | grep -v target | grep -vi "error\|err\|io" | head -20
# → 所有 bail!/anyhow! 中的消息文本必须是中文

grep -rn "capabilityMessage.*'" frontend/src/ --include="*.js"
# → 不应包含硬编码英文（应通过 t() 包裹）

grep -rn "var(--tv-" frontend/src/pages/ --include="*.css"
# → 返回 0

grep -rn "QS0609" quantscript/src/ --include="*.rs"
# → 只在 analysis.rs 中出现一次（resolve.rs 已改为 QS0613）

grep -rn "format!(\"QS0502" quantscript/src/ --include="*.rs"
# → 返回 0（改用 Diagnostic::warning）
```
