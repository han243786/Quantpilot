# v4.1.0 规划方案 — v4 运行时加固 + P2 审计消化

> 版本类型: MINOR | 基准: v4.0.0 closeout (88306bf) | 终稿确认: 2026-05-24
> 来源: v4.0.0 V9 自由维度诱错审计 P2 发现 (9 项) + v4.0.0 规划文档 §非目标 延期项 + Phase 10 暗示

---

## 目标

v4.1.0 的目标是在 v4.0.0 架构主线上完成三项收敛：

1. **消化 v4.0.0 V9 审计的全部 P2 发现** — 静态校验、运行时验证、错误诊断码、版本一致性脚本补全
2. **加固 v4 运行时事件循环** — event payload 校验、memory 类型检查、guard 参数 fail-closed
3. **补齐 Phase 10 第一版** — v4 runtime 正式 CLI/UI 启动入口 + 条件单本地模拟补全

核心变化:

- v4 runtime 从"API/测试驱动"升级为"用户可在前端启动 v4 PaperSimulated 策略"
- event payload 按 MachineEventCatalog 校验，不满足 required/nullable/type 则拒绝
- memory 字段类型不再作为字符串透传，改用 QsTypeRef 校验
- 错误响应统一携带稳定诊断码
- 版本一致性检查覆盖 release manifest、OpenAPI、启动横幅

## 非目标

- 不在 v4.1.0 开放嵌套状态机 (仍为 reserved)
- 不实现逐 tick 完全复现 (仍为后续增强)
- 不新增订单能力类型 (24 种第一波保持)
- 不把学习流水线扩展到所有协作者 (仍只服务 owner)
- 不改变 V1 QS 保留面
- 不新增 MAJOR 演化 Phase

## W1 — P2 审计消化 (2.5 天)

### W1-1 错误响应统一携带诊断码

**严重度**: P2
**来源**: V9 P2-7
**文件**: `src/api_errors.rs:51`

**现状**: `json_bad_request(...)` 等默认错误 helper 将 `error_code` 固定为 `None`，前端和日志无法按稳定诊断码做分类处理。

**方案**:
1. 在 `src/error_codes.rs` 中为 v4 新增的 API 路径注册诊断码
2. 默认 helper 强制传入或自动派生 `error_code`
3. 中文 message 保持用户展示，诊断码用于程序处理

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/api_errors.rs` | `json_bad_request()` / `internal_error()` 签名增加 `error_code: &str` 参数 |
| 2 | `src/error_codes.rs` | 注册 v4 runtime/compile/executor 诊断码段 |
| 3 | `src/compile_api.rs` 等调用处 | 传入对应诊断码 |

**约束**: GP §4.2 (错误变更测试修复), GP §2.1 (中文消息)
**验收**: `curl -X POST /api/runtime/compile -d '{}'` → 响应包含 `"error_code":"QSCxxxx"`

### W1-2 告警 acknowledge 404 返回 404 状态码

**严重度**: P2
**来源**: V9 P2-8
**文件**: `src/alert_engine.rs:169`

**现状**: acknowledge 不存在告警时返回 `json_bad_request("not_found", ...)`，HTTP 状态 400。应返回 404。

**方案**: 增加 `json_not_found` helper，返回 404 + 结构化错误体。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/api_errors.rs` | 新增 `json_not_found(error_code, message)` |
| 2 | `src/alert_engine.rs:169` | 替换为 `json_not_found("ALERT_NOT_FOUND", ...)` |

**约束**: GP §4.2, §4.4
**验收**: `POST /api/v1/alerts/:id/acknowledge` 不存在 ID → HTTP 404

### W1-3 启动脚本版本横幅同步

### W1-4 回测 equity_curve 非单调防御

**严重度**: P2

## W2 — 运行时加固 (1.5 天)

### W2-1 event payload 按 MachineEventCatalog 校验

**严重度**: P2
**来源**: V9 P2-4
**文件**: `qrpc_runtime/src/v4_runtime.rs:914`

**现状**: runtime transition 只看 `event_type/source/freshness`，不按 `MachineEventCatalog.payload_fields` 校验 required/nullable/type。payload 字段缺失或类型不匹配时静默通过。

**方案**: 在 `submit_event` / `process_event` 中按 event catalog 校验 payload：
- required 字段缺失 → 拒绝事件，记录 `V4RuntimeEventRejected`
- 字段类型不匹配 → 拒绝
- nullable 字段为 null → 允许

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_runtime/src/v4_runtime.rs` | `process_event` 开始处增加 `validate_event_payload()` |
| 2 | `qrpc_core_ir/src/v4.rs` | 增加 `V4RuntimeEventRejected` 事件类型和 rejected event 记录 |
| 3 | `frontend/src/components/V4RuntimeEvidencePanel.jsx` | 展示 rejected event 信息 |

**约束**: GP §1.8 (状态迁移事件驱动可解释), GP §5.2 (禁止静默忽略参数)
**验收**: 发送缺少 required 字段的事件 → runtime 拒绝 + 事件日志记录 rejected event

### W2-2 memory 字段类型用 QsTypeRef 校验

**严重度**: P2
**来源**: V9 P2-2
**文件**: `quantscript/src/v4_static_audit.rs:542`, `qrpc_core_ir/src/v4.rs:283`

**现状**: QS `memory <name>: <type>` 的 type 作为字符串透传，Core IR 只检查非空。`memory foo: made_up` 可通过所有校验。

**方案**: 将 memory type 解析为 `QsTypeRef`，在静态审计阶段校验类型是否在类型系统契约中声明。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `quantscript/src/v4_static_audit.rs` | `parse_memory_declaration()` 调用 `parse_qs_type_ref()` |
| 2 | `qrpc_core_ir/src/v4.rs` | `MachineMemoryField.type_name` 改为 `Option<QsTypeRef>` 或增加 `type_ref` 字段 |
| 3 | `quantscript/src/v4_static_audit.rs` | 新增 QSV4117 诊断码: memory 类型不在类型系统中 |

**约束**: GP §1.7 (QS DSL 不是通用语言), GP §1.2 (跨三层验证)
**验收**: `memory foo: made_up` → QSV4117 诊断拒绝

### W2-3 memory_writes 静态校验

**严重度**: P2
**来源**: V9 P2-1
**文件**: `qrpc_core_ir/src/v4.rs:246`, `qrpc_runtime/src/v4_runtime.rs:982`

**现状**: `MachineActionSpec.memory_writes` 未校验是否属于本 machine 声明的 memory 字段。runtime 只要 payload 有同名 key 就写入，可写入未声明字段。

**方案**:
1. Core IR 静态校验: `memory_writes ⊆ machine.memory.name`
2. Runtime 写入前按声明字段再次过滤，拒绝未知字段

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core_ir/src/v4.rs` | `V4MachineContract::validate_static_contract()` 增加 memory_writes 校验 |
| 2 | `qrpc_runtime/src/v4_runtime.rs` | `process_event` memory 写入前校验字段名 |

**约束**: GP §1.7, §5.2 (禁止静默忽略)
**验收**: transition 声明 `write foo` 但 machine 未声明 `memory foo` → 静态校验失败

## W3 — v4 用户入口 + 条件单补全 (1.5 天)

### W3-1 v4 runtime 前端启动入口

**来源**: v4.0.0 规划文档 Phase 10 暗示

**现状**: v4 PaperSimulated runtime 只能通过 Rust 测试和 API 调用，用户在 UI 中无法直接启动 v4 策略。

**方案**: 在策略工作区增加 v4 runtime 启动触发路径：
- 编译 v4 QS 脚本通过静态审计后，`V4QsRuntimeHandoffReport.accepted_for_runtime_handoff=true` 时启用"v4 模拟运行"按钮
- 后端增加 `POST /api/runtime/v4/run` 端点
- 前端监控面板展示 v4 runtime evidence

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/app_router.rs` | 新增 `/api/runtime/v4/run` 路由 |
| 2 | `src/runtime/` | 新增 v4 run handler，创建 `V4PaperSimulatedRuntime` 实例 |
| 3 | `frontend/src/components/TopToolbar.jsx` | 增加 `start_v4_simulation` 动作 |
| 4 | `frontend/src/hooks/workspaceActionBarShared.js` | 增加 `canStartV4Simulation` 逻辑 |

**约束**: GP §1.12 (前端入口由后端 capability 驱动)
**验收**: 编译 v4 QS 通过 → "v4 模拟运行"按钮可用 → 点击后在 MonitorTab 看到 v4 evidence

### W3-2 v4 CLI 启动入口

**来源**: v4.0.0 规划文档 Phase 10 暗示

**方案**: `cargo run --bin quantpilot -- v4-run <graph_id>` 从 CLI 启动 v4 PaperSimulated 策略。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/cli_support.rs` | 增加 `v4-run` 子命令 |
| 2 | `src/main.rs` 或 `src/lib.rs` | CLI 参数解析增加 v4-run 分支 |

**验收**: `cargo run -- v4-run <graph_id>` → v4 runtime 启动并输出事件

### W3-3 条件单本地模拟补全

**来源**: v4.0.0 规划文档 Phase 10 暗示

**现状**: v4 模拟撮合引擎已支持 Market/Limit/FOK，但 stop-market/stop-limit/take-profit-market/take-profit-limit 的触发逻辑未完整实现。

**方案**:
- `V4SimulatedExecutionRuntimeState` 增加条件单触发检查
- 每次 `update_simulated_market_price` 时检查 stop/take-profit 触发价格
- 触发后按条件单语义转为市价/限价单执行

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_runtime/src/v4_runtime.rs` | 增加 `check_conditional_order_triggers()` |
| 2 | 同上 | stop-market/stop-limit/take-profit 触发逻辑 |
| 3 | 同上 | 触发后订单状态转换和事件记录 |

**约束**: GP §1.10 (Execution 能力来源必须显式标记 — 条件单为 `runtime_simulated`)
**验收**: 部署含 stop-loss 的 v4 策略 → 价格触及止损价 → 触发市价平仓 → 事件/面板可观测

## 兼容性与迁移

- **现有 v1/v3 QuantScript 保留面不迁移**: v4.1.0 的 `memory` 类型解析和 `memory_writes` 校验只作用于 v4 状态机 DSL；旧 `fn strategy()` 保留面继续走既有 lowering。
- **现有运行/回测记录不迁移**: 新增 `/api/runtime/v4/run` 生成独立 v4 handoff/output，不改变既有 run/backtest artifact schema；历史记录按 safe default 读取。
- **前端 capability 向后兼容**: 新增 `start_v4_simulation` 为 additive action；旧前端缺失该 action 时只隐藏 v4 模拟入口，不影响 compile/start_simulation/run_backtest。
- **执行端不迁移**: 条件单补全仅在 v4 PaperSimulated runtime 本地撮合层生效，不改 `src-executor` OKX Paper/Live ProviderNative 路径。
- **版本元数据统一迁移**: Cargo/Tauri/package/lockfile/release manifest/OpenAPI/start banner 统一到 `v4.1.0`，由 `tools/check-version-consistency.ps1` 阻断漂移。
