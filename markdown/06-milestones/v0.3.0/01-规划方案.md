# QuantPilot v0.3.0 规划方案（讨论稿 v3） — 22 项

> **核心原则**：
> 1. QS 是策略图生成的**唯一路径**——graph 前端降级为可视化/编辑层
> 2. 文档中声明的功能**必须全部可用**
> 3. 以下**不得**宣称为产品能力：实盘交易（真实资金）、研究级回测语义、套利平台、第三方插件市场、通过 QuantScript 执行任意宿主代码
> 4. 交易所**模拟盘/测试网**交易属于 v0.3.0 范围——它与实盘共享 API 规则但无资金风险

## 一、架构定调：QS 作为唯一策略定义路径

### 当前问题

v0.2.0 中存在两条编译路径：

```
路径A（Graph）: 前端拖拽 → FrontendRuntimeConfig → map → compile → sandbox
路径B（QS）  : .qs 源码 → lower_script_to_runtime_config → compile → sandbox
```

两条路径产出不同的 intent 类型（`double_ma` vs `LongTermBuy`），行为不一致。

### v0.3.0 目标

```
QS 源码 (.qs) ──→ 解析/分析/校验 ──→ lowering ──→ Core IR ──→ sandbox
                                        │
                        前端 graph 编辑器 ←── 可视化/编辑
                                        │
                        Playwright ←── data-testid 交互
```

Graph 编辑器不再有独立的编译路径。前端保存策略图时，本质是保存对应的 QS 源码。`POST /api/runtime/compile` 内部调用 QS 编译。

## 三、优化项清单

### P0 — 正确性（3 项）

#### P0-1 QS SMA lowering 对齐

**理由**：QS 是唯一策略路径。`sma()` → `LongTermBuy` → 0 fills 意味着所有 SMA 策略不可用。这是阻塞性缺陷。

**方案**：在 `lowering/intents.rs` 中识别 `sma()` + `emit Intent` 模式，生成与 graph `double_ma` 等效的 intent 配置。

| 文件 | 改动 |
|------|------|
| `quantscript/src/lowering/intents.rs` | 新增 `detect_sma_crossover_pattern()` |
| `quantscript/src/lowering/orchestrator.rs` | 在 `infer_intents` 中调用 |

**验收**：`scenario_01_btc_dual_ma.qs` 回测 `total_fills > 0`

#### P0-2 `backtest.metrics.win_rate` 补充

**理由**：文档 §4.2 声明了此断言，但从未实现。

**方案**：在 `execute_backtest_core` 中统计盈亏交易数。

```rust
let (win_count, loss_count): (usize, usize) = fills.iter().fold(...);
let win_rate = if win_count + loss_count > 0 {
    win_count as f64 / (win_count + loss_count) as f64
} else { 0.0 };
```

**验收**：`@assert backtest.metrics.win_rate >= 0` → passed

#### P0-3 断言失败显示 actual 值

**理由**：当前 `assert failed: run.equity > 0` 不显示实际值，需翻 data_snapshot 诊断。

**方案**：失败消息中嵌入 actual。

```
assert failed: run.equity > 0 (actual: -150.32)
```

**验收**：失败消息包含 `(actual: ...)`

### P1 — 完整性（4 项）

#### P1-1 回测对比断言 `@compare`

**理由**：文档提到的核心能力。参数修改后需要对比两次回测。

**方案**：

```
@step("A") { @backtest { source: "deterministic_mock", seed: 7 } }
@step("B") { @backtest { source: "deterministic_mock", seed: 42 } }
@step("对比") { @compare { left: 0, right: 1 }
               @assert compare.net_profit_diff != 0 }
```

| 文件 | 改动 |
|------|------|
| `quantscript/src/test_plan.rs` | 新增 `TestActionDef::Compare` |
| `src/test_runner.rs` | 实现 `Compare` 分支，从 `backtest_history` 取两次指标比较 |

**验收**：两次不同 seed 的回测对比输出 `net_profit_diff != 0`。

#### P1-2 `compile.counts` 真实值暴露

**理由**：当前 `compile.counts.data_sources >= 1` 只检查 compile_result 是否存在，不读真实值。

**方案**：`evaluate_assert` 读取 `compile_result` 中的实际 counts 进行数值比较。

**验收**：`@assert compile.counts.data_sources == 1` → passed（精确匹配）

#### P1-3 `@backtest` 保存到正式存储

**理由**：`@save_run` 写入 `storage/test-runs/`，但正式回测 API 写入 `storage/backtests/`。两份数据不互通。

**方案**：`@backtest { save: true }` 时调用 `runtime_persistence` 写入正式目录。

**验收**：`storage/backtests/` 下出现持久化文件。

#### P1-4 Mock 数据可配置波动率

**理由**：当前所有 SMA 参数给出相同结果。可配置波动率后，参数调优才有意义。

**方案**：`@backtest { volatility: 1.5, regime_count: 4 }` 控制 mock 行为。

| 参数 | 默认 | 说明 |
|------|:--:|------|
| `volatility` | 0.5 | 日波动率 % |
| `regime_count` | 4 | 行情阶段数 |

**验收**：`volatility: 2.0` 的回测结果与 `volatility: 0.5` 不同。

### P3 — 模拟盘交易 + API 密钥安全（3 项）

#### P3-1 交易所模拟盘执行模块

**理由**：v0.2.0 的 `@run { mode: "paper" }` 在进程内模拟成交，不连接真实交易所。模拟盘（testnet）与实盘共享 API 规则、订单簿深度、手续费结构，只是资金为虚拟——是验证策略在真实市场环境中行为的最低风险方式。

**实现差异**：

| 维度 | Paper (v0.2.0) | Testnet (v0.3.0) |
|------|:---:|:---:|
| 市场数据 | deterministic_mock | 交易所实时 WebSocket |
| 订单成交 | 本地简易撮合 | 交易所撮合引擎 |
| 资金 | 虚拟初始余额 | 模拟盘虚拟余额 |
| 延迟 | 0 | 真实网络延迟 |
| API 密钥 | 不需要 | 需要 |

**方案**：

```
@run { mode: "testnet", exchange: "binance", duration: 3600s }
```

| 文件 | 改动 |
|------|------|
| `qrpc_runtime/src/execution_module.rs` | 新增 `TestnetExecutionModule`，调用交易所 REST API 下单 |
| `qrpc_runtime/src/data_module.rs` | 新增 `LiveDataModule`，通过 WebSocket 订阅实时行情 |
| `src/test_runner.rs` | `mode == "testnet"` 时加载密钥、创建对应模块 |
| `quantscript/src/script.rs` | parser 接受 `mode: "testnet"` |

**边界**：
- 仅支持 Binance Testnet（`testnet.binance.vision`）
- 仅 Spot 市场
- flag=0 标识模拟盘环境
- 明确标注 "模拟盘交易，非实盘"

**验收**：`@run { mode: "testnet", exchange: "binance", duration: 60s }` → 订单出现在 Binance Testnet 的未成交列表。

#### P3-2 API 密钥安全存储

**理由**：模拟盘需要 exchange API key/secret。明文存储或日志泄露会导致密钥被盗——即使是测试网密钥也可能被用于刷量等滥用。

**安全模型**：

```
┌─ 环境变量 ─────────────────────────────────┐
│ QUANTPILOT_EXCHANGE_KEY=xxx                │ ← 运行时注入，不落盘
│ QUANTPILOT_EXCHANGE_SECRET=xxx             │
├─ 内存 ────────────────────────────────────┤
│ 密钥仅在 TestnetExecutionModule 创建时读取  │
│ 用完即丢弃字符串，不留副本                   │
├─ 日志/API 响应 ───────────────────────────┤
│ 任何输出中 key/secret 替换为 "***"          │
│ TestReport 不含密钥字段                     │
├─ 存储 ────────────────────────────────────┤
│ 密钥不入 storage/ 目录                      │
│ .gitignore 已排除 .env                      │
└───────────────────────────────────────────┘
```

| 文件 | 改动 |
|------|------|
| `src/test_runner.rs` | `load_exchange_credentials()` — 从环境变量读取，立即消费 |
| `src/api_test_scenario.rs` | 响应中排除所有密钥相关字段 |
| `.env.example` | 新增 `QUANTPILOT_EXCHANGE_KEY` / `QUANTPILOT_EXCHANGE_SECRET` 模板 |

**验收**：
- 环境变量未设置时 → `mode "testnet" requires QUANTPILOT_EXCHANGE_KEY and QUANTPILOT_EXCHANGE_SECRET`
- 密钥不会出现在 `/api/test/scenario/run` 的响应中
- 密钥不会出现在后端 stderr 日志中

#### P3-3 模拟盘风险护栏

**理由**：即使模拟盘无资金风险，仍需防止策略失控（无限循环下单、天量请求触发交易所 rate limit）。

**方案**：在 TestnetExecutionModule 中内置硬限制：

| 护栏 | 值 | 说明 |
|------|:--:|------|
| 最大下单频率 | 1 req/s | 超过返回 `rate_limited` |
| 最大持仓市值 | 初始余额 × 3 | 防止杠杆失控 |
| 单笔最大数量 | 初始余额 × 0.1 | 单笔不超过 10% |
| 最长运行时间 | 3600s | `@run` 的 duration 上限 |
| 最大连续错误 | 10 次 | 超过自动停止 |

**验收**：连续 11 次错误 → `testnet aborted: too many consecutive errors (10)`

## 四、信号体系扩展 + 自定义计算

### 设计原则（采纳专家建议）

新增信号遵循业界公认的**四大分类 + 三项原则**：

```
四大分类
  ├── 趋势类（判断方向）：SMA, EMA, MACD, ADX, 布林带, Parabolic SAR
  ├── 动量类（判断力度）：RSI, Stochastic, CCI, Williams %R, ROC
  ├── 波动率类（判断活跃度）：ATR, 布林带宽度, Keltner 通道, 标准差
  └── 成交量类（确认可信度）：OBV, CMF, VWAP, MFI

三项原则
  ├── 高度常用 → 出现在绝大多数策略中
  ├── 可组合   → SMA + RSI + ATR = 趋势 + 超卖 + 止损
  └── 原子化   → 每个信号只做一件事，不重叠
```

**相关性警示**：均线交叉和 MACD 信号来源相近（都基于价格平滑），同时使用容易双赔。组合时选择**逻辑来源互补**的信号，而非重复信号。

### 现有信号（v0.2.0）

| 信号 | 分类 | QS 语法 |
|------|:--:|---------|
| SMA 双均线 | 趋势 | `sma()` + `emit Intent` |
| RSI | 动量 | `rsi()` |
| MACD | 趋势/动量 | `macd()` |
| Momentum | 动量 | `momentum()` |
| Z-Score | 均值回归 | `zscore()` |

### 入门六核心（P4 — 必做，6 项）

目标是让用户能用 6 个核心信号搭建出大部分常见策略。

| # | 信号 | 分类 | 一句话用途 | v0.2.0 |
|---|------|:--:|--------|:--:|
| 1 | **EMA** | 趋势 | 对近期价格更敏感的均线 | ❌ |
| 2 | **MACD** | 趋势/动量 | 零轴方向 + 柱状图动能 + 交叉信号 | ✅ |
| 3 | **RSI** | 动量 | 超买超卖 + 背离 | ✅ |
| 4 | **ATR** | 波动率 | 动态止损/止盈的"元工具" | ❌ |
| 5 | **布林带** | 趋势/波动率 | 动态支撑阻力，超买超卖 | ❌ |
| 6 | **OBV/CMF** | 成交量 | 量价背离，假突破过滤器 | ❌ |

### 进阶扩展（P5 — 6 项）

入门六核心完成后，补充以下信号达到 12~15 个原子的覆盖度。

| # | 信号 | 分类 | 一句话用途 |
|---|------|:--:|--------|
| 7 | **ADX** | 趋势 | 衡量趋势强度，不判断方向——用于识别趋势/震荡市场状态切换 |
| 8 | **Stochastic** | 动量 | 超买超卖，震荡市表现优于 RSI |
| 9 | **CCI** | 动量 | 测量价格偏离统计均值的程度 |

|---------|------|------|--------|--------|

### 组合方法论（文档化，不入代码）

以下方法论写入 `markdown/guides/signal-combination-guide.md`，供用户参考，不强制代码实现：

1. **条件叠加（规则类）**：`MACD 金叉 AND RSI > 50 AND 成交量放大`
2. **加权评分**：各指标分别输出 0~1 分数，加权求和（可根据波动率动态调整权重）
3. **IC/IR 框架**：Information Coefficient 衡量单信号预测排序相关性，Information Ratio 衡量体系综合表现。主动管理基本定律 `IR = IC × √N` 表明——信号数量越多、质量越高，整体策略的稳健性越强


### P6 — 自定义信号计算 + 调试（2 项）

#### P6-1 用户自定义公式信号

**理由**：内置信号永远无法覆盖所有策略。用户应能写出任意公式，系统将其 lowered 为合法的 Core IR indicator。只要符合底层协议即可。

**约束**：
- 公式必须基于已有数据源（fetch 的结果）
- 公式必须输出一个标量值
- 公式不能包含循环、递归、外部调用
- 公式的 Core IR 表示需满足底层协议的 indicator 格式
- **参数过拟合风险由用户自行管理**（建议留出样本外验证）

```qs
fn strategy() {
    let closes = fetch("BTCUSDT", interval="1d", lookback=100)?

    # 自定义：RSI 背离（RSI 上升但价格下降 = 底背离）
    let rsi_val = rsi(closes, 14)
    let rsi_rising = rsi_val > rsi_val[1]
    let price_falling = closes.last() < closes[1]
    let bull_divergence = rsi_rising && price_falling

    # 自定义：ATR 动态仓位（波动率越高仓位越小）
    let atr14 = atr(highs, lows, closes, 14)
    let dynamic_qty = 0.01 * (1.0 / (atr14 / closes.last()))

    if bull_divergence {
        emit Intent("BUY", instrument="BTCUSDT", quantity=dynamic_qty)
    }
}
```

## 五、图编辑器修复 + QS→Graph 合规（P6 — 2 项）

#### P6-1 修复 Handle 端点无法连接

**验证结果**：`node_runtime_8`（运行控制节点）的 inputPorts 和 outputPorts 均为空数组，导致 Handle 组件不渲染。这是 `BaseNodeCard` 未为该节点类型生成端口数据——很可能是 `StrategyCanvas.jsx` 的 `nodeTypes` 映射中缺少对应的 `data` prop 配置。

**方案**：

| 步骤 | 文件 | 改动 |
|------|------|------|
| 1 | `frontend/src/components/StrategyCanvas.jsx` | 排查 `runtime` 节点类型的端口生成逻辑 |
| 2 | `frontend/src/nodes/BaseNodeCard.jsx` | 若 `inputPorts`/`outputPorts` 为空 → 至少渲染一个默认 Handle（不可连接也比不可见好） |
| 3 | Playwright 测试 | 新增连线专项测试：遍历所有节点类型，验证至少有一个 source handle 和一个 target handle |

**验收**：画布上每个节点都有可见的 Handle 端口圆点。

#### P6-2 QS 编译产出合法策略图

**理由**：QS 是唯一策略路径。`@compile` 成功后，前端必须能加载对应的策略图（`/strategies/:id`），用户可以可视化看到 QS 定义的节点和连线。

**当前差距**：QS lowering 产出 `RuntimeProtocolCoreConfig` → Core IR → sandbox 可运行，但未生成对应的 `FrontendRuntimeConfig` 并保存到 graph store。前端无法加载 QS 策略的图表示。

**方案**：

| 步骤 | 文件 | 改动 |
|------|------|------|
| 1 | `src/test_runner.rs` | `@compile` 成功后，调用 `frontend_runtime_config_from_core_with_template` + `POST /api/graphs/save` 持久化策略图 |
| 2 | `src/api_test_scenario.rs` | 响应中增加 `graph_id` 字段 |
| 3 | `frontend` | 已有加载逻辑——仅需 graph_id 对应到已保存的策略图即可 |
| 4 | Playwright 测试 | 验证 `@compile` 后前端 `/strategies/:id` 可加载完整的节点+连线图 |

**验收**：
```
@compile → compile: ok, graph_id=saved_graph_xxx
浏览器打开 /strategies/saved_graph_xxx → 画布显示 QS 中定义的节点和连线
```
