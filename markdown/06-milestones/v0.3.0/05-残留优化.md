## R0 — 信号正确性（2 天）

### R0-1 新信号不再借壳现有 IntentKind

**现状**：`qrpc_runtime/src/intent_module.rs` 中 BollingerBands/Stochastic/CCI → `IntentKind::Rsi`，OBV/CMF/ADX → `IntentKind::Momentum`。RSI 的超买超卖阈值（30/70）对布林带/CCI 毫无意义，用户写 `if bb.upper < close` 时触发的是 RSI 语义。

**方案**：为 10 个新信号各自定义正确的阈值语义。不需要新增 `IntentKind` 变体——在 `IndicatorNode.params` 中携带 `intent_variant` 和阈值参数，evaluator 函数已经各自实现了正确的 side/strength 判断。`intent_module.rs` 只需确保 params 正确传递即可。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_runtime/src/intent_module.rs` | 每个新 CoreIndicatorKind 映射到 `IntentKind::Rsi` 或 `IntentKind::Momentum`，但注入正确的参数覆盖（oversold_threshold/overbought_threshold 等） |
| 2 | `quantscript/src/lowering/intents.rs` | 为每个新指标类型生成准确的 intent params（如 BollingerBands → `entry_ratio=1.0` 表示价格触及 band） |

**验收**：
```
// 布林带策略回测
@test { name: "R0-1 布林带" }
@step("编译") { @compile @assert compile.compilable == true }
@step("回测") { @backtest { source: "deterministic_mock" } @assert backtest.metrics.total_fills > 0 }
// 应该产生与 RSI(30/70) 不同的 fill 模式
```

### R0-2 10 个新信号 evaluator 的 smoke test

**现状**：`core_ir_evaluator.rs` 的 tests 模块不含任何新 evaluator 的测试。11 个计算函数（`true_range`、`bollinger_bands`、`stochastic_oscillator` 等）的数学正确性完全未经验证。一次重构或浮点行为变更就能静默破坏所有新信号。

**方案**：为每个新计算函数各写 1 个 smoke test：构造 30 bar 的模拟 kline 数据，验证输出落在合理范围。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_runtime/src/core_ir_evaluator.rs` tests | `test_true_range_normal_case` — 验证 TR 恒为正 |
| 2 | 同上 | `test_bollinger_bands_output_range` — close 在上/下轨之间 |
| 3 | 同上 | `test_stochastic_oscillator_k_is_percentage` — %K 在 [0, 100] 内 |
| 4 | 同上 | `test_adx_positive_di_plus_minus_di_equals_100` — +DI + -DI ≈ 100 |
| 5 | 同上 | `test_cci_oscillates_around_zero` — 平稳序列 CCI ≈ 0 |
| 6 | 同上 | `test_parabolic_sar_flips_on_extreme_move` — 极端行情 SAR 翻转 |
| 7 | 同上 | `test_keltner_channel_upper_above_middle_above_lower` — upper > middle > lower |
| 8 | 同上 | `test_donchian_channel_upper_is_period_high` — upper == max(high) |
| 9 | 同上 | `test_obv_accumulates_on_uptrend` — 持续上涨时 OBV 单调递增 |
| 10 | 同上 | `test_cmf_positive_when_close_near_high` — close == high 时 CMF > 0 |

**验收**：
```
cargo test --package qrpc-runtime -- core_ir_evaluator
→ 10/10 new tests passed
```

### R0-3 @debug 收集真实 per-bar 变量值

**现状**：`@debug` 只从 `backtest.equity_curve` 提取 bar 数据，所有用户变量列都是 `null`。前端调试标签页看到的是空表。文档承诺的是"指定变量的 per-bar 值（如 `rsi_val` 每 bar 的实际计算结果）"，sandbox 不暴露此数据。

**方案**：在 `FastBacktestSandbox` 中新增 `debug_var_names: Vec<String>` 字段和 `debug_bars: Vec<BTreeMap<String, f64>>` 字段。每个 bar 推进时，调用 evaluator 计算指定变量的当前值并记录。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_runtime/src/sandbox.rs` | `FastBacktestSandbox` 新增 `debug_var_names` / `debug_bars` 字段 + getter |
| 2 | `src/test_runner.rs` | `@debug` → 在创建 sandbox 前注入 `debug_var_names`；回测后从 sandbox 读取 `debug_bars` |
| 3 | `frontend/src/pages/StrategyWorkspaceDebugTab.jsx` | 移除对 null 列的处理，所有列都有真实值 |

**验收**：
```
@debug(closes, fast, slow)
@backtest { source: "deterministic_mock" }
→ 切换到调试标签页 → 表格每列显示真实数值（非 null）
→ SVG 折线图有实际曲线
```

## R2 — 架构收敛（1.5 天）

### R2-1 合并双编译路径

**现状**：v0.3.0 规划明确"QS 是唯一策略定义路径"，但 `POST /api/runtime/compile`（Graph → FrontendRuntimeConfig → compile）和 QS lowering 路径（QS → HIR → Core IR → compile）仍然并存。两条路径产出不同的 intent 类型和参数语义，未来任一边改动都可能再次导致行为不一致。

**方案**：Graph 编译路径内部改为先生成 QS 源码（`generate_quantscript_from_graph_value`），再走 QS lowering 管线。前端保存策略图时，本质是保存对应 QS 源码，编译走同一条路。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/graph_api.rs` 或新 compile 端点 | Graph compile → 内部调用 `generate_quantscript_from_graph_value` → QS parse → lowering → Core IR → sandbox |
| 2 | `src/frontend_runtime_mapping.rs` | 标记为 deprecated，Graph 路径不再直接生成 FrontendRuntimeConfig |
| 3 | 测试 | `@compile`（QS 路径）与 Graph compile（前端路径）产出相同的 Core IR 结构 |

**验收**：
```
同一个策略：
  前端拖拽编译 → 回测 fills 数 = QS @compile → 回测 fills 数
```

---

### R2-2 保存时保留原始 QS 源码

**现状**：`persist_graph_version` 调用 `generate_quantscript_from_graph_value` 从 graph JSON 重新生成 QS，覆盖原始 `.qs` 文件。用户手写的注释、复杂表达式、自定义变量名全部丢失。

**方案**：`.qs` 文件分为两种保存模式：如果 graph 有 `source_mode: "quantscript"` 且原始源码存在，保留原始源码；仅在 `source_mode: "graph"`（纯前端拖拽）时重新生成。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/graph_api.rs:persist_graph_version()` | 检查 metadata.source_mode；若为 "quantscript"，保留原 .qs 文件内容 |
| 2 | 同上 | 将 graph JSON 变更反向合并到 QS 源码中（参数值更新、连线变更），而非全文重新生成 |

**验收**：
```
1. QS 编辑器写策略（含注释 "// 自定义止损"）
2. @compile → 生成图 → 前端打开 → 手动改连线 → 保存
3. 打开源码标签页 → 注释 "// 自定义止损" 仍在
```

### R2-3 @modify node="" 空字符串防误解

**现状**：我刚修了 `@modify { node, param, value }` 支持按 node_id 限定范围。但当 `node_id.is_empty()` 时，修改仍然应用到**所有**同类型节点。用户如果忘了写 node 字段（`@modify { param: "fast_period", value: 10 }`），所有 intent 的 fast_period 都会被改。

**方案**：`node_id.is_empty()` 时返回 warning，不应用修改；或在 TestReport 中标注 "applied to N nodes"。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/test_runner.rs:compile_strategy()` | `node_id.is_empty()` → 收集所有匹配节点 ID 列表，在消息中标注 "modify applied to N intents: [id1, id2, ...]" |

**验收**：
```
@modify { param: "fast_period", value: 10 }
→ 消息: "modify: fast_period=10 applied to 2 intents: [intent_1, intent_2]"
→ 用户能明确知道影响了哪些节点
```

---

### R2-4 testnet 执行模块持续运行

**现状**：`execute_testnet_run` 只下一笔单就返回。文档承诺"60 分钟持续运行"、"WebSocket 实时行情订阅"均未实现。函数签名的 `duration_secs` 虽然已接入但只用作守卫，不控制运行时长。

**方案**：在 `duration_secs` 时长内，循环拉取行情并根据策略信号下单。使用 REST 轮询替代 WebSocket（WebSocket 依赖 `reqwest` 异步运行时，是独立基础设施回合）。

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `src/test_runner.rs:execute_testnet_run()` | `for _ in 0..cycles` 循环：获取行情 → 评估策略信号 → 下单 → sleep 间隔 |
| 2 | 同上 | 每 10 次迭代输出一次状态摘要（余额、持仓、累计成交数） |

**验收**：
```
@run { mode: "testnet", duration: 60s }
→ OKX Testnet 订单列表出现多笔订单（非单笔）
→ 最后输出: "testnet: 60s completed, 5 orders placed, equity=100123.45"
```
