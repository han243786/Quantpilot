## P1 — 审计阻断 (10项, 预计 9.5 人日)

### P1-1: rotate_refresh_token 无事务保护

**严重度**: P1
**来源**: 审计维度D+E
**策略**: GP §9.2（数据写入原子性 — 关键状态变更必须事务保护）
**问题**: `auth/mod.rs` 中 `rotate_refresh_token` 函数的DELETE旧token和INSERT新token不在同一SQLite事务中。异常路径下：若DELETE成功但INSERT失败，用户永久丢失会话；若并发请求交错，可能产生重复token或token族分裂。
**方案**:
1. 在 `auth/mod.rs` 中将DELETE和INSERT包裹为 `rusqlite::Transaction`
2. 使用 `conn.execute_batch("BEGIN; DELETE ...; INSERT ...; COMMIT;")` 确保原子性
3. 为事务添加超时保护（5s），超时自动ROLLBACK
4. 添加单元测试：在INSERT步骤注入错误，验证DELETE被回滚
**验收**: 注入INSERT失败 → token表中该用户仍有旧token（事务回滚）；正常路径 → 新旧token正确替换
**依赖**: 无
**工时**: 1.5 人日

### P1-2: is_condition_resolved 忽略 resolve_condition 字段

**严重度**: P1
**来源**: 审计维度A
**策略**: GP §9.3（告警引擎 — 每条告警规则必须有可执行的恢复条件）
**问题**: `alert_engine.rs` 中 `is_condition_resolved` 函数硬编码 `data_freshness < 60` 阈值，完全忽略 `AlertRule.resolve_condition` 字段。用户自定义恢复条件永不生效，告警只能手动ack解除。
**方案**:
1. 修改函数签名：`is_condition_resolved(rule: &AlertRule, metrics: &HashMap<String, f64>) -> bool`
2. 优先评估 `rule.resolve_condition` 表达式（复用已有的表达式解析器）
3. `resolve_condition = None` 时回退硬编码阈值（兼容已有数据）
4. 表达式解析异常时记录 `warn!` 日志，返回 `false`（安全降级）
5. 添加单元测试：自定义条件 vs 默认条件的对比验证
**验收**: 创建 `resolve_condition = "data_freshness < 120"` 的规则 → 触发后 metrics 降至 120 以下 → 自动 Resolved；无 resolve_condition 的规则行为不变
**依赖**: 无
**工时**: 1 人日

### P1-3: 编译缓存 key 含 compile_id 致缓存失效

**严重度**: P1
**来源**: 审计维度A
**策略**: GP §5.4（缓存有效性 — 缓存key不可包含每次变化的量）
**问题**: `compile_api.rs` 中编译缓存的key包含了 `compile_id`（每个编译请求的自增ID）。因 `compile_id` 每次不同，相同策略图的每次编译都命中不同key，缓存永不生效，所有编译请求均全量执行QS管道。
**方案**:
1. 重新定义缓存key结构：`CacheKey { graph_hash: String, compile_options_hash: String }`
2. 从key中移除 `compile_id`（保留在缓存value的元数据中供审计追踪）
3. 清理因key变更产生的旧缓存条目
4. 添加缓存命中/未命中的 metrics 计数
**验收**: 相同策略图连续编译2次 → 日志显示第2次 "cache HIT"，耗时 < 100ms
**依赖**: 建议前置P1-4（缓存原子操作改造涉及同模块）
**工时**: 0.5 人日

### P1-4: 编译缓存 check-insert 非原子性

**严重度**: P1
**来源**: 审计维度B
**策略**: GP §5.4（缓存一致性 — check-then-insert 必须原子）
**问题**: `compile_api.rs` 编译缓存实现为 check-then-insert：先 `if !cache.contains(key)` 检查，后 `cache.insert(key, result)` 写入。无锁保护下并发N个请求同时通过检查，全部执行全量编译，浪费CPU且可能导致资源耗尽。
**方案**:
1. 将缓存容器从 `HashMap` 替换为 `Mutex<HashMap<CacheKey, Arc<CompileResult>>>`
2. 原子操作：`cache.lock().entry(key).or_insert_with(|| compile(...))`
3. 对首次编译的未来请求去重：编译中标记 `CompileStatus::InProgress`，后续请求 await 同一 future
4. 或使用 `moka` / `cache-padded` 线程安全缓存库替代手写HashMap
**验收**: 10个并发 `compile(graph)` 请求 → 仅第1个执行实际编译，其余9个返回同一缓存结果
**依赖**: 建议与P1-3同批次修复（同文件）
**工时**: 1 人日

### P1-5: 告警去重 TOCTOU 竞态

**严重度**: P1
**来源**: 审计维度B
**策略**: GP §9.3（告警引擎 — 告警去重必须原子）
**问题**: `alert_engine.rs` `trigger_alert_check` 存在经典TOCTOU窗口：(1) 查询告警是否已触发；(2) 若未触发则插入新告警。步骤(1)和(2)之间其他协程可能插入相同告警，导致同一条件下多次触发。
**方案**:
1. 数据库层：告警表添加 `UNIQUE(rule_id, alert_key, status)` 约束 + `INSERT OR IGNORE`
2. 内存层：维护 `Mutex<HashSet<AlertFingerprint>>` 最近100条告警指纹，作为前置快速去重
3. 指纹包含 `(rule_id, metric_name, triggered_at_epoch / 60)` 允许每分钟至少触发一次
4. 内存指纹超过100条时淘汰最旧条目
**验收**: 并发触发同一条告警条件（同一rule_id同一指标值）→ 数据库仅存1条；不同分钟再次触发 → 可生成新告警
**依赖**: 建议与P1-6同批次修复（同模块同文件）
**工时**: 1 人日

### P1-6: 告警恢复持写锁等I/O

**严重度**: P1
**来源**: 审计维度B
**策略**: GP §9.3（告警引擎 — 告警恢复不应阻塞并发读）
**问题**: `alert_engine.rs` 在告警恢复路径中持有 `Mutex` 写锁的同时执行磁盘I/O（写告警文件、更新数据库持久化）。持有锁期间所有读操作（告警列表查询、状态检查）被阻塞，严重时导致系统短暂无响应。
**方案**:
1. 将写锁保护范围缩小：锁内仅更新 `AlertStatus` 内存状态（纳秒级）
2. 磁盘I/O和数据库写入移至锁外，通过异步任务执行
3. 使用 `RwLock` 替代 `Mutex`：恢复状态判断使用读锁，写入新状态时短暂升级为写锁
4. 添加性能测试：并发读请求数在告警恢复前后无显著变化
**验收**: 告警恢复时执行 `SELECT count(*) FROM alerts` 不受阻塞；并发10个读请求P99 < 5ms
**依赖**: 建议与P1-5同批次修复
**工时**: 1 人日

### P1-7: refresh_tokens 表无TTL清理

**严重度**: P1
**来源**: 审计维度D+E
**策略**: GP-TTL-CLEANUP（存储生命周期 — 过期数据必须自动清理）
**问题**: `auth/mod.rs` 中 `refresh_tokens` 表只增不删。refresh token 过期后（默认7天）仍占用存储空间。长期运行后表膨胀至数十万行，拖慢 `SELECT ... WHERE expires_at > now()` 和 `INSERT` 性能。且无清理机制意味着token泄漏后永不可彻底删除。
**方案**:
1. 在 `auth/mod.rs` 中 `init_db` 或启动后 `spawn` 定时清理任务：每小时执行 `DELETE FROM refresh_tokens WHERE expires_at < datetime('now', '-7 days')`
2. 每次清理上限 5000 行，避免长事务
3. 清理间隔可配置（环境变量 `REFRESH_TOKEN_CLEANUP_INTERVAL_MINUTES`）
4. 添加 `last_cleanup_count` 和 `last_cleanup_at` 指标
**验收**: 手动插入100条已过期token → 触发清理 → `SELECT count(*) FROM refresh_tokens WHERE expires_at < datetime('now')` = 0
**依赖**: 建议与P1-8同批次（同表操作）
**工时**: 0.5 人日

### P1-8: refresh_tokens 表缺索引

**严重度**: P1
**来源**: 审计维度D+E
**策略**: GP §7.2（数据库性能 — 高频查询路径必须有索引）
**问题**: `refresh_tokens` 表无任何索引。所有查询（按 `user_id` 查活跃token、按 `expires_at` 查过期token）均走全表扫描。随着token数增长超过1000条，查询延迟急剧上升。
**方案**:
1. 添加单列索引：`CREATE INDEX IF NOT EXISTS idx_refresh_tokens_expires_at ON refresh_tokens(expires_at)`
2. 添加单列索引：`CREATE INDEX IF NOT EXISTS idx_refresh_tokens_user_id ON refresh_tokens(user_id)`
3. 若查询模式经常为 `WHERE user_id = ? AND expires_at > ?`，可考虑复合索引 `(user_id, expires_at)`
4. 迁移脚本需兼容已有数据库（`IF NOT EXISTS`）
**验收**: `EXPLAIN QUERY PLAN SELECT id FROM refresh_tokens WHERE user_id = ? AND expires_at > ?` 显示 `SEARCH ... USING INDEX`
**依赖**: 建议与P1-7同批次
**工时**: 0.5 人日

### P1-9: 策略参数面板 strategyId 切换竞态

**严重度**: P1
**来源**: 审计维度F+G
**策略**: GP §5.3（前端异步状态一致性 — 请求响应必须与当前UI状态匹配）
**问题**: `StrategyParamsPanel.jsx` 中使用 `useEffect` 监听 `strategyId` 变化后发起异步请求 `GET /strategies/{id}/params`。当用户快速切换策略时，多个请求并发发出，后选择的策略响应可能晚到，前选择的策略响应覆盖正确数据，导致参数面板显示错乱。
**方案**:
1. 在 `useEffect` cleanup 中设置 `cancelled` 标志，请求回调检查标志后跳过状态更新
2. 或使用 `AbortController` 在 `strategyId` 变化时主动取消未完成请求
3. 或使用请求序列号：每次请求附带递增 `seq`，仅当响应 `seq === latestSeq` 时更新state
4. 添加 loading indicator：切换策略时显示加载骨架屏，避免数据跳跃
**验收**: 快速切换策略列表（200ms间隔切换5次）→ 参数面板始终与当前选中的strategyId一致，无数据错乱
**依赖**: 无
**工时**: 1 人日

### P1-10: 确认弹窗缺焦点/ARIA/esc

**严重度**: P1
**来源**: 审计维度F+G
**策略**: GP §2.5（前端可访问性 — 弹窗必须支持键盘导航和屏幕阅读器）
**问题**: `ExecutorTopBar.jsx` 的 Paper/Live 模式切换确认弹窗三项违规：(1) 无焦点捕获，Tab键可跳出弹窗操作背后元素；(2) 无 ARIA 属性，screen reader 无法感知弹窗内容和角色；(3) Esc 键不关闭弹窗，键盘用户无法退出。
**方案**:
1. 焦点管理：弹窗打开时 `focus()` 到"取消"按钮；监听 `Tab` 键在弹窗内循环（`focus-trap` 模式）
2. ARIA 属性：`div` 添加 `role="alertdialog"`, `aria-modal="true"`, `aria-labelledby="dialog-title"`, `aria-describedby="dialog-desc"`
3. Esc 关闭：`onKeyDown` 中 `e.key === 'Escape'` → 触发取消回调
4. 焦点归还：弹窗关闭后将焦点返回到触发切换的"Live"按钮
**验收**: Tab键无法跳出弹窗范围 / 按Esc关闭弹窗 / 屏幕阅读器识别role和标题 / 关闭后焦点返回触发按钮
**依赖**: 无
**工时**: 1 人日

## P2 — 质量收口 (23项, 预计 16.5 人日)

### P2-1: init_db 缺 foreign_keys=ON

**严重度**: P2
**来源**: 审计维度D+E
**策略**: GP §9.2（数据完整性 — 外键约束必须激活）
**问题**: `init_db` 函数创建SQLite连接后未执行 `PRAGMA foreign_keys = ON`。SQLite 默认外键约束关闭，定义的外键仅作文档用途，引用违规不报错。
**方案**:
1. 在 `init_db` 中 `conn.execute_batch("PRAGMA foreign_keys = ON;")` 紧随连接创建之后
2. 验证外键是否真正生效：插入违反外键的数据应被拒绝
**验收**: `PRAGMA foreign_keys` 返回 `1`；插入不存在 user_id 的 token 行 → SQLite 返回约束错误
**依赖**: 无
**工时**: 0.5 人日

### P2-2: 错误代码重载 token_invalid

**严重度**: P2
**来源**: 审计维度A
**策略**: GP §5.1（错误码设计 — 不同语义必须有不同编码）
**问题**: `error_codes.rs` 中 `ERROR_TOKEN_INVALID` 和 `ERROR_TOKEN_EXPIRED` 被赋值为相同数值，前端/客户端无法区分"token格式错误"和"token已过期"两种不同语义。
**方案**:
1. 为 `ERROR_TOKEN_INVALID` 和 `ERROR_TOKEN_EXPIRED` 分配不同数值
2. 更新所有引用点，确保正确的错误码被用在正确的上下文中
3. 添加注释说明两值的语义区别
**验收**: `assert_ne!(ERROR_TOKEN_INVALID, ERROR_TOKEN_EXPIRED)` 通过
**依赖**: 无
**工时**: 0.5 人日

### P2-3: refresh_handler 死条件分支两个401

**严重度**: P2
**来源**: 审计维度A
**策略**: GP §2.8（用户认证 — 错误响应应有区分度）
**问题**: `auth/mod.rs` 的 `refresh_handler` 中两个条件分支都返回 HTTP 401，但语义不同："refresh token 不存在"和"refresh token 已过期"。客户端无法区分两种失败原因，无法做差异化处理（如前者应重新登录，后者可尝试静默刷新）。
**方案**:
1. 两个分支返回不同 HTTP 状态或响应体：不存在 → 401 + `{"error": "refresh_token_not_found"}`，已过期 → 401 + `{"error": "refresh_token_expired"}`
2. 更新前端/客户端对应错误处理逻辑
**验收**: 传入不存在的 refresh_token → `{"error":"refresh_token_not_found"}`；传入已过期 token → `{"error":"refresh_token_expired"}`
**依赖**: 无
**工时**: 0.5 人日

### P2-4: JWT生成失败静默回退

**严重度**: P2
**来源**: 审计维度E
**策略**: GP §5.2（禁止静默忽略 — 失败必须记录且不执行危险回退）
**问题**: `auth/mod.rs` 中JWT签名生成失败时静默返回旧access token，无日志、无错误提示。客户端拿到旧token继续请求，直到token真正过期才报错，期间用户不知认证已降级。
**方案**:
1. JWT生成失败时记录 `error!` 日志，包含用户ID和错误详情
2. 不返回旧token，改为向客户端返回 500 + `{"error":"token_generation_failed"}`
3. 客户端收到此错误后引导用户重新登录
**验收**: 模拟JWT签名密钥缺失 → `error!`日志写入 → 客户端收到 500 而非旧token
**依赖**: 无
**工时**: 0.5 人日

### P2-5: user 字段可能为 null

**严重度**: P2
**来源**: 审计维度A
**策略**: GP §2.7（API输出 — 字段类型应精确反映可空性）
**问题**: 部分API响应的 `user` 字段类型为 `Option<serde_json::Value>`，但前端按非空对象处理。当 `user` 为 `null` 时前端 `user.name` 访问导致运行时异常。
**方案**:
1. 后端审计：检查所有 `user` 字段返回路径，确保不会返回 `null`
2. 若存在合法的 null 场景，后端返回明确的错误码而非 `user: null`
3. 前端添加防御性检查：`user?.name ?? '未知用户'`
**验收**: 所有API返回中 `user` 字段不为 `null`；前端 `user` 为 `null` 时显示"未知用户"而非白屏
**依赖**: 无
**工时**: 1 人日

### P2-6: 已解警告警磁盘文件不删除

**严重度**: P2
**来源**: 审计维度D
**策略**: GP §7.4（存储生命周期 — 已无引用数据必须清理）
**问题**: 告警状态从 `Firing` 转为 `Resolved` 后，对应磁盘上的告警证据文件（日志快照、指标截图等）未被删除。随时间累积占据磁盘空间，且可能与后续新告警的文件名冲突。
**方案**:

2. 删除采用 `try_remove_dir_all`，失败仅记录 `warn!` 日志，不阻塞主流程
3. 保留告警的数据库记录（仅清理证据文件）
**验收**: 告警从 Firing → Resolved → 对应 `storage/alerts/<alert_id>/` 目录被删除
**依赖**: 无
**工时**: 0.5 人日

### P2-7: 同步SQLite未用 spawn_blocking

**严重度**: P2
**来源**: 审计维度E
**策略**: GP §5.5（异步执行 — 阻塞操作必须委托阻塞线程池）
**问题**: SQLite操作（`rusqlite`）为同步阻塞API，某些调用路径直接使用 `await` 上下文执行而不包裹 `tokio::task::spawn_blocking`。这些调用阻塞 tokio 工作线程，导致同一线程上其他异步任务饥饿。
**方案**:
1. 审查所有 `rusqlite::Connection` 调用的 `mod.rs`、`auth/mod.rs`、`alert_engine.rs`、`compile_api.rs`
2. 将 `run`、`query_row`、`execute`、`prepare` 等阻塞调用包裹为 `spawn_blocking(move || ...)`
3. 对高频调用路径（每次HTTP请求都触发的查询）优先修复
4. 添加线程池指标监控
**验收**: 所有同步SQLite调用在异步上下文外执行；并发100请求情况下无tokio工作线程阻塞
**依赖**: 无
**工时**: 1 人日

### P2-8: 缓存驱逐 drain() panic 丢全部

**严重度**: P2
**来源**: 审计维度B
**策略**: GP §5.4（缓存稳定性 — 驱逐操作必须安全失败）
**问题**: 编译缓存或指标缓存的LRU驱逐使用 `HashMap::drain()` 方法。`drain()` 在迭代过程中若某个元素的drop实现panic，整个 `drain()` 操作中止，已迭代的元素被丢弃、未迭代的元素留在原集合中。这可能导致缓存状态不一致或全部数据丢失。
**方案**:
1. 将 `drain()` 替换为安全的逐条淘汰：`while cache.len() > MAX { cache.remove(oldest_key); }`
2. 或使用 `std::mem::take` 加 `retain`：先提取旧条目，再用 `extend` 插入保留条目
3. 每个淘汰操作包裹 `catch_unwind`，panic时记录错误并重建缓存
4. 引入 `moka` 等成熟缓存库替代手写LRU
**验收**: 缓存元素drop时panic → 缓存不丢失全部数据，仅丢失正在drop的条目
**依赖**: 无
**工时**: 1.5 人日

### P2-9: poison恢复丢失Live模式

**依赖**: 无

### P2-20: schema迁移无版本化

**严重度**: P2

**问题**: 数据库 schema 迁移通过 `init_db` 中的 `execute_batch` 直接执行，无版本号、无迁移历史表、不可回滚。新增字段或表需要手动改 `init_db` 脚本，不同版本之间数据库兼容性无法保证。

4. 每个迁移文件包含向上和向下（回滚）脚本
5. 当前schema版本标记为 v1，对应的init_db SQL作为第一次迁移
**验收**: `SELECT max(version) FROM schema_migrations` = 当前版本号；回滚迁移后状态恢复

### P2-21: 编译缓存无持久化（重启丢失）

**严重度**: P2
**来源**: 审计维度E
**策略**: GP §7.4（缓存持久化 — 重启后应恢复热缓存）
**问题**: 编译缓存仅存于内存 `HashMap`/`LruCache` 中，进程重启后全部丢失。重启后的首次编译请求都需全量运行QS管道，在频繁开发迭代场景下每次重启都造成数秒延迟。
**方案**:
1. 将编译缓存序列化到磁盘文件 `cache/compile_cache.{version}.bin`
2. 启动时通过 `mmap` 或 `serde` 反序列化加载
3. 每次写入缓存时异步更新磁盘文件（防丢失窗口 < 2s）
4. 缓存版本号与编译schema版本绑定，schema变化时自动丢弃旧缓存
5. 缓存文件最大 50MB，超限后丢弃最旧条目
**验收**: 编译策略图 → 重启进程 → 再次编译同策略图 → 命中磁盘缓存（< 200ms）
**依赖**: 无
**工时**: 2 人日
