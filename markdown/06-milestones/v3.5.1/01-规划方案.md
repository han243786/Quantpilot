## 方案

### 数据安全 (3项)

#### P1-1: rotate_refresh_token 无事务保护

**严重度**: P1
**来源**: 审计维度D+E
**策略**: GP §9.2（数据写入原子性）
**问题**: `rotate_refresh_token` 中删除旧refresh token和插入新token不在同一SQLite事务中。若在删除后、插入前进程崩溃，用户将永久丢失会话；若并发请求交错，可能产生重复token。
**方案**:
1. 将 `auth/mod.rs` 中 `rotate_refresh_token` 的DELETE和INSERT包裹为同一 `rusqlite::Transaction`
2. 事务提交前捕获 `rollback` 异常，确保原子回滚
3. 添加单元测试：模拟写入异常后验证token表状态一致
**验收**: 模拟 `rotate_refresh_token` 中途崩溃 → token表数据一致，不存在孤儿子孙token

#### P1-7: refresh_tokens 表无TTL清理

**严重度**: P1
**来源**: 审计维度D+E
**策略**: GP-TTL-CLEANUP（存储生命周期管理）
**问题**: `refresh_tokens` 表只增不删，已过期refresh token永久占用存储空间。长期运行后该表膨胀至数十万行，拖慢token查询和刷新性能。
**方案**:
1. 在 `auth/mod.rs` 启动初始化或定时任务中添加 `DELETE FROM refresh_tokens WHERE expires_at < datetime('now')`
2. 清理周期：每小时执行一次，每次最多清理5000条防锁
3. 添加 `last_cleanup_at` 监控指标
**验收**: 插入100条过期token → 手动触发清理 → `SELECT COUNT(*) FROM refresh_tokens WHERE expires_at < datetime('now')` 返回0

#### P1-8: refresh_tokens 表缺索引

**严重度**: P1
**来源**: 审计维度D+E
**策略**: GP §7.2（数据库性能）
**问题**: `refresh_tokens` 表无索引，到期清理和按 `user_id` 查询均走全表扫描。token刷新高频路径上的延迟随表增长线性恶化。
**方案**:
1. 为 `refresh_tokens` 表添加索引：`CREATE INDEX idx_refresh_tokens_expires_at ON refresh_tokens(expires_at)`
2. 添加复合索引：`CREATE INDEX idx_refresh_tokens_user_id ON refresh_tokens(user_id)`
**验收**: `EXPLAIN QUERY PLAN SELECT ... FROM refresh_tokens WHERE user_id = ?` 显示 `SEARCH ... USING INDEX`

### 并发安全 (4项)

#### P1-4: 编译缓存 check-insert 非原子性

**严重度**: P1
**来源**: 审计维度B
**策略**: GP §5.4（缓存一致性）
**问题**: 编译缓存实现为 check-then-insert 模式：先检查缓存是否存在，不存在则插入。无锁保护下，多个并发编译请求对同一策略图均通过检查，导致重复编译和资源浪费。
**方案**:
1. 将缓存操作包裹为 `Mutex<HashMap<CacheKey, CacheEntry>>` 或使用 `once_cell::sync::Lazy` + `RwLock`
2. check-then-insert 合并为原子操作：`cache_map.entry(key).or_insert_with(|| compile(...))`
3. 对并发编译同一图的N个请求，仅第一个执行编译，其余等待结果（future dedup）
**验收**: 10个并发请求编译同一策略图 → 实际编译执行次数 = 1，其余9次命中缓存

#### P1-5: 告警去重 TOCTOU 竞态

**严重度**: P1
**来源**: 审计维度B
**策略**: GP §9.3（告警引擎 — 告警去重原子性）
**问题**: `alert_engine.rs` 中告警触发逻辑存在 Time-of-Check-Time-of-Use 窗口：先检查该告警是否已触发，再插入新告警记录。两个检查之间其他线程可能已插入相同告警，导致重复告警。
**方案**:
1. 使用数据库唯一约束 `(rule_id, alert_key, status)` 或 `INSERT OR IGNORE` 实现去重
2. check-insert 合并为一条原子SQL：`INSERT INTO alerts (...) VALUES (...) ON CONFLICT(rule_id, alert_key) DO NOTHING`
3. 内存中保留最近N条告警指纹的 `HashSet` 作为前置过滤（受 `Mutex` 保护）
**验收**: 并发10个线程同时触发同一告警 → 数据库仅产生1条告警记录

#### P1-6: 告警恢复持写锁等I/O

**严重度**: P1
**来源**: 审计维度B
**策略**: GP §9.3（告警引擎 — 告警恢复不应阻塞读路径）
**问题**: `trigger_alert_check` 在告警恢复路径中持有写锁的同时执行磁盘I/O（写告警文件、更新数据库），期间阻塞所有读操作，导致系统短暂不可用。
**方案**:
1. 将告警记录的磁盘I/O操作移到写锁释放之后
2. 使用两阶段提交：锁内仅更新内存状态，锁外异步执行数据库写入
3. 或使用 `RwLock` 替代写锁，仅在写入数据库时短暂升级为写锁
**验收**: 告警恢复期间，其他goroutine读内存状态不被阻塞（并发read不受影响）

#### P1-9: 策略参数面板 strategyId 切换竞态

**严重度**: P1
**来源**: 审计维度F+G
**策略**: GP §5.3（前端异步状态一致性）
**问题**: `StrategyParamsPanel.jsx` 在 `strategyId` 快速切换时发出多个异步请求。由于响应到达顺序不确定，后选择的策略可能被先响应的旧数据覆盖，导致参数面板显示与当前选中策略不一致。
**方案**:
1. 使用 `AbortController` 或标志变量取消strategyId变更前的未完成请求
2. 或使用 `useEffect` cleanup 函数设置 `let cancelled = true` 标志，响应到达时检查 `cancelled` 跳过旧响应
3. 添加请求序列号：每次请求附带自增ID，响应处理时仅接受等于当前序列号的结果
**验收**: 在策略列表中快速切换（每秒切换5次）→ 参数面板始终显示当前选中策略的参数，无闪烁或错乱

### API规范 (2项)

#### P1-2: is_condition_resolved 忽略 resolve_condition 字段

**严重度**: P1
**来源**: 审计维度A
**策略**: GP §9.3（告警引擎 — 每条告警规则必须有恢复条件）
**问题**: `is_condition_resolved` 函数硬编码检查 `data_freshness < 60` 阈值，完全忽略 `AlertRule.resolve_condition` 字段。用户自定义的恢复条件表达式永不生效，告警只能手动确认解除。
**方案**:
1. 修改 `is_condition_resolved(rule: &AlertRule, ctx: &EvalContext) -> bool`：优先使用 `rule.resolve_condition` 表达式
2. 若 `resolve_condition` 为 `None`，回退到当前硬编码逻辑（保持向后兼容）
3. 若表达式解析失败，记录警告日志并返回 `false`（安全降级）
**验收**: 创建含 `resolve_condition = "data_freshness < 120"` 的告警规则 → 触发后等待 data_freshness 降至 120 以下 → 告警自动 Resolved

#### P1-3: 编译缓存 key 含 compile_id 致缓存失效

**严重度**: P1
**来源**: 审计维度A
**策略**: GP §5.4（缓存有效性 — key不应包含每次变化的量）
**问题**: 编译缓存的 key 中包含了 `compile_id`（每次自增的唯一ID）。因 `compile_id` 每次都不同，相同的策略图每次编译都生成不同的 key，缓存永不命中，形同虚设。
**方案**:
1. 从缓存 key 中移除 `compile_id`
2. 重新定义缓存 key 为 `(graph_hash: String, compile_options_hash: String)` 二元组
3. `compile_id` 仅用于日志追踪和审计，不作为缓存标识
**验收**: 相同策略图连续编译2次 → 第一次全量编译（2-5s），第二次命中缓存（<100ms）

### 前端质量 (2项)

#### P1-10: 确认弹窗缺焦点/ARIA/esc

**严重度**: P1
**来源**: 审计维度F+G
**策略**: GP §2.5（前端可访问性 — 弹窗焦点管理 + ARIA）
**问题**: `ExecutorTopBar.jsx` 中 Paper/Live 模式切换的确认弹窗：无焦点捕获（Tab可跳出弹窗操作背后元素）、无 ARIA 属性（屏幕阅读器无法感知弹窗存在）、Esc 键不关闭弹窗。
**方案**:
1. 焦点捕获：弹窗打开时自动聚焦"取消"按钮；Tab循环限制在弹窗内（`focus-trap` 或手动 `keydown` 监听）
2. ARIA：添加 `role="alertdialog"`、`aria-modal="true"`、`aria-labelledby` 关联标题元素
3. Esc 关闭：监听 `keydown === Escape` 触发取消操作
4. 关闭时焦点归还：弹窗关闭后将焦点返回到触发切换的按钮
**验收**: Tab键循环仅在弹窗内 / Esc键关闭弹窗 / 屏幕阅读器读出弹窗标题和选项
