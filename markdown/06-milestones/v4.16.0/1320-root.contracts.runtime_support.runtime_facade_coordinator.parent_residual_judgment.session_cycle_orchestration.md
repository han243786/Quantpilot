## Selected Child Boundary

`session_cycle_orchestration` owns the high-level runtime session and cycle orchestration methods:

- `RuntimeCoordinator::run_session`
- `RuntimeCoordinator::run_slow_cycle`
- `RuntimeCoordinator::run_fast_cycle`
- `RuntimeCoordinator::run_cycle`

The child owns orchestration flow only:

- apply pending module config at session boundary
- run slow and fast cycles
- invoke risk monitor stop-state check after a session
- build per-cycle trace IDs
- sequence data collection, open-order processing, portfolio refresh, intent evaluation, agent evaluation, merge, risk evaluation, execution planning, execution, final portfolio refresh, and runtime event assembly
- assemble `SessionOutput` and `RuntimeCycleOutput`

## Exclusions

The selected child does not own:

- `RuntimeCoordinator` struct definition
- constructor/provider wiring
- execution submission method body
- market data update entry point
- state/config accessors
- module config swap/apply implementation
- config generation history mutation
- provider delegation helper implementations
- portfolio update projection helper
- coordinator test harness

Provider delegation helpers may stay in the parent during this child extraction. A later child can decide whether those helpers belong to session orchestration or a separate delegation leaf.

## Split Decision

`continue_split: true`.

Reasons:

- session/cycle orchestration is a public behavior cluster with clear entry points
- it coordinates many private helper calls but does not itself own their implementation details
- extracting it reduces parent weight while preserving the runtime facade shape
- remaining execution, state/config, config generation, portfolio projection, and test harness clusters still have independent owner boundaries

No release-transition optimization is proposed.
