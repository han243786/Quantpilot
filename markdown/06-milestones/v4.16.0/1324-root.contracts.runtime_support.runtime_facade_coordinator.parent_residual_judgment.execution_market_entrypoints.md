## Selected Child Boundary

`execution_market_entrypoints` owns the public execution and market-data entry point methods:

- `RuntimeCoordinator::submit_execution_plan`
- `RuntimeCoordinator::on_market_data`

The child owns the entrypoint flow only:

- lock the execution module safely through poisoned-lock recovery
- submit execution plans through `ExecutionModuleProvider::submit_plan`
- forward market data through `ExecutionModuleProvider::on_market_update`
- pass mutable portfolio state into the execution provider
- refresh portfolio state after execution or market update
- return `qrpc_core::FillResult`

## Exclusions

The selected child does not own:

- `RuntimeCoordinator` struct definition
- constructor/provider wiring
- session/cycle orchestration
- state/config accessors
- module config mutation and config generation
- provider delegation helper implementations
- `refresh_portfolio_state` implementation
- `portfolio_update_event`
- coordinator tests

`refresh_portfolio_state` remains parent-owned for now because it is also used by session/cycle orchestration and is a better fit for the later portfolio projection leaf.

## Split Decision

`continue_split: true`.

Reasons:

- execution and market entrypoints are a cohesive public API cluster
- the cluster is small enough to extract without dragging portfolio projection into the same child
- keeping `refresh_portfolio_state` in the parent preserves a clean later split target
- remaining state/config, config generation, provider delegation, portfolio projection, and tests still have independent owner boundaries

No release-transition optimization is proposed.
