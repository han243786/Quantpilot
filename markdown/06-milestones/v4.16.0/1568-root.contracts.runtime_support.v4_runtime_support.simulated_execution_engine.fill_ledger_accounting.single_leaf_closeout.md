## Stop-Split Rationale

`fill_ledger_accounting` has a single owner: converting an accepted existing order into fill, fee, portfolio, and ledger side effects. It remains intentionally parent-mediated:

- trigger flow calls `fill_existing_order` through the simulated execution state boundary;
- direct-submit orchestration calls `apply_fill_to_ledger` through the same parent boundary;
- validation, snapshot projection, microstructure metrics, and direct-submit orchestration remain outside this child.

Rejected finer splits:

| Candidate | Decision | Reason |
| --- | --- | --- |
| `fill_existing_order` | Reject | It owns fill projection and event ordering around one existing-order fill path; splitting would only move half of one fill transaction. |
| `apply_fill_to_ledger` | Reject | Ledger mutation is coupled to fill price, fee, side/action semantics, average price math, and position market value updates. |
| fee projection child | Reject | Fee math is embedded in the fill event/ledger transaction and is too small to own independently. |
| position accounting child | Reject | Position accounting would be a tiny helper behind the same fill transaction and would increase call indirection. |
