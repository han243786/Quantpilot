## Candidate Boundary

`fill_ledger_accounting` should evaluate the helper cluster around fill execution and ledger mutation:

- `fill_existing_order`;
- `apply_fill_to_ledger`;
- fill record construction and fee event projection shared by direct submit and triggered fills;
- position average price, signed quantity, market value, and cash balance updates;
- asset point recording only if the baseline proves it can move without taking snapshot projection ownership.

The next baseline must decide whether direct-submit fill construction inside `submit_order` can be extracted into a narrow helper, or whether it must remain parent-owned until a later parent facade/orchestration pass.

## Exclusions

The selected child must not own:

- `submit_order` wholesale;
- request validation and pre-execution rejection helper families;
- non-executable resting order admission;
- market trigger sweep already closed in `market_trigger_flow`;
- order lifecycle internals already closed in `order_lifecycle_flow`;
- snapshot projection and microstructure metrics;
- runtime adapter behavior already closed in `runtime_adapter`;
- v4 tests.

## Stop Conditions

Stop and request scope review if the next baseline or extraction requires:

1. moving `submit_order` wholesale;
2. changing fill event names, event order, payload shapes, order status values, fee semantics, or position accounting math;
3. moving snapshot projection or microstructure metrics into fill accounting;
4. adding direct child-to-child calls that bypass the simulated execution parent;
5. changing public runtime API, route/schema, persistence owner, lock owner, or runtime mode;
6. entering release-transition performance optimization.
