## Candidate Boundary

`market_trigger_flow` should evaluate the helper cluster around conditional order execution:

- `update_market_price` entrypoint behavior, but the next baseline must decide whether it stays as parent orchestration or moves behind a wrapper;
- `check_order_triggers`;
- `update_trailing_stop`;
- `request_from_order`;
- interaction with `order_lifecycle_flow.expire_orders` and `order_lifecycle_flow.cancel_oco_siblings` only through parent-visible methods;
- trigger-event ordering around stop/limit/take-profit/trailing-stop conversions.

The candidate owns trigger eligibility and conversion from resting order state to execution request. It does not own fill ledger mutation.

## Exclusions

The selected child must not own:

- `submit_order` validation and direct submit orchestration;
- fill construction, fill application, ledger/accounting mutation, fee charging, and asset curve mutation;
- snapshot projection, microstructure metrics, or asset point projection;
- request validation and pre-execution rejection helper families;
- order lifecycle helper internals already closed in `order_lifecycle_flow`;
- runtime adapter behavior already closed in `runtime_adapter`;
- v4 tests.

## Stop Conditions

Stop and request scope review if the next baseline or extraction requires:

1. changing event names, event order, payload shapes, or order status semantics;
2. moving `fill_existing_order` or `apply_fill_to_ledger` into trigger flow;
3. adding direct child-to-child calls that bypass the simulated execution parent;
4. changing public runtime API, route/schema, persistence owner, lock owner, or runtime mode;
5. entering release-transition performance optimization.
