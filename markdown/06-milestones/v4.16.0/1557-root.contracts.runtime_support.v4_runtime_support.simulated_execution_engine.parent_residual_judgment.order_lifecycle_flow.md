## Decision

Select `order_lifecycle_flow` as the next child under `simulated_execution_engine`.

The remaining simulated execution implementation is still an oversized high-risk trading and state-machine leaf. The next split should isolate order-book lifecycle state transitions before touching market triggers, fill ledger accounting, snapshot projection, or validation helper families.

## Boundary

`order_lifecycle_flow` owns the order lifecycle helper layer currently held in `qrpc_runtime/src/v4_simulated_execution.rs`:

- accepted order construction and order id sequencing;
- order rejection and existing-order rejection event projection;
- OCO bracket order registration and linked leg setup;
- cancel-replace amend flow for open accepted orders;
- order expiry flow;
- OCO sibling cancellation after a filled linked order;
- order history trimming policy for order book retention.

The next baseline must decide whether the `submit_order` public orchestration remains parent-owned while only lifecycle helpers move, or whether a narrower wrapper can move without creating sibling horizontal calls. It must not move `submit_order` wholesale if doing so pulls validation, fill construction, ledger mutation, and portfolio snapshot projection into this child.

## Exclusions

The selected child must not own:

- market price update, conditional trigger sweep, trailing stop update, or conditional execution conversion;
- fill construction, fill application, ledger/accounting mutation, fee charging, asset curve mutation, or portfolio valuation;
- snapshot projection or microstructure metrics;
- simulated order request validation, capability derivation, payload parsing, or token normalization helper families;
- v4 runtime adapter layer already closed in `runtime_adapter`;
- v4 tests.
