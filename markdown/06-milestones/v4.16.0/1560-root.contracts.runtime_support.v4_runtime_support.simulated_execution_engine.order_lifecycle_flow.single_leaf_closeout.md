## Stop-Split Rationale

`order_lifecycle_flow` is within the target terminal leaf range and has one owner: simulated order lifecycle state transitions. It has several outward-facing helper methods because the parent and sibling v4 runtime orchestration still need parent-mediated access, but those methods operate on the same state owner and event vocabulary.

Rejected finer splits:

| Candidate | Decision | Reason |
| --- | --- | --- |
| OCO registration | Reject | Shares accepted-order construction, order id sequencing, retention trimming, and portfolio event emission. |
| Amend flow | Reject | Shares existing-order rejection, order status validation, asset point recording, and same order book state. |
| Reject helpers | Reject | Rejection count and order event projection are shared by submit, amend, trigger, and future fill flows. |
| Expiry flow | Reject | Expiry must stay near order lifecycle retention and event projection; splitting would add sibling coupling. |
| Retention trimming | Reject | Too small as an independent child and called by multiple lifecycle changes. |
