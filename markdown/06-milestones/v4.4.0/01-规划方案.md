# v4.4.0 规划方案 — 嵌套状态机 (第一波)

> 版本类型: MINOR | 基准: v4.3.0 | 终稿确认: 2026-05-25
> 来源: v4.0.0 规划文档 §非目标 首项 — "任意层级嵌套状态机作为后续潜在优化方向"

---

## 目标

v4.4.0 开放 v4.0.0 以来最大的 deferred 能力——嵌套状态机。当前 QS 的 `machine` block 内只能声明扁平的 `state + state_group`。本版本允许 machine 内部嵌套子 machine，形成两级状态机层次。

1. **父-子状态层次** — machine 内的 `state` 可以包含子 `machine`，子 machine 有自己的状态/transition/memory
2. **跨层 transition 优先级** — 父层 transition 高于子层，但子层 transition 在父状态未匹配时生效
3. **复杂度预算强制执行** — 嵌套后状态空间、transition 数、事件处理路径数受 `ComplexityBudgetContract` 约束
4. **性能与审计警告** — UI 在嵌套状态机运行时展示状态空间大小、最大嵌套深度、事件处理路径数和回放成本

核心变化:

- v4 QS 静态审计从 "嵌套 machine block → QSV4104 拒绝" 变为 "接受但校验深度 ≤2 和预算"
- UI 展示嵌套层次和预算使用率
- 这是 v4.0.0 规划文档明确标注的"后续潜在优化方向"的第一版落地

## 非目标

- 不在 v4.4.0 开放超过 2 层的深度嵌套 (三级及以上为 reserved)
- 不开放跨父 machine 的子 machine 通信
- 不改变顶层 DAG 无环约束
- 不把嵌套状态机设为默认策略模板
- 不新增 Machine 模板类型 (仍为 Observation/Decision/Execution 三种)

## W1 — 嵌套状态机: 类型系统 + 校验 (2 天)

### W1-1 Core IR 嵌套类型定义

**文件**: `qrpc_core_ir/src/v4.rs`

**方案**: `MachineState` 增加 `child_machine: Option<V4MachineContract>` 字段。子 machine 复用现有 `V4MachineContract` 结构，但受额外约束：
- 子 machine 的 `template` 必须与父 machine 相同（Observation 下只能嵌套 Observation）
- 子 machine 不能继续嵌套（深度限制为 2）
- 子 machine 的 transition 优先级低于父 machine 的同 state transition

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_core_ir/src/v4.rs` | `MachineState` 增加 `child_machine: Option<Box<V4MachineContract>>` |
| 2 | 同上 | `validate_static_contract()` 增加深度检查 (max_depth=2) |
| 3 | 同上 | `ComplexityBudgetContract` 增加 `max_nesting_depth` 字段 |

**验收**: 定义含子 machine 的 V4MachineContract → 静态校验通过 → 深度 3 的嵌套 → 拒绝

### W1-2 QS 嵌套 machine 语法

**文件**: `quantscript/src/v4_static_audit.rs`

**方案**: 当前 QSV4104 拒绝 `machine` block 内出现 `machine`。修改为：
- 解析器接受 state 内嵌套的 `machine { ... }` block
- 静态审计校验嵌套深度 ≤ 2
- 子 machine 必须使用与父相同的 template
- 超深度返回 QSV4118 诊断码

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `quantscript/src/v4_static_audit.rs` | `parse_machine_block()` 接受嵌套 machine |
| 2 | 同上 | 新增 QSV4118: 嵌套深度超限 |
| 3 | 同上 | 新增 QSV4119: 父子 template 不匹配 |

**验收**: `machine obs observation { state idle { machine sub observation { ... } } }` → 解析通过

### W1-3 嵌套状态机复杂度预算

**方案**: `ComplexityBudgetContract` 新增：
- `max_nesting_depth` (默认 2)
- `max_total_states` (含子 machine，默认 1024)
- `max_total_transitions` (含子 machine，默认 2048)

静态校验拒绝超预算的嵌套策略。

**验收**: 嵌套策略状态总数 > 1024 → 静态校验拒绝

## W2 — 嵌套状态机 runtime (2.5 天)

### W2-1 事件路由到子 machine

**文件**: `qrpc_runtime/src/v4_runtime.rs`

**方案**: `process_event` 的事件候选发现逻辑扩展：
1. 先检查当前 state 是否有子 machine
2. 如有，先尝试子 machine 的 transition 匹配
3. 子 machine 无匹配时，回退到父 machine 的 transition
4. 父 machine transition 优先于子 machine（当两者都匹配同一事件时）

| 步骤 | 文件 | 改法 |
|------|------|------|
| 1 | `qrpc_runtime/src/v4_runtime.rs` | `process_event` 增加子 machine 遍历 |
| 2 | 同上 | 父 transition 优先级覆盖子 transition |

**约束**: GP §1.8 (transition 必须事件驱动)
**验收**: 父 state 的 transition 匹配事件 → 父 transition 执行，子 transition 被跳过

### W2-2 子 machine memory 隔离

**方案**: 子 machine 的 `memory` 字段独立于父 machine。子 machine 只能读写自己的 memory，父 machine 只能读写自己的 memory。父子之间通过 emit 事件通信。

**约束**: GP §1.7 (action block 不能跨节点直接修改 memory)
**验收**: 子 machine action block 写入 memory → 父 machine memory 不变

### W2-3 嵌套 machine 快照与回放

**方案**: `memory_snapshot()` 输出层级结构，`V4MachineRuntimeSnapshot` 增加 `child_snapshot: Option<Box<V4MachineRuntimeSnapshot>>`。

**验收**: 嵌套 machine 运行 → `memory_snapshot()` 包含子 machine 状态 → 前端可渲染

## W3 — UI 可视化 + 审计警告 (1 天)

### W3-1 V4RuntimeEvidencePanel 嵌套展示

**文件**: `frontend/src/components/V4RuntimeEvidencePanel.jsx`

**方案**: machine 状态行增加缩进层级，子 machine 缩进显示。hover 时展示子 machine 的 transition 历史。

**验收**: 嵌套 v4 策略运行 → 证据面板展示层级 machine 状态

### W3-2 复杂度预算面板

**文件**: `frontend/src/components/ComplexityBudgetPanel.jsx` (新增)

**方案**: 策略编译后在编译面板中展示复杂度预算使用率：

| 指标 | 预算 | 当前 |
|------|------|------|
| 嵌套深度 | 2 | 2 |
| 总状态数 | 1024 | 18 |
| 总 transition 数 | 2048 | 35 |
| 事件处理路径数 | 4096 | 120 |

超预算项标红，接近预算 (>80%) 标黄。

**约束**: v4.0.0 规划文档 §复杂度: "超预算时警告，严重超预算时拒绝运行。未来若启用嵌套状态机，必须显示状态空间、最大嵌套深度、事件处理路径和回放成本警告。"
**验收**: 编译嵌套策略 → 预算面板显示使用率 → 超预算时警告

## W4 — 收口与门禁 (0.5 天)

### W4-1 兼容桥更新

**方案**: v3 兼容桥 (`bridge_core_ir_to_v4_machine_graph`) 不受影响（不产生嵌套 machine）。旧图/旧 QS/旧运行记录继续正常读取。
